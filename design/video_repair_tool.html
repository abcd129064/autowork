文案口径（2026-11-07 修订，下方画布已按此同步）：界面上不用括号式旁白，一律改成 · 分隔的短句或逗号顺承；卡片说明压到两行以内，只留「为什么需要这个输入」与「填错会怎样」， 原理细节留给本文档与后端 docstring。耗时、兜底条件这类次要信息挪到悬停提示，不占正文。 终端输出同样去掉括号，字段之间用 · 或逗号分隔。
要解决的问题：球桌录制端写 mp4 时把 mdat 的 size 写成 0 占位（意为「一直吃到文件尾」）， 索引盒 moov 留到最后落盘。中途掉电/强制关机 → moov 永远没写出来， 播放器一律报 moov atom not found，文件看着有十几 MB 却完全打不开。
但媒体数据本身是完好的：mdat 里就是一整条 MPEG-4 Part 2 裸码流（00 00 01 B6 帧起始码 + 00 00 01 B3 GOP 起始码），只要补回一份配置头、按 GOP 边界切掉尾部半帧、重新封装成 mp4 就能播。
为什么需要「参考文件」：MPEG-4 短头码流里不带 VOL 头，分辨率/量化参数只存在于正常文件的 moov → stsd → esds → DecoderSpecificInfo（描述符链 0x03 → 0x04 → 0x05）里。 所以修复必须借同机同参数录制的正常文件提供这份头。
设计边界：本页只修「无 moov + mdat 尾扩展 + MPEG-4 Part 2(mp4v) 视频轨」这一类文件； 已含 moov 的文件、H.264/H.265、带音轨的文件一律在体检阶段明确拒绝并说明原因，不做猜测性修复。

无损证明是本工作区的核心可信度来源：输出 mp4 的 mdat 负载去掉借来的 VOL 后，必须与原文件 es[:cut] 的 SHA-256 相同。 校验通过时不再追加解释，只有不一致才补一句「与原件不一致，请人工核对」。报告同时经 _append_log 落主窗口日志，弹出窗口形态下转发主窗口，日志单源。

函数返回职责与关键约束
scan_boxes(path) -> dict{boxes, payload_off,
payload_size, has_moov,
mdat_last, ok, reason}		 用 mmap 顺序走顶层盒；size==0 解释为「吃到 EOF」。不整文件读进内存（几百 MB 的录像会撑爆 UI 进程）。 mdat_last 为假 → 切点不可信，直接判不可修复。
scan_frames(mm, off, size) -> dict{vops, gops, last_vop_tail,
median_frame}		 mmap 上 find() 扫 00 00 01 B6（VOP）与 00 00 01 B3（GOP）起始码，返回偏移列表； median_frame 用来判断末帧是否明显偏短（不完整）。
read_vol(path) -> bytes|NoneVOL 头原始字节 走 moov→…→esds 描述符链 0x03(ES) → 0x04(DecCfg) → 0x05(DecSpecificInfo)。 两个已知坑：① find(b"esds") 命中的是类型字段，描述符从 +8 起； ② 0x03 层有 ES_ID(2B)+flags(1B)，flags 最高位置位时还要再跳 dependsOn(2B)。
probe_reference(path) -> dict{codec, profile, w, h, fps,
has_audio, muxer}		 ffprobe 读参考文件；codec != mpeg4 或 has_audio 为真时体检判不支持。
discover_reference(broken) -> str|None参考文件路径 同目录按 mtime 倒序，取第一个 codec_name=mpeg4 且有 moov 的 mp4；排除损坏文件自身与已存在的 *_repaired.mp4。
pick_cut(vops, gops, mode) -> int裁剪偏移 auto（默认）：小于最后一个 VOP 偏移的最大 GOP 偏移 —— 切在最后一个 VOP 上会留下悬空 GOP 头，解码器改报 header damaged（实测）。 vop：直接取最后一个 VOP 偏移（仅在用户显式选择时用）。
repair(broken, ref, out, fps, mode,
on_line, should_stop) -> dict		{out, frames, duration,
dropped, sha_ok, decode_errors,
cancelled}		 四步：抽 VOL → 写 VOL + es[:cut] 到 tempfile.mkdtemp() 下的临时 .mpg（打包版没有 tools/ 目录，临时物一律走系统临时目录，用完即删）→ ffmpeg -f mpegvideo -framerate N -c:v mpeg4 -i in.mpg -c:v copy -avoid_negative_ts make_zero out.mp4 → ffprobe -count_frames + ffmpeg -f null - 数解码错误 + SHA-256 比对媒体字节。 必须显式 -c:v mpeg4：裸流无 mpeg1 序列头，ffmpeg 会自动误判成 mpeg1video 并报 「aspect ratio has forbidden 0 value / frame_rate_index 0 is invalid」。

线程与状态契约 workers/video_repair_worker.py（QThread，与 SingleVideoWorker 同形状）
项约定
VideoRepairWorker(stage, params) stage="probe"（体检，秒级）/ stage="repair"（重封装 + 校验）。 体检也走线程：mmap 扫起始码在 GB 级文件上是秒级操作，放 UI 线程会冻住整个 FluentWindow。
信号 line(str) 逐行输出 · probed(dict) 体检结果 · finished_ok(dict) 修复报告 · error(str) 失败原因。 与 SingleVideoWorker 一致，不用 finished 承载业务（那是 QThread 原生信号，遮蔽过会崩，见本仓 QThread 教训）。
busy 守卫 worker 引用挂宿主属性 _video_probe_worker / _video_repair_worker； 释放走 win._release_worker_safe(w)（线程仍在跑时交 finished→deleteLater，避免 GC 掉运行中的 QThread）。
取消 requestInterruption() + should_stop 回调 → 终止 ffmpeg 子进程、删除半成品输出与临时 .mpg、终端打印「已取消」。
settings 键 repair_last_ref（上次参考文件路径，同机录像固定，省得每次重选）· repair_auto_open_dir（完成后打开输出目录，默认关）· repair_cut_mode（默认 auto）· repair_fps（兜底帧率，默认 25）。
原文件保护 损坏文件全程只读打开（"rb" + mmap ACCESS_READ），输出永远是另一个路径； 输出路径与输入相同时直接报错，不给「覆盖原件」的机会。
不做的事 不支持 H.264/H.265（起始码体系与参数集不同，需要 SPS/PPS 重建，另立版本）； 不处理带音轨文件（流拷贝方案会丢音轨）；不做重编码（重编码 = 有损，与「无损修复」的定位冲突）； 不引入第三方修复库（untrunc 之类需要额外二进制分发）。
