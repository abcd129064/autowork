# 远程会话凭据与传输可靠性（2026-10-06）

> 范围：远程会话（SFTP / SSH）本轮三项加固 —— **凭据来源显式化**、**未完成传输队列落盘 + 两侧大小校验**、**终端远端工作目录（OSC 7）**；
> 外加 P0-5「共享 Transport」的**测量**（只测不改）。
> 接口契约见 [API.md](API.md) 的 `core.credentials` / `core.transfer_queue` / `core.transfer_verify` 三段；终端屏幕模型见 [终端全屏应用渲染修复.md](终端全屏应用渲染修复.md)。

## 一、改造前的具体行为（问题）

| # | 现象 | 根因 |
|---|------|------|
| 1 | 临时输一次别人的设备密码，就被永久写进 `config/credentials.json`，之后所有连接都用它 | 三处凭据入口（远程页 XTCP 卡 / TCP 卡、主面板 P2P 表单）**共用同一对键**，且"表单里当前是什么就写什么"；界面上看不到"这次用的是哪来的密码"，也没有清除入口 |
| 2 | 传输显示「已完成」，远端却是半个文件 | 成功判定只看 `sftp.put/get` 有没有抛异常；磁盘写满、中途断开导致的截断无声通过 |
| 3 | 排队中/传输中的任务一旦关标签或重启就消失 | 队列只活在 `SFTPPanel` 内存里（`_queued_transfers` / `_transfer_workers`） |
| 4 | 终端里 `cd` 到某目录后，想用 SFTP 看同一个目录只能手抄路径；会话恢复丢工作目录 | OSC 7（`\E]7;file://host/path\E\\`）被当"无影响的 OSC"丢弃（`core/vt_screen.py` 旧解析器） |
| 5 | 多文件传输时每一件都重新 SSH 登录一次 | `workers/network_workers.py` 的 `SFTPOperationWorker.run()` 每任务 `paramiko.Transport(...)` + `connect()`（浏览路径 `SFTPListWorker` 反倒复用了面板连接） |

## 三、凭据：来源与落盘策略

### 3.1 类别与键（`core/credentials.py`）

| 类别 | 常量 | 用户键 | 密码键 | 界面入口 |
|------|------|--------|--------|----------|
| 设备（XTCP 隧道主机） | `KIND_DEVICE` | `ssh_user` | `ssh_pass` | 远程页 XTCP 卡、主面板 P2P 表单 |
| 直连主机（经 frps / 局域网） | `KIND_DIRECT` | `tcp_ssh_user` | `tcp_ssh_pass` | 远程页 TCP 直连卡 |

两类键互不覆盖（2026-10-04 拆分，见 [CHANGELOG.md](CHANGELOG.md) 3.13 远程段）；`core/app_settings.KEY_DOMAIN` 里都在 `credentials` 域，密码键在 `core/secrets.SENSITIVE_KEYS`（DPAPI）。

### 3.2 解析优先级（`resolve_credentials`）

**逐字段**取 `表单 > 会话表 > 设置`，`source` 以**密码**的来源为准：

| 来源 | 含义 | `source_persisted` |
|------|------|--------------------|
| `SOURCE_FORM` | 用户此刻在表单里敲的 | 否（除非勾了"记住密码"并被保存流程写盘） |
| `SOURCE_SESSION` | 本次运行输过、但明确不落盘 | 否 |
| `SOURCE_SAVED` | 从设置读出来的（DPAPI 加密） | 是 |
| `SOURCE_NONE` | 没有可用密码 | 否 |

`Credentials.describe()` 只输出 `用户@来源`，**绝不含密码明文**。

### 3.3 "记住密码"未勾选时

`credential_patch(kind, username, password, remember=False)` 生成的补丁**在构造上就不含密码键**——不是"写了空值"，而是根本不碰，因此不会覆盖已保存的密码。控件把这次的密码放进 `SessionCredentialStore`，本次运行内继续可用，日志记「仅用于本次会话（未勾选记住密码，未写入 ssh_pass）」。

### 3.4 清除入口

`clear_patch(kind)` 默认只写 `{pass_key: ""}`（空串即清除，见 `core/secrets.encrypt_secret("")` 原样返回 `""`），保留账号名；两张卡各有一个「清除已保存凭据」按钮，带二次确认。

### 3.5 界面可见性

- 卡片下方常驻一行 `凭据来源：… · ssh_pass 已落盘，重启后仍在 / 未落盘，关闭窗口即丢失 / 不会写入配置文件`；
- 提示只把**与已保存值不同**的表单值算作"本次输入"（否则卡片一打开就把回填显示成"本次输入"，误导用户）；
- 主面板 P2P 表单与远程页 XTCP 卡是同一对键，勾选状态各自独立、键共享。

### 3.6 本轮没做

- 阶段 2（来源标签继续细化到"哪一次输入"）与阶段 3（密钥认证：`paramiko` 的 key 文件 / agent）未做；
- 未引入系统凭据管理器（Windows 凭据管理器）；DPAPI 不可用时（`core.secrets.dpapi_available()` 为假）行为与改造前一致。

## 四、传输可靠性

### 4.1 两侧大小校验（步骤 1a，`core/transfer_verify.py`）

传输结束后比对两端字节数，**一致才 `success.emit`**：

| 方向 | 期望值来自 | 校验对象 | 不一致时措辞 |
|------|-----------|----------|--------------|
| 上传 | 本地 `os.path.getsize` | 远端 `sftp.stat().st_size` | 「远端文件被截断（磁盘可能写满或传输中途断开）」 |
| 下载 | 远端 `sftp.stat().st_size` | 本地 `os.path.getsize` | 「本地文件被截断（…）」 |

- 实际比预期**大**时措辞改为「比另一端大（传输期间被改写？）」；
- 读不到大小：`unreadable()` **不谎报**"相差 N 字节"，只说读不到；本地大小未知（`<0`）或 `verify_size=False` 时跳过校验（单文件只记 info）；
- 目录传输 `SFTPDirTransferWorker` 逐文件校验，不一致的记进 `errors` 汇总成「部分失败」，**不计入** `transferred`。

### 4.2 未完成队列落盘（步骤 1b，`core/transfer_queue.py` + `sftp_window.py`）

- **存什么**：只存重做所需的最小集合 —— `op` / `name` / `local_path` / `remote_path` / `size`（**不含密码**，不含连接参数）；按 `host:port` 分组；每目标上限 200 条、最多 50 个目标（`prune_store`）。
- **何时写**：状态变化后 800ms 去抖（`_pending_save_timer`）；`shutdown()` 里同步 flush 一次（早于清 `_queued_transfers` 和释放 worker）。
- **恢复什么**：`state ∈ {queued, running, paused}` 的任务（正在跑的按"未完成"重做）；本地已不存在的路径跳过。
- **何时问**：SFTP 连接成功、`_retry_failed_transfers()` 之后**每面板只问一次**（`MessageBox`：恢复 / 忽略）；恢复出的任务仍走并发闸门（`_max_concurrent_transfers`，超出的排队）。
- **落盘位置**：设置键 `sftp_pending_queue`（域 `remote` → `config/remote.json`），容忍手改配置（`normalize_record` 只保留 5 个键，脏数据丢弃）。

### 4.3 步骤 3（字节级续传）为什么还没做

需要 `.part` 临时文件 + `SFTPFile.seek()` / `putfo` / `getfo` 的 offset + `posix_rename` 原子替换 + 传输后 `stat` 校验，并且**必须真机验证**（本地无法模拟半途断链）；另外现有 `pause()/resume()` 只是 Event 级（暂停的是进度回调，不是 TCP 流），续传语义要先与它对齐。

## 五、终端远端工作目录（OSC 7）

- **只消费不注入**：`core/vt_screen.py` 认 `\E]7;file://<host>/<path>\E\\`（BEL 或 ST 终止），`unquote` 解码后存 `cwd` / `cwd_host`；超过 1024 字节的 OSC 整条丢弃（截断的 OSC 7 会给出错路径，宁可不认）；清屏、切换备用屏幕不丢，`reset()` 清空。
- **谁发**：这是**服务端行为**。zsh 默认上报；CentOS 的 bash 需要一行 `PROMPT_COMMAND`（终端 chip 的 tooltip 里给了现成命令）。
- **消费点**：① 终端底部状态条 chip（home 缩写成 `~`）；② chip 右侧「在 SFTP 中打开」按钮 → `open_sftp_here` → `RemoteSessionManager._open_sftp_at()`（打开同一目标、同一个目录的 SFTP 面板，并把 `open_terminal_here` 接回去实现反向跳转）；③ 会话存档多存一个 `remote_path`，恢复时作为 SFTP/终端的起始目录。
- 未上报时不显示假路径：chip 留空、按钮置灰，tooltip 给出配置提示。

## 七、已知边界

- **offscreen 环境现象**：构造 `SFTPPanel` 后进程收尾以 `0xC0000005` 结束（rc=-1073741819），与本轮改动无关（`tools/_scratch/_probes/` 里的 `probe_sftp_exit_crash.py` 三种模式对照：只建 `QApplication` 正常、建面板即崩）；相关冒烟以末行 `SMOKE_OK` 判定。
- **共享 Transport 未改造**：`paramiko.SFTPClient` 同步且非线程安全，共享必须"一条 Transport + 每任务独立 channel + 独立 SFTPClient"，并处理断链重连与退出清理；先有并发闸门（已有）再谈。
- `config` 里的 `sftp_max_concurrent_transfers` 目前仍按 `misc` 域兜底（历史落盘位置，避免已存值变孤儿）。
- 队列恢复不做"同名去重"：用户可能故意重传；恢复前只跳过本地已不存在的源文件。

## 八、维护提示

- 新增**凭据类别**：`core/credentials.py` 加 `KIND_*` + `CREDENTIAL_KEYS` + `KIND_LABELS`；`core/app_settings.KEY_DOMAIN` 登记键；含密码则加进 `core/secrets.SENSITIVE_KEYS`，并在 `tests/test_credentials.py` 的跨模块一致性用例里补一行。
- 新增**传输操作类型**：`core/transfer_queue.VALID_OPS` + `OP_LABELS`，并在 `sftp_window._restore_pending_queue()` 补恢复分支。
- 任何"传输完成"的判定都必须走 `core/transfer_verify.check_transfer_size`，**不要**只看 `put/get` 有没有抛异常。
- 终端新增 OSC 消费时，沿用"只消费不注入"：不把远端状态回写成控制序列，也不因 OSC 内容改动屏幕网格。
