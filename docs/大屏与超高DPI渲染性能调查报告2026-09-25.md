## 〇、结论摘要（TL;DR）

三台真机的现象是**同一条物理曲线上的三个采样点**，不是三个独立 bug：
每帧渲染成本 ≈ 线性于「物理像素数 = 逻辑窗口 × 系统缩放²（× 应用内 dpi_scale²，若叠加）」，
叠加若干条 qfw 库的「整窗逐帧离屏渲染」路径后，在核显机器上超出 60fps 预算：

| 现象 | 根因 |
| --- | --- |
| A（27 寸）轻微卡、弹出动画帧数低 | 物理像素 369~829 万，「新增」卡片弹窗动画每帧 = 整窗离屏渲染 + opacity effect（实测 effect 放大 1.8~3.6×，且随 scale 增大） |
| A 全屏后明显加重 | 光栅面积 ×2.56（2K@100% 例）+ 可见表格行数 21→36 行，滚动/切换/弹窗全部同比例放大 |
| B（14 寸）正常 | 同是核显，但全屏物理像素 369 万 = A 的 1/2.25 或 1/1.5，均帧成本仍在 16ms 预算内 |
| C（55 寸电视）严重卡 + 未响应 | 829 万物理像素（4K@150% 例）下，弹窗动画单帧实测 ≥48ms（offscreen 快速 CPU 的下界），真机核显 + DWM 合成再放大到数百 ms；持续动画/悬停/滚动事件风暴使主线程消息泵饥饿超过 Windows 5s 判定阈值 → 「未响应」。亚克力导航展开另有 PIL 高斯模糊单次 ~30-160ms 主线程同步阻塞（打包环境实锤走 PIL：两份 .spec 均 excludes scipy） |

**阻塞点定性（调查要求 2）**：场景 C 的「未响应」不是死锁/死等，是**渲染过慢导致的
事件泵饥饿**（每帧数百 ms × 动画期间连续重绘请求排队），叠加两条次要同步阻塞
（亚克力模糊 PIL 全分辨率实现、菜单 DROP_DOWN 每帧 setMask）。详细机理见 §4。

## 三、测量数据

### 3.1 弹窗/页面切换/菜单（perf_popup_dpi，offscreen，均帧单位 ms）

| 场景 | 物理像素 | 整窗 grab | 切换动画均帧 | 菜单动画均帧 | 弹窗动画均帧 | opacity effect 静态（挂/摘） | effect 放大 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1.0 @ 1600x900 | 144 万 | 12.4 | 16.4 | 15.1 | **30.4** | 2.9 / 2.0 | 1.4× |
| 1.0 @ 2560x1440（A 2K 全屏） | 369 万 | 18.7 | 16.3 | 14.9 | **29.0** | 5.5 / 3.0 | 1.8× |
| 1.5 @ 1707x960（B 全屏） | 369 万 | 16.7 | 16.0 | 15.5 | **31.6** | 13.1 / 4.8 | 2.7× |
| 1.5 @ 2560x1440（C 全屏） | 829 万 | 24.5 | 19.7 | 15.0 | **48.4** | 26.9 / 7.4 | **3.6×** |
| 2.0 @ 2560x1440（极端） | 1475 万 | 29.3 | 20.6 | 14.8 | **41.2** | 21.5 / 13.2 | 1.6× |

要点：

- **弹窗动画是最贵的路径且对像素数最敏感**：30→48ms（144 万→829 万像素），
  且 opacity effect 的离屏放大倍数随 scale 增大（1.4×→3.6×）。动画期每帧 =
  「整窗（含全屏遮罩）离屏渲染 + effect 合成」，829 万像素时单帧已超 60fps 预算
  近 3 倍——这还是开发机快 CPU 软光栅的**下界**。
- 整窗 grab（光栅地板）随像素数近线性：12.4→24.5→29.3ms。任何「每帧重绘整窗」
  的动画（切换、弹窗遮罩）都继承这条曲线。
- **菜单弹出动画与窗口尺寸无关**（独立小窗口，均帧恒 ~15ms）——27 寸上「下拉
  展开动画」的卡不是菜单自身光栅慢，而是合成与下方整窗的交互（见 §4.3）。
- 页面切换动画均帧 16→20ms 温和增长，但每帧是「两页整窗」光栅 + 真机 texture
  上传，真机放大倍数高于 offscreen。

## 四、根因分析与机理差异（调查要求 1、3）

### 4.1 四条「逐帧整窗渲染」路径（qfw 1.11.2 源码定位）

| 路径 | 触发 | 每帧成本构成 | 源码位置 |
| --- | --- | --- | --- |
| 「新增」卡片等 6 个弹窗 | show/done | 整窗（含全屏半透明遮罩）QGraphicsOpacityEffect 动画 200/100ms + 卡片常驻 QGraphicsDropShadowEffect(blurRadius=60) | `components/dialog_box/mask_dialog_base.py` L52-75、L37-44 |
| 页面切换 | 面板 switchTo | 新旧两页整窗并行 slide/fade/scale 220~230ms | `components/widgets/stacked_widget.py` L70+、L225 |

### 4.2 场景 C「未响应」的阻塞点定性（调查要求 2）

**结论：渲染过慢导致的事件泵饥饿，不是死等/死锁。** 证据链：

1. offscreen 下界：829 万像素时弹窗动画单帧 ≥48ms（§3.1）。真机在此之上还有
   三项 offscreen 测不到的放大：iGPU（UHD 630 级）纹理上传与合成、DWM 对
   WA_TranslucentBackground 分层窗口的逐帧重组、以及弹窗卡片
   DropShadowEffect(blurRadius=60) 对大位图的高斯滤波（QGraphicsEffect 内部
   逐帧执行，大图上单帧可达数百 ms）。综合单帧 100~500ms 量级是合理推断。
2. 饥饿反馈环：动画期间连续发出重绘请求，而每帧处理时间 > 事件到达间隔 →
   队列持续增长 → Windows 判定「未响应」（主线程 5s 未处理消息）。200ms 动画
   在 500ms/帧下本身就是一次可感知冻结；用户再连点（每次点击又触发新动画/
   抓屏/查询）即形成秒级以上无响应。
3. 次要叠加项：导航展开亚克力 PIL 模糊 4K 级单次 ~160ms 主线程同步
   （i5 笔记本实测可能更高）；菜单 DROP_DOWN 每帧 setMask。
4. 排除项：数据库查询、FTS、网络与屏幕尺寸无关（数据量同）；S2 缓存使
   滚动/切换的文本层不再是主要矛盾（§3.3 lean 12.5ms@553 万可接受）。

### 4.3 三个机理问题的直接回答

**Q1：为什么全屏比默认窗口更卡？**
两条独立放大：① 光栅面积 ×2.56（1600x900→2560x1440@100% 例），所有整窗级
路径等比放大；② 可见表格行数 21→36（固定行高 38px），滚动/悬停重绘的单元
格数同步增加。两者相乘即「关掉平滑滚动后有所改善」的原因——平滑滚动的
连续插值帧把②进一步放大成逐帧重绘风暴。

**Q2：同是核显，为什么 14 寸笔记本（B）远好于 27 寸/55 寸？**
B 全屏物理像素 369 万（2K@150%），A/C 是 369~829 万+。均帧成本近线性于像素
数，B 恰好压在 16.7ms 预算线附近（§3.1 第 3 行），A/C 超出 1.5~3 倍。核显
算力相近时，差距几乎完全由像素数决定——27 寸/55 寸的「大」不是物理尺寸而是
像素数。若 A/C 机器上应用内 dpi_scale 与系统缩放叠加，像素数再乘 2~5 倍。

**Q3：为什么 C 独有「未响应」而 A 只是卡？**
A 的单帧超出预算 2~3 倍 → 掉帧（肉眼卡顿）但消息泵尚能喘息；C 在 A 的基础上
再放大 + 电视 55 寸观看距离普遍配更高系统缩放（150~200%）+ 电视面板常见
30Hz/24Hz 使 DWM 合成节奏恶化 → 单帧进入数百 ms 区间 → 动画期间事件队列
持续积压，最终触碰 Windows 5s「未响应」判定。同一段代码，A 与 C 之间没有
新 bug，只有帧成本跨越了「掉帧 → 饥饿」的阈值。

实施附注（P1-1 关键发现与坑）：

1. **windowOpacity 方案不可行**（调研阶段原设想）：qfw `MaskDialogBase.__init__`
   里 `setWindowFlags(Qt.FramelessWindowHint)` 整组替换 flags 丢失 `Qt.Dialog` 位
   → 弹窗实际是父窗内的**子部件覆盖层**（`isWindow()==False`、`windowHandle()` 为
   None）→ `setWindowOpacity` 是空操作。故卡片级 effect 是唯一可行路径（也正是
   本表 P1-1 原方案）。
2. **Qt `finished` 信号语义**：`QPropertyAnimation.stop()` 中途打断**不触发**
   `finished`（仅自然播完触发，Qt 源码 setState 的 endTime 判定）；测试里用
   `setCurrentTime(duration())` 同步模拟自然播完。生产无影响（事件循环驱动自然
   播完），`_stop_fade` 注记已写明。

### offscreen 口径的局限（结论外推说明）

offscreen 软件光栅只含 CPU 侧成本，真机的 iGPU 纹理上传、DWM 合成、
DropShadowEffect 大位图滤波、setMask(SetWindowRgn) 均未计入——即 **§3.1 全部
数值是下界，真机放大只多不少**。这也是方案以「阈值自动降级」而非「微调时长」
为主线的原因：阈值以下保持原生体验，阈值以上保可用性。

**补充勘误（2026-09-25 实施时核实）**：生产代码全仓的页面切换都走
`FluentWindowBase.switchTo` → `setCurrentWidget(popOut=False)`（单页 250ms 滑入；
二级 Pivot 容器是裸 `QStackedWidget` 无动画），harness 测的 popOut=True（双页
整窗）是理论上界——实际切换成本约为 §3.1 数字的一半。这不改变 P0-3 的结论
（超阈值直切照样消除整段），但「未响应」主源更集中在弹窗动画与亚克力模糊，
即 P0-1/P0-2 优先于页面切换。
