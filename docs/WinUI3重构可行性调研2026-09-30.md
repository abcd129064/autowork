# WinUI 3 重构可行性调研（2026-09-30）

> 状态：**调研快照**（结论有时效性，WinUI 3 生态迭代较快）
> 提问：AutoWork 是否可能用 WinUI 3 重构？技术架构怎么设计？
> 结论一句话：**技术上可行，但这是 5.45 万行 Python 的全量 C# 重写而非重构；本项目最大风险不在框架成熟度，而在表格控件生态与测试体系重建；建议不立即启动，先做 2 周 spike 拿实测数据。**
> 关联动作：[`docs/TODO.md`](TODO.md) 的 C# 迁移观察项；本轮已新建独立项目 `autowork-winui3`（桌面同级目录，不入本仓）。

---

## 一、结论摘要

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 技术上可行吗 | **可行** | Windows App SDK 已到 **2.4 stable**（2026-08-13 发布，Current 通道，支持至 2027-04-29）；unpackaged + self-contained 部署链路成熟；微软有官方 LOB 业务应用指引 |
| 是「重构」还是「重写」 | **重写**。UI 层不存在可增量迁移的桥梁 | Python 侧 WinRT 投影只覆盖 UWP 时代 API，撑不起 WinUI 3 XAML；`main_window` + `windows/` 共约 4.5 万行 UI 代码无一可复用 |
| 现在该做吗 | **不建议立即启动** | 表格控件无第一方实现；621 项 pytest 需重写；WinUI 3 无 offscreen 等价物，UI 测试手段退化 |
| 最大单点风险 | **DataGrid 缺失** | WCT DataGrid 已归档且未移植 WinUI 3；社区接棒者 WinUI.TableView 为个人维护；商用控件厂商大面积撤退（见 §三） |
| 若要迁，优选路线 | **WPF + .NET 10**（降级保真）> WinUI 3（原生体验） | WPF 有第一方 DataGrid 与 `INotifyDataErrorInfo` 校验；.NET 9 起 WPF 自带第一方 Fluent 主题（`ThemeMode` 属性，含亮暗模式与系统强调色） |
| 无条件该做的一步 | **剥离 `core/database/workers` 的 UI 依赖** | 无论将来选 WPF 还是 WinUI 3，这步都直接降本；且现在就能做、可立即回归验证 |

## 二、现状实测（本仓第一手数据，非估算）

### 2.1 代码规模

实测命令与结果（2026-09-30）：

```
find core windows database workers win_api main_window -name "*.py" | wc -l        # 115
find core windows database workers win_api main_window -name "*.py" -exec cat {} + | wc -l   # 54539
```

| 层 | 职责 | 迁移评估 |
| --- | --- | --- |
| `core/` `win_api/` | 设置门面、DPI 策略、updater、DPAPI、frpc 封装 | 逻辑可平移，约 8 成 |
| `database/` | 双后端（SQLite 主 + MySQL 兜底 LWW）、DDL 单一来源 | 逻辑可平移，方言需重写 |
| `workers/` | QThread 后台任务（查询/写入/导出分离） | 需重构为 async/await |
| `windows/` + `main_window/` | 8 大面板、delegate 自绘表格、qfw 控件 | **完全重写，约 4.5 万行** |

### 2.2 测试基线

`tests/` 共 **44 个 `test_*.py`**（基线 632 passed / 0 failed，2026-10-01 口径）。全部为 pytest + offscreen Qt 模式。

关键差异：WinUI 3 **没有 offscreen 等价物**。现有 `QT_QPA_PLATFORM=offscreen` 全量回归链路在 WinUI 3 下不复存在，UI 层只能靠 WinAppDriver（半弃维护）或人工回归。这是隐性的**测试覆盖率断崖**，比行数更值得担心。

### 2.3 已完成的性能资产（迁移将全部作废）

| 资产 | 落点 | 迁移后命运 |
| --- | --- | --- |
| S5 整格缓存（35 例像素等价回归） | `core/lean_table_delegate.py` | 作废（Composition 渲染模型不同） |
| 文本层绘制缓存（实测地板 -84%） | 同上 | 作废 |
| 弹窗/DPI 阈值自动降级 | `core/perf.py` + `tools/perf/perf_popup_dpi.py` | 部分作废（DPI 感知原生更好，但降级策略需重设计） |
| `ops_link_delegate` 自绘链接列 | `core/ops_link_delegate.py` | 需换范式（见 §四） |
| 100k 行查询 338.9ms → 0.14ms | `database/` SQL/FTS | **保留**（数据层成果与 UI 框架无关） |

结论：数据层优化全部保留，渲染层优化全部归零。净损失约等于 S1~S5 五个阶段的工程投入。

## 三、生态现状核实（2026-09/10 联网查证）

### 3.1 Windows App SDK 版本与支持期

来源：[Windows App SDK release channels](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/stable-channel)

| 版本 | 原发布 | 最新补丁 | 支持状态 | 生命周期结束 |
| --- | --- | --- | --- | --- |
| **2.4.0** | 2026-08-13 | — | **Current** | 2027-04-29 |
| 1.8 | 2025-09-09 | 1.8.260710003 | Maintenance | 2026-09-09（已到期） |
| 1.7 | 2025-03-18 | — | Out of Support | 2026-03-18 |
| 1.6 / 1.5 / 1.4 | 2024~2023 | — | Out of Support | 已到期 |

要点：
- 2.x 稳定版节奏为**每半年一次大版本**（2.0 于 2026-04-29 发布，2.4 于 2026-08-13 发布），迭代快于 WPF，但也意味着**升级要跟版本滚动**。
- 2.0 引入**破坏性变更**：`CoreWindow` 不再支持、部分游戏/IoT/Xbox 场景不支持。迁移必须直接上 2.x，不能从 1.x 渐进。
- 官方明确：WinUI 应用的**启动速度、内存占用、安装体积仍大于 UWP**，正在改善中。

### 3.2 DataGrid：最大的坑

来源：[what-is-supported](https://learn.microsoft.com/en-gb/windows/apps/windows-app-sdk/migrate-to-windows-app-sdk/what-is-supported)、[WCT DataGrid 归档公告](https://learn.microsoft.com/zh-tw/dotnet/communitytoolkit/archive/windows/datagrid)

| 选项 | 状态 |
| --- | --- |
| 第一方 DataGrid | **不存在**。微软文档原文：No first-party WinUI 3 control |
| WCT DataGrid | **已归档**。WCT 7.1 仅支持 UWP/Uno，未移植 WinUI 3；官方建议新项目用 DataTable 或 WinUI.TableView |
| WCT 8.0 DataTable | 只读，非可编辑表格 |
| WinUI.TableView | 社区个人维护，功能较全（排序/筛选/分组/编辑/CSV），被微软迁移文档列为推荐替代 |
| 商业控件 | **大面积撤退**：Developer Express 已撤市；Actipro 取消移植；Infragistics 仅 preview |

对本项目的具体影响：现有表格重度依赖**排序键语义**（`_SortKeyItem` 为组合列保留原始字段值，避免 Qt `sortItems` 按显示文本比较导致跨年错序）、**操作列链接清单**（`_OPS_LINKS_UNRESOLVED` / `_OPS_LINKS_RESOLVED` 按行取）、**行状态并入绘制键**、**分页 60 行**。这些在 WinUI.TableView 上都要重新设计，不是换个控件名了事。

### 3.3 其他已确认的坑

| 项 | 影响本项目 |
| --- | --- |
| 无 `INotifyDataErrorInfo` 自动校验 | 表单校验需自建，与现有 qfw 表单体验有差距 |
| 无可视化设计器 | 纯 XAML 手写，UI 迭代成本上升 |
| 已知控件缺口 | `CaptureElement` 无替代（截图相关）、`InkCanvas` 仅实验通道、`PrintManager` 仅 Win11 |
| WebView | 用 WebView2（需 WebView2 Runtime，Win10/11 多数已预装） |

### 3.4 部署形态对自动更新链路的影响

来源：[Distribute an unpackaged WinUI 3 app](https://learn.microsoft.com/zh-tw/windows/apps/package-and-deploy/unpackage-winui-app)

本项目现有 updater 是「整包 zip + 外部 bat/vbs 三向原子换位」（见 [`auto_update_research.md`](auto_update_research.md)）。三条路线取舍：

| 部署形态 | 单文件 EXE | 自动更新 | 包标识 | 适配现有 updater |
| --- | --- | --- | --- | --- |
| **unpackaged + self-contained** | 不支持 | 无 App Installer 更新，需自带 runtime | 无 | ✅ **最贴合**，保留现有 zip 换位 |
| packaged with external location | — | 有 | 有 | ⚠️ 需改更新流程 |
| MSIX | — | 有（App Installer） | 有 | ❌ 需重写，且签名分发链变化 |

`WindowsPackageType=None` + `WindowsAppSDKSelfContained=true` 是保留现有 updater 的最短路径，代价是输出体积（含完整 runtime 约 200MB 量级）。注意：**unpackaged 不支持 `PublishSingleFile`**，WinUI 原生运行时必须以独立文件存在。

## 四、逐层技术映射与难度

| 现状（Python / PySide6） | 目标（C# / WinUI 3） | 难度 | 备注 |
| --- | --- | --- | --- |
| `main.py` / `autowork_with_table.py` | `App.xaml` + Bootstrapper | ✅ 低 | WASDK 2.4 入口；unpackaged 需 `WindowsPackageType=None` |
| `main_window/` FluentWindow + Pivot 五视图 | `MainWindow` + `NavigationView` | ✅ 低 | 原生 Fluent，Mica 一行启用；可**删掉** `core/perf.py` 的 mica 双通路补丁 |
| qfw `InfoBar` / `CalendarPicker` / `SegmentedWidget` | 原生 `InfoBar` / `CalendarView` / `Pivot`(或 `SelectorBar`) | ✅ 低 | 设计语言同源，迁移最顺的一层 |
| `windows/<module>/` 8 大面板 | View (XAML) + ViewModel (CommunityToolkit.Mvvm) | ⚠️ 中 | `x:Bind` 编译期绑定；MVVM 纪律需新建（现有代码是 code-behind 混合态） |
| `LeanTableDelegate` / S5 缓存 / `ops_link_delegate` | ListView+DataTemplate 自绘 **或** WinUI.TableView | 🔴 **高** | 无第一方 DataGrid；组合列排序键语义需重新设计 |
| cv2 视频（`single_shot_video.py` 等 6 处） | `MediaPlayerElement` 或 `SoftwareBitmap` + `SwapChainPanel` | 🔴 高 | OpenCV 帧管线需重搭；`SwapChainPanel` 是低延迟 GPU 呈现路径 |
| `workers/` QThread + `_query_seq` 代数守卫 | `async/await` + `Task` + `DispatcherQueue` | ⚠️ 中 | **必须保留代数守卫语义**（防止过期查询覆盖新结果），这是已踩过的坑 |
| `database/schema.py` 双后端 DDL 单一来源 | `Microsoft.Data.Sqlite` + `MySqlConnector` | ✅ 低 | 纯逻辑平移；保留「SQLite 自动迁移 / MySQL 人工 ALTER」既有红线 |
| DPAPI（`core/secrets.py`） | `ProtectedData`（`System.Security.Cryptography`） | ✅ 低 | 直接对应 |
| QProcess 管 frpc（terminate→kill 两段式） | `System.Diagnostics.Process` | ✅ 低 | 注意 `QProcess` 无 `quit()` 的坑在 .NET 不存在 |
| 整包 zip + bat/vbs updater | unpackaged + self-contained | ✅ 低 | 见 §3.4 |
| 621 项 pytest + offscreen | xUnit + 无 offscreen UI 测试 | 🔴 高 | **覆盖率断崖**，见 §2.2 |
| DPAPI 凭据 + 上传（49.235.34.253） | `HttpClient` + `ProtectedData` | ✅ 低 | urllib 的 `ProxyHandler({})` 坑在 `HttpClientHandler.UseProxy=false` |

### 架构骨架（目标态）

```
AutoWork.Core            (net10.0，无 UI 依赖，可独立单测)
├── Models/              AftersaleRecord、LedgerRecord …
├── Data/                SqliteAftersaleRepository、MySql…、SchemaCatalog(单一来源)
├── Services/            AppSettings、AftersaleRankQuery、UpdaterClient
└── Abstractions/        IRepository<T>、IQueryDispatcher（对应 _query_seq 守卫）
        ▲
        │ 依赖倒置；两个 UI 宿主（WinUI 3 / WPF / Avalonia）均可复用
────────┼────────────────────────────────────────────
AutoWork.App             (net10.0-windows10.0.19041.0，WinUI 3)
├── Views/               MainWindow( NavigationView ) + 各 Page(XAML)
├── ViewModels/          每页一个 VM，x:Bind 编译期校验
└── Contracts/           ViewModel ↔ Core 的 DTO 映射
```

**关键设计约束**：`AutoWork.Core` 不得引用任何 `Microsoft.UI.Xaml` 命名空间。这是保证「同一份数据层将来能换 UI 框架」的唯一手段，也是 xUnit 测试不需要 WinUI 运行时（因而可以在本机无 SDK 环境下先跑通逻辑层）的前提。

## 五、路线对比

| 维度 | 维持 PySide6 | WPF + .NET 10 | **WinUI 3** | Avalonia |
| --- | --- | --- | --- | --- |
| 迁移工作量 | 0 | 全量重写 | 全量重写 | 全量重写 |
| UI 还原度 | 基线 | 高（DataGrid 齐全） | 高（原生 Fluent） | 中（无原生 Mica） |

| 启动/内存 | 差（raster + 5.4 万行 Python 解释器） | 好 | 官方承认仍逊于 UWP，但优于现状 | 好 |

## 七、分阶段路径（若决定启动）

### 阶段 0：解耦（无悔投入，强烈建议先做）

剥离 `core/` `database/` `workers/` 对 UI 的隐式依赖：worker 结果通过回调/`Future` 返回，而非直接操作 widget；配置读写不触碰 QObject。此步**与框架选型无关**，无论将来 WPF / WinUI 3 / 继续 PySide6 都有收益，且可用现有 632 项测试立即验证回归。

### 阶段 1：2 周 spike（决策闸门）

| 项 | 内容 |
| --- | --- |
| 目标 | 用 **WinUI.TableView** 复刻「售后记录页」，验证三件事：① 组合列排序键能否表达；② 操作列链接清单能否承载；③ 分页 60 行 + 千行滚动帧率 |
| 交付 | 可运行 demo + 一页实测数字（构建/启动耗时、滚动 FPS、内存） |
| 判据 | ①或②做不到 → **立即转 WPF**，不再投 WinUI 3 |

同时并行做一个**环境 spike**：本机当前只有 .NET 8 运行时、无 SDK，需先装 .NET 10 SDK + Windows App SDK 2.4 验证构建链通畅（这是当前最硬的阻塞，见 §八）。

### 阶段 2：数据层先行

`AutoWork.Core` + xUnit 全绿，把 `schema.py` 单一来源与 LWW 逻辑平移。这一步**与 UI 无关**，可在无 SDK 环境下先用 SQLite 跑通逻辑单测。

### 阶段 3：壳 + 低风险页先行

`NavigationView` 壳 + 设置页 + 球桌管理页（表格相对简单），跑通 unpackaged 部署与现有 updater 兼容。

### 阶段 4：重表格页 + 视频

售后记录页、远程页（9 列联动）、跑视频页、cv2 视频链路。

### 阶段 5：并行运行与切换

两套 UI 共用同一 DB 目录（**只读期 / 单写期**需明确约定），真机回归 → 生产灰度 → 停 PySide6 分发。

## 八、当前环境阻塞（2026-09-30 实测）

在本仓准备阶段实测本机工具链：

```
dotnet --list-sdks     → （空）
dotnet --list-runtimes → Microsoft.NETCore.App 8.0.22
                         Microsoft.WindowsDesktop.App 8.0.22
```

**本机只有 .NET 8 运行时，没有 SDK**（`dotnet` 主机存在但无 SDK，`dotnet --version` 报 "The application '--version' does not exist"）。因此：

- 无法 `dotnet build` / `dotnet restore` / `dotnet new`；
- WinUI 3 项目文件已按 **.NET 10 + Windows App SDK 2.4.0** 写好（2.4 需 .NET 10 通道；1.8 已于 2026-09-09 结束支持，不可选）；
- 后续需安装：**.NET 10 SDK** + （unpackaged 自包含则**无需**另装 Windows App Runtime）。
