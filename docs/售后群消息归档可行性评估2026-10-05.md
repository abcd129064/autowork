# 售后群消息自动归档可行性评估（微信 / 企业微信）

> 日期：2026-10-05（当日二更：群现状已确认，见下方「现状更新」） ｜ 性质：需求可行性评估（只调研，未改任何业务代码）
> 需求原文：接入微信和企业微信，自动获取各售后群的消息记录，按群聊/时间/问题类型
> 等维度自动归档整理，生成结构化的售后报告。
> 信息来源：企业微信官方开发者文档（2026-09-10 更新口径）+ 微信机器人生态公开实测数据，
> 关键结论均附来源；未做任何侵入式尝试。

> **【现状更新 2026-10-05】** 用户确认：售后群 **80% 已迁企微**，且群结构为
> **群主 = 用户本人（企业微信成员）+ 其余成员均为个人微信用户**（即企微「客户群」，
> edition≥2 即可覆盖）。结论：**最大组织门槛已清除**，剩余 20% 未迁移的群走 §2.3
> 兜底；且因群内每条消息用户均为接收者，**只需将用户这 1 个账号纳入存档授权范围**
> 即可覆盖其所在全部群的全量消息（席位费=1 个账号，成本最低，详见 §2.1 末段）。

## 一、结论速览（先结论后展开）

| 子问题 | 结论 | 一句话依据 |
| --- | --- | --- |
| 企业微信能合规拿到群消息吗 | **能，且是唯一官方合规通路** | 官方「会话内容存档」（数据与智能专区）提供 SDK 拉取全量会话，支持含个人微信客户的客户群 |
| 个人微信能拿到群消息吗 | **不能（作为正式功能）** | 无任何官方 API；Hook/协议/UI 自动化全部违反《微信软件许可及服务协议》7.1.2，封号实测极高（见 §三） |
| 最大前提条件 | ~~售后群必须迁到企微侧~~ **已清除（80% 已迁移，群=客户群结构）**；剩余动作=管理后台开通存档 | 客户无需安装企微——个人微信用户可被拉进企微「客户群」；会话存档覆盖外部会话（edition≥2） |
| 最硬的技术约束 | **会话记录只能拉最近 5 天** | 必须部署常驻拉取服务持续增量拉取，不能事后补拉（官方接口文档明确） |
| 主要合规动作 | **员工+客户知情告知 + 存档范围最小化** | 企微开启存档后强制向双方展示存档提示（不可关闭）；须符合《个人信息保护法》 |
| 推荐方案 | **A：企微会话存档做主干 + C：人工导出做兜底**；个人微信自动化路线**否决** | 见 §六方案对比 |

**总体判定（2026-10-05 更新）：需求可行，组织门槛已清除——剩余前置只剩
「管理后台开通会话存档 + 设公钥 + 授权范围含用户本人 + edition≥2」这一组管理员动作
（§三 checklist 1~6），完成后即可启动 S0 spike（§七）。**
原判定（迁移门槛未确认时的措辞）存档：可行性押在群迁移组织动作上；现已确认 80% 完成，
未迁移的 20% 群走 §2.3 半自动兜底，不影响主干。

## 二、开放能力盘点

### 2.1 企业微信：官方「会话内容存档」（推荐主通路）

官方文档：`developer.work.weixin.qq.com/document/path/101365`（获取会话记录）、
`/document/52569`（获取会话存档授权成员列表，最后更新 2026-09-10）。

关键能力与限制（均出自官方文档原文）：

| 项 | 事实 |
| --- | --- |
| 接口形态 | 自建应用具备「**数据与智能专区权限**」后，通过专区 SDK 调用 `sync_msg` 拉取；公钥必须先在管理后台设置（自建应用：管理后台 → 安全与管理 → 管理工具 → 数据与智能专区 → 会话内容），**未设公钥则不存档** |
| 时间窗口 | **只可获取 5 天内的会话记录** → 拉取服务必须常驻增量消费，cursor 分页持久化 |
| 吞吐 | 单次上限 1000 条，三种拉取模式（默认 / 预分页 / 自适应），cursor 链式 |
| 频控 | 请求建议带回调事件下发的 `token`（10 分钟有效），否则接口有严格频率限制 → 需配合「产生会话回调通知」消费 |
| 授权范围 | 消息发送者或接收者必须在会话内容授权范围内；`get_auth_user_list` 的 `edition_list` 明确版本：1=内部会话、**2=内外部会话**、3=内外部+语音通话——外部客户群须开到 2 |
| 身份转译 | 会话内容导出接口可把 userid/chatid 批量转译为真实姓名/群名（报告展示需要） |
| 强制提示 | 开启存档后，企微会**强制向员工和客户展示存档提示，不能关闭**——这既是合规保护也是业务沟通成本 |

对"客户在个人微信"这一现实的关键解法：**企业微信成员可把个人微信好友拉进企微「客户群」，
客户用个人微信即可入群聊天**。会话存档开到 edition≥2 即覆盖此类群的全部消息。
即：**迁移成本主要在"建群挪群"这个动作，不在客户侧装软件**。

**单账号覆盖简化（2026-10-05 现状确认后新增）**：授权范围的判定是
"消息发送者**或接收者**在授权范围内"。用户当前群结构 = 用户（企微成员）为群主 +
其余成员为个人微信用户：群聊中**每条消息用户都是接收者**（含用户自己发的——发送者即本人）。
因此**只需把用户这 1 个企微账号加入会话存档授权范围**，即可拉取其所在全部客户群的
100% 消息：席位费 1 个账号、无需为任何他人开通、隐私暴露面最小化（R3 同步缓解）。
唯一不覆盖的场景 = 用户新拉了不含自己的群（组织上不会发生：群主必须在群内）。

补充通路（只作触发器，不适合归档）：企微群机器人 Webhook 只能**发**不能收；
自建应用回调只能收到 @应用或应用会话内的消息。二者可作为"报告完成→群里发通知"的出口，
不能作为全量消息入口。

### 2.2 个人微信：无官方通路，第三方全部违规（否决）

2025-04 WeChatFerry（WCF）作者本人发布的封号统计（腾讯云社区可查）：

- 被调查用户中 **Hook 框架用户几乎无一幸免**（原话："hook 封的全都是 WCF"）；
  有人累计被封 20 次；甚至半年未使用仍被追封。
- 协议模拟（itchat/Web 协议已死；GeweChat/iPad 协议中等风险、需同省 IP、消息≤5条/分钟）
  与 UI 自动化（wxauto，相对不易封但本质是模拟人手操作，脆弱且拿不到结构化数据）。
- 法律层面：Hook/逆向属于《微信软件许可及服务协议》7.1.2 明确禁止的
  "第三方工具、插件、外挂干扰平台正常运行"；大规模自动化场景极易触发风控。

**对 AutoWork 的特别含义**：个人微信侧方案对个人玩家尚属"自担风险"，但对一个
分发给客户的商业桌面产品，等于把封号风险与业务中断责任转嫁给所有用户，
且"自动获取他人会话内容"叠加 PIPL 后是产品级合规事故。**不可作为正式功能，评估即否决。**

### 2.3 半自动兜底（合规但"自动"打折）

群确实无法迁移时，唯一合规的数据来源是**用户主动导出**：

- C1 业务流程：规定售后问题在企微客户群同步流转（双群并行过渡）；
- C2 文件导入：微信 PC 端聊天记录手工导出/复制存 txt，AutoWork 提供本地解析导入工具
  （本地文件、零侵入、零封号风险，但含客户个人信息，仍需告知义务）；
- C3 截图 OCR：成本高、准确率不稳，仅作补充，不推荐主路径。

## 三、前提条件清单（开工前必须逐项确认）

### 组织/资质前提（决定可行性的硬门槛）

1. **有企业微信主体**（营业执照可注册）+ 超级管理员操作权限。
2. **管理员后台开通会话存档**：如实填写使用场景与行业资质、等待官方审核
   （金融/保险/政务类默认更顺；一般行业如实写"售后服务质量管控"即可）。
3. **设置 RSA 公钥 + 自建应用具备「数据与智能专区权限」**（见 §2.1 入口）。
4. **被存档员工在授权范围内、edition 开到 ≥2**（覆盖含个人微信客户的群）。
5. **售后群完成向企微客户群的迁移**（旧群可保留只读期，新问题引流到新群）。
6. **员工与客户知情**：开启后企微有强制存档提示（不可关），建议再内部公示存档范围。

### 技术/部署前提

7. **常驻拉取服务**：5 天窗口 → 增量拉取 worker 必须常驻且有心跳监控。
   推荐部署在 49.235.34.253（已有 aftersale-web.service 常驻先例与 MySQL），
   而非用户桌面端（桌面端关机=断档，超 5 天即永久丢失）。
8. **RSA 私钥保管**：服务端安全存储；桌面端侧可复用 `core/secrets.py` 的 DPAPI 机制。
9. **会话存档为付费能力**：按开通存档的员工数计费，开通时以企微后台报价为准
   （只存售后客服号，费用可控；此处不写具体数字以免过期失真）。
10. **断档检测**：cursor 落库时间距今 > 4 天即告警（给 1 天补救余量）。

## 四、合规与隐私风险登记

| # | 风险 | 等级 | 缓解 |
| --- | --- | --- | --- |
| R1 | 个人微信自动化路线：违反平台协议 + 封号业务中断 + （抓取他人通信内容）叠加 PIPL/数据安全风险 | **致命** | 直接否决该路线（§2.2） |
| R2 | 未履行告知义务即存档员工/客户会话 | 高 | 企微强制提示为兜底；内部制度书面留痕 |
| R3 | 全量无差别存档扩大隐私暴露面 | 中 | 只授权售后客服号；只存档目标客户群；按 §三-6 范围最小化 |
| R4 | 归档库含客户 PII（姓名/手机号/设备照片语音） | 中 | 介质文件 P0 不拉取（只存文本+计数）；库表权限对齐 aftersale_ro 只读惯例；导出报告脱敏 |
| R5 | 报告金额引用（减损规则 20~50 元档）涉及对客户计费 | 中 | 报告仅作内部质量分析，与对客沟通口径分离 |
| R6 | 存档数据留存周期无界 | 低 | 明确保留期（建议 1 年）+ 定期清理，写入设置项 |

## 五、功能设计思路（分层架构）

```
[采集] 企微会话存档 worker（Python + 会话存档 SDK，Linux 常驻 @49.235.34.253）
        心跳拉取 sync_msg（建议 ≤1h 一次）→ RSA 解密 → 结构化消息
        │  断档检测：cursor 时间距今 >4 天告警（5 天窗口，1 天余量）
        ▼
[存储] MySQL（复用现有 autowork 库），新表经 database/schema.py 单一来源 DDL 治理：
        chat_archive_messages(msg_id PK, room_id, room_name, sender_id, sender_name,
                               msg_type, content, media_count, msg_ts, pull_batch)
        chat_archive_tags(msg_id, category, matched_rule, confidence, tagged_by)
        chat_archive_cursor(scope, next_cursor, last_success_ts)   ← 断档自愈依据
        ▼
[打标] 规则引擎：关键词 → 问题类型，直接映射既有售后类型体系
        （安装配置缺失 / 更新错误 / 新球助手配置错误 / 其他——与减损规则档位对齐）
        可选 LLM 兜底分类规则未命中的消息（confidence 区分，低置信只入"待人工"）
        ▼
[报告] 聚合查询：群聊 × 时间段 × 问题类型 三维透视
        复用 windows/aftersale/rank.py 的排行口径（room/table 联合分组），
        产出：日/周报 = 各群问题量、TOP 问题类型、待处理清单、金额风险预估
        可选联动：一键生成 aftersale_records 录入草稿 → 人工确认入库
        （保持"AI 只产草稿，人拍板"的既有协作原则）
        ▼
[展示] AutoWork 新面板子页（Pivot，双宿主注册：主面板 + 弹出窗口）
        通知出口：企微群机器人 Webhook 把"周报已生成"推回群里
```

设计要点：

- **复用率极高**：双后端（`database/backend.py`）、DDL 单一来源（`database/schema.py`）、
  密钥（`core/secrets.py`）、排行统计口径、ops_link 表格范式、面板 Pivot 规范全部现成。
- **新增工作量集中在两处**：① 会话存档 SDK 接入（C SDK + Python binding，
  服务端 Linux 部署比 Windows 桌面侧省事）；② 打标规则与报告查询。
- **桌面端只做展示**：拉取放服务端，规避"用户关机导致归档断档"这一致命场景。
- **P0 只做文本**：图片/语音/文件仅存计数（media 接口留 P2），报告足够。

## 六、方案对比与推荐

| 路线 | 合规 | 稳定性 | 覆盖现实售后群 | 封号风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A. 企微会话存档（群迁企微客户群） | ✅ 官方 | 高（官方 API） | 需迁移动作，客户免装软件 | 无 | **推荐主干** |
| B. 个人微信 Hook/协议/UI 自动化 | ❌ 违反协议 | 低（版本绑定/风控） | 原样覆盖 | **极高**（实测几乎必封） | **否决** |
| C. 人工导出 + 本地解析导入 | ✅ | 高（人驱动） | 原样覆盖 | 无 | **兜底**（自动化打折） |
| D. 企微机器人/应用回调 | ✅ | 高 | 仅触发场景，收不到全量消息 | 无 | 只作通知出口 |

**推荐 = A 主干 + C 兜底 + D 通知出口**：

- 若能完成"售后群 → 企微客户群"迁移：全功能自动化归档 + 自动报告，长期正路；
- 若群迁移受阻：C 兜底（导出导入工具）保住"归档+报告"价值，放弃"自动获取"；
- B 路线无论商业还是技术角度都无讨论价值，2025-04 实测数据（Hook 用户几乎无一幸免，
  含半年未用仍被追封）说明其连"个人自担风险"都站不住。

## 八、决策点台账（2026-10-05 更新）

| # | 决策点 | 状态 |
| --- | --- | --- |
| 1 | 售后群现状：个人微信群还是企微群？ | ✅ **已确认**：80% 已迁企微；群结构 = 群主（用户，企微）+ 其余均为个人微信用户 = 企微客户群 → 走 A 主干，未迁移的 20% 走 C 兜底 |
| 2 | 企微主体与管理权限 | 待确认（用户为群主且已用企微建客户群，大概率具备；需确认是**超级管理员**还是普通管理员——开通存档与设公钥须超管） |
| 3 | 存档员工范围 | **已有默认推荐**：只授权用户本人 1 个账号（§2.1 单账号覆盖简化），待用户确认 |
| 4 | 报告节奏（日报/周报，是否推回群） | 待拍板（S2 实现前确认即可，不阻塞 S0/S1） |
| 5 | 预算（席位费） | 待确认；按 §2.1 简化后 = 1 个账号的席位费，开通时以后台报价为准 |

### 下一步：管理员侧操作清单（只有用户本人能做，S0 的前置）

1. 用**超级管理员**账号登录企微管理后台；
2. 管理后台 → 安全与管理 → 管理工具 → **数据与智能专区 → 会话内容**：
   申请开通（如实填写使用场景：售后服务质量管控），等待官方审核（1~3 天）；
3. 审核通过后，同一入口**设置 RSA 公钥**（工具侧先随机生成密钥对，公钥填后台、
   私钥留服务端，生成方法见 S0 spike 准备）；
4. 把**用户本人账号**加入会话存档授权范围，并确认 **edition≥2（内外部会话）**；
   开通后用 `get_auth_user_list` 复核 `edition_list`；
5. 确认席位费报价并按需充值（1 个账号）；
6. 完成后通知工具侧启动 S0 spike（测试群拉取 → 解密 → 落库最小闭环）。
