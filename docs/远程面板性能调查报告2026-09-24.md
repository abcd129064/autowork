## 1. 背景

远程面板承载 P2P 内网穿透（frp xtcp visitor）的全部用户入口：会话总览 /
P2P 访客 / 连接质量 / frps 代理四张表，以及 SSH / SFTP / RDP 三类会话面板。
用户反馈集中在三类现象：**点击按钮后长时间无响应**、**首次打开会话慢**、
**搜索/刷新时界面顿挫**。本报告按「表格滚动 → 按钮反馈 → 连接速度」三个
性能面做代码走读 + 离线实测，给出量化结论与分级优化建议。

方法参照：`docs/售后面板性能调查报告2026-09-06.md`（报告结构）、
`docs/perf_scroll_investigation.md` 与 `tools/perf/scroll_profile.py`
（配对基线 + 同步重绘测量范式）。

## 4. 量化数据

### 4.1 表格滚动（perf_remote_scroll.py，60 行 / 9 列 / 每行 5 按钮 cellWidget）

| --- | --- | --- | --- |

关键发现（**Windows 25H2 本机 TCP 行为**）：

- 对**从未监听**的回环端口 `connect_ex` 不返回 RST 而是**静默丢弃 SYN**，
  `p2p.is_port_in_use`（`settimeout(1)`）每次走满 1s 超时 → 实测 1005.9ms/次
- 连带效应：`wait_ports_ready` 标称 200ms 轮询周期的**有效周期 ≈ 1.2s**
  （200ms QTimer + 每轮探测 1s），8s deadline 的实际到达时间为 8.26s；
  `ensure_visitor` 的端口探测在端口未就绪时也固定 +1s
- 上述探测全部发生在 GUI 线程（open_session 主调用链上）

### 4.4 超时上限常量表（理论最坏，均在 GUI 线程）

| 链路点 | 常量 | 最坏值 |
| --- | --- | --- |
| frps 预检 refresh | `_DEFAULT_TIMEOUT_SEC = 2.5` × happy path ≈10 GET | **≈25s**（不可达时熔断后仅 1 次） |
| apply 热重载 `_reload_with_retry` | 3s × 3 次 + 2×0.5s sleep | **≈10s** |
| `_stop_frpc` POST /api/stop + quit 兜底 | 3s + 2.5s | ≈5.5s |
| `wait_ports_ready` | 200ms 间隔 / 8s deadline（有效周期 1.2s） | 8.26s 实测 |
| 预热打洞 | `_PREWARM_TIMEOUT_MS = 3000` | 3s |
| admin API 单次 | `_ADMIN_API_TIMEOUT_SEC = 3` | 3s |
| SSH 面板关闭 `shutdown()` | join(2.0) + forensic wait(2.0) | ≈4s |

open_session 单次点击的 GUI 冻结最坏叠加：预检 25s + ensure 热重载 10s +
wait_ports 8.3s ≈ **43s**（真实网络罕见；常见值为 0.5~2s）。

### 4.5 周期性后台任务对主线程的影响

| 任务 | 周期 | 执行线程 | 实测影响 |
| --- | --- | --- | --- |
| frps 感知（request_refresh） | 30s | **后台线程** | 仅 `proxies_changed` 信号回 GUI 触发 refresh（≈35~210ms，见 §4.2-A） |
| 连接质量探测轮（prober） | 30s | **后台线程** | `changed` → refresh（Visitor/Quality 轻量；Session 全量重建受影响） |
| SFTP 健康检查 | 5s | **后台线程** | 无 |
| frpc 健康（`_on_frpc_health`） | 按钮触发 | **GUI 线程** ❌ | `ping_admin` ×2 同步 HTTP，最坏 2×3s |

结论：**周期任务本身全在后台线程，设计正确**；其对主线程的唯二冲击是
（a）信号回调触发的全量 refresh，（b）`_on_frpc_health` 按钮的同步 HTTP。

## 5. 根因分析

1. **网络调用一律同步跑在 GUI 线程**（历史设计：manager 方法为可直调的同步
   函数，按钮处理器直接 await 不了就硬等）。四处热点：open_session 预检、
   apply 热重载、_stop_frpc、_on_frpc_health。这是「点击没反应」现象的全部来源。
2. **表格刷新采用全量重建 + cellWidget 按钮**。≈5ms/行的控件创建成本使
   SessionWork 50 行 refresh 达 274ms；叠加 5 个信号源直连 `self.refresh`
   （`visitors_changed` / `frpc_state_changed` / `proxies_changed` /
   `channel_state_changed` / `prober.changed`）且无合并门控，事件密集时连续重建。
3. **`is_port_in_use` 的 1s 超时假设与本机 TCP 行为不匹配**（Windows 25H2 对
   回环未监听端口静默丢 SYN），把 200ms 轮询退化成 1.2s，且探测在 GUI 线程。
4. **滚动帧耗时的主要构成是 fluent 委托/样式（≈2.5×）与 cellWidget**，但两者
   都在 16ms 预算内——**滚动不是用户可感知的痛点，重建才是**。
5. SFTP 面板构造 56ms 属于一次性小开销（离线扫描 + 控件树），优先级低。

## 6. 优化建议（P0 / P1 / P2）

### P0 — 消除 GUI 线程同步网络调用（用户可感知冻结的全部来源）

| # | 建议 | 落点 | 预期收益 |
| --- | --- | --- | --- |
| P0-1 | open_session 预检移后台线程（worker + 回执，复用 `request_refresh`/`refresh_finished` 既有机制），先弹 InfoBar「正在检查 frps…」 | `core/frp_remote.py` `open_session` | 最坏 25s 冻结 → 0；点击到受理反馈 <5ms |
| P0-2 | `apply`/`_reload_with_retry`/`_stop_frpc` 移后台；断开/删除按钮立即改按钮态 + InfoBar，完成后回执刷新 | `core/frp_remote.py`、`windows/remote_session/window.py` | 最坏 ~10s（热重载）+5.5s（全停）冻结 → 0；实测 1:1 透传完全消除 |
| P0-3 | `_on_frpc_health` 移后台线程 | `windows/remote_session/remote_hub.py` | 最坏 2×3s 冻结 → 0 |
| P0-4 | `is_port_in_use` 超时降至 ~150-200ms（非阻塞 connect + select），或探测整体挪后台 | `p2p.py` | wait_ports_ready 有效周期 1.2s→~0.2s；ensure 未就绪路径 -0.8s；8s deadline 实际到达 8.26s→标称值 |

### P1 — 刷新与重建成本

| # | 建议 | 落点 | 预期收益 |
| --- | --- | --- | --- |
| P1-1 | SessionWork.refresh 合并门控（dirty 标志 + `QTimer.singleShot(0, …)` 合帧），多事件同帧只重建一次 | `windows/remote_session/remote_hub.py` | 事件密集时 5×274ms → 1×274ms（@50 行） |
| P1-2 | 代理页搜索 `textChanged` 加 300ms 防抖 | 同上 | 连续输入 8 字符 8×210ms → 1×210ms |
| P1-3 | `SSHTerminalPanel.shutdown()` 的 join(2.0)+wait(2000) 移后台或分段等待 | `windows/remote_session/ssh_terminal.py` | 关标签最坏 ~4s 冻结 → 0 |
| P1-4 | 会话总览操作列轻量化：以委托绘制（参考 `core/lean_table_delegate.py` 既有实现）替代 5 按钮 cellWidget，先在数据量大时启用 | `remote_hub.py` | 重建 308ms→~1ms 量级（§4.1 实测 280×）；滚动 -18%~-19%；P95 长尾显著收窄 |

## 8. 已确认做对的部分

- **周期后台任务全部在后台线程**（frps 感知 / 连接质量探测 / SFTP 健康），主线程零常态占用
- `_on_probe_now` 的「InfoBar 立即 + refresh_finished 回执」模式是本项目
  异步反馈的正确范式，P0 各项建议即推广该模式
- `wait_ports_ready` 首轮 `_poll` 同步执行，端口已就绪时**就绪即回（实测 0.2ms）**——
  P2-4（首轮同步探测）优化有效
- frps 不可达熔断（3 次 / 60s）避免每次点击都打满 2.5s 超时
- SessionWork 已 `setWordWrap(False)`、SmoothMode 由 `apply_table_smooth_mode`
  统一管理（NO_SMOOTH 下测量，排除了平滑滚动干扰）
- Visitor/Quality 两视图为纯 item 轻量实现（<1.1ms@50 行），无需改动
