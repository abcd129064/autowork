## 一、结论摘要

1. **本仓库没有 .ui，也不适合引入 .ui。** 全仓 0 个 `.ui`；唯一的「生成物」 `autowork_with_table.py`（918 行）已被人肉改造，生成链断裂。技术栈 qfluentwidgets + PySide6 不支持 Designer 预览，且约七成界面是运行时生成（列定义驱动、卡片循环、delegate 运行时安装、自绘 FlowLayout），迁 .ui 收益为负。
2. **用户直觉指向的真问题成立**：不是「缺 .ui」，而是**上帝类**——`records.py` 1465 行、`RecordsPage` 约 1350 行、69 个方法、`tests/` 中命中 `RecordsPage` 的用例为 **0**。
3. 已完成 `records/` 四层拆分：`query_state.py`（66 行，无 Qt）/ `table_adapter.py`（143 行，记录→单元格） / `controller.py`（219 行，唯一持有 QThread） / `page.py`（1325 行，视图 + 意图翻译）。
4. **页面代码 0 个 QThread、0 个 `*_worker` 属性**；行为映射逐条保持，24 处 worker 启动点全部改为 controller 信号。
5. P0 测试 `tests/test_aftersale_records_page.py` **8/8 绿**（改造前写、改造后仍绿）；P2-1 又补 `tests/test_aftersale_sort.py` 7 例，两文件 **15/15 绿**；P2-2 补 `tests/test_aftersale_query_state.py` **32/32 绿**（纯逻辑，不依赖 qfw）。跨页排序与「视图反向拥有数据」已在 P2-1 修复：排序键下推 SQL、行操作改 id 锚；表格 model 化仍留 P3，见 §七。

## 三、为什么不迁 .ui

- **生成链已断且不可逆**：`autowork_with_table.py` 里 12 个手写类被塞进生成文件头部，重新 `pyuic` 会全部覆盖；重建 .ui 等于重画整个主窗口。
- **Designer 看不见 qfw 控件**：`ComboBox`/`InfoBar`/`RoundMenu`/`FlowLayout` 在 Designer 里是空占位，拖拽预览还不如直接跑程序。
- **多数界面是数据驱动的**：表格列来自 `TABLE_COLUMNS`、统计卡是循环生成的、操作列是 delegate 画出来的（不是 widget）。.ui 只能描述静态骨架，这些仍要写代码，反而多一层「ui 文件 + py 文件」同步成本。
- **团队约束**：AGENTS.md §3.1 原把 `autowork_with_table.py` 列为禁改生成物，但现实是它已被人手维护；P2-1 期间已把该条改为「历史生成物，改前先读本文」，文档需要的是更新事实，不是补回 .ui。

**结论**：手写 UI 不是原罪；问题在「一个类里混了四层职责」。改进方向是分层，不是上 .ui。

## 四、分层方案

```
windows/aftersale/records/
├── __init__.py       # 再导出 RecordsPage / TABLE_COLUMNS / _web_entry_url，保持旧 import 路径不变
├── query_state.py    # 纯逻辑：筛选字典、分页文案、列键、tooltip、短时间格式（无 Qt，可直接 pytest）
├── table_adapter.py  # 呈现层：记录 → CellSpec（文本/字体/色/对齐/操作链接）；排序已下沉 SQL
├── controller.py     # 编排层：唯一持有 QThread，worker 生命周期 + 信号中继（无 widget）
└── page.py           # 视图层：建控件、套用 CellSpec、把用户意图翻译成 controller 调用
```

依赖方向（单向，无环）：

```
page.py ──> controller.py ──> workers.aftersale_worker ──> database.aftersale_db
   │
   ├──> table_adapter.py ──> query_state.py
   └──> windows.aftersale.common（TABLE_COLUMNS 等）
```

三条硬边界（评审时按此卡）：

1. `controller.py` 不许出现 widget / InfoBar / QMessageBox；
2. `page.py` 不许 `new QThread` / 不许 import `AftersaleDBWorker`；
3. 跨线程只走 queued 信号（worker → controller → page），页面槽一律在主线程执行。

## 五、改造清单（P1 行为保持 + P2-1 缺陷修复）

| 原实现 | 现实现 |
| --- | --- |
| 页面内 9 个 `self._xxx_worker = AftersaleDBWorker(...)` | `RecordsController` 的 9 个 worker 属性；页面只调 `controller.query/fetch_cycles/mutate/...` |
| worker 的 `result_ready` 直接连页面方法（lambda 在 worker 线程执行） | worker → controller 信号 → 页面槽；Qt AutoConnection 自动排队回主线程（比原来更安全，行为等价） |
| `_populate` 内逐列 if/elif 造单元格 | `table_adapter.data_cells(rec)` 返回 `CellSpec` 列表；`_populate` 只负责套用 |
| `_short_dt` / `_current_filters` / `_col_key` / `_update_pager` / `_row_tooltip` | `query_state` 同名纯函数（`_row_tooltip` 方法名保留，兼容 `tools/perf/scroll_profile.py`:198 的 monkeypatch） |
| 写操作各自拼 InfoBar + 刷新 | `mutation_done(tag, payload)` + `_MUTATION_DONE` 表驱动（quick/batch_resolve/batch_delete/duplicate/update/delete 六种文案） |
| `pivot_page.detach_workers` 靠 `dir(page)` 扫 `*_worker` | 新增页面钩子 `page.detach_workers()`；`PivotPage` 先调钩子，再保留旧扫描兜底（其他页不受影响） |

外部契约未变：`from windows.aftersale.records import RecordsPage`（hub_pages / aftersale/window / tests / tools 共 10 处引用）无需改动；`set_keyword / refresh_async / _apply_smooth_mode / _sync_auto_timer / _cycles_loaded / _load_cycles_then_data` 等被外部调用的成员全部保留。

### P2-1：跨页排序下沉与行 id 锚（2026-10-18）

| 项 | 旧实现 | 现实现 |
| --- | --- | --- |
| 表头排序 | `_sort_table` 只对当前 60 行 `sortItems`，翻页后顺序不成立 | `_on_click_header` 先过 `LIST_SORT_KEYS` 白名单，再把 `sort_key/sort_order` 下推 `query_page` 的 `ORDER BY` |
| 排序键 | `_SortKeyItem` 在单元格里携带原始字段值，供 Qt 比较 | 删除 `_SortKeyItem`；`created_at`/`location`/`response_time` 由 SQL 按原列或逐级排序，是/否列用 `CASE` 转数值 |
| 行序锚 | `_sync_rows_to_table` 按勾选列 `UserRole` 锚把 `_rows` 重排成可视行序，行操作靠 `_rows[row]` | 删除 `_sync_rows_to_table`；`_populate` 建 `_rec_by_id`，所有行入口走 `_rec_at_row(row)`，按 id 反查记录 |
| 跨页稳定 | 无并列兜底，同值行在翻页时可能重漏 | `_build_order` 末尾统一追加 `id DESC`，并列行跨页顺序稳定 |
| 操作列 | 曾被 `col_key` 映射成 `"ops"`，存在被当排序键的风险 | `if col == _COL_CHECK or key not in aftersale_db.LIST_SORT_KEYS: return`，操作列不参与排序 |

排序白名单（`database/aftersale_db.py`）：`created_at` / `occurred_at` / `issue_type` / `location`（`room_name,region,table_no`）/ `problem` / `cause` / `solution` / `response_time` / `resolved` / `is_our_problem` / `is_initiative`。未知键回退 `id DESC`，方向只认 `asc`/`desc`。

行为保持：筛选、分页、统计卡、操作链接、勾选与视图还原均未改；翻页后排序由数据库保证，页面不再二次 `sortItems`。

## 七、遗留问题与风险（本轮明确不修）

1. **跨页排序已修（P2-1）**：`_sort_table` 已删除，排序键下推 `query_page` 的 `ORDER BY`。仍需守住：新增可排序列必须同时登记 `aftersale_db._LIST_SORT`，否则表头点击会被白名单静默忽略。
2. **视图反向拥有数据已修（P2-1）**：`_sync_rows_to_table` 已删除，`_rec_at_row` 按勾选列 `UserRole` 的 id 反查 `_rec_by_id`。记录不在当前页或 id 失效时返回 `None`，行操作直接返回，不再误伤相邻行。
3. **表格未 model 化**：仍用 qfw `TableWidget`（`QTableWidget` 子类）。60 行/页 + delegate 缓存已够用；换 `QAbstractTableModel` 需回归 27 处定制（勾选列、徽章、操作链、重要行底色…），留待 P3 按需。
4. **UIMixin 1600 行 / 5 mixin 未动**：这是下一个值得评审的上帝模块，但不在本试点范围。
5. **真机冒烟**：P1 后已走过「首屏 → 翻页 → 批量 → 编辑候选 → 导入导出 → 自动刷新/隐藏页面」；P2-1 排序已在 Windows 原生 Qt 平台用回归用例复跑通过。发版前仍建议补一轮人工目视：点表头、翻页看顺序、在排序态下点操作链。
6. **旧报告行号失效**：`docs/售后面板性能调查报告2026-09-06.md`、`docs/QSS使用审计与弃用评估.md` 等按旧 `records.py:NNN` 引用的行号已不可用；这些是历史快照，未逐条改（改路径引用已做）。
7. `tools/perf/scroll_profile.py` 的 `fewer_cols` 变体原先猴补丁 `records.TABLE_COLUMNS`，包化后需打 `table_adapter.TABLE_COLUMNS` 才生效；本次已同步修正该行。
