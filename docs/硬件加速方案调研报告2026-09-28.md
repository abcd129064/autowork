# 硬件加速方案调研报告（2026-09-28）

> 主题：桌面端（PySide6 + qfluentwidgets）是否/如何引入 GPU 硬件加速，  
> 以及 Intel 核显 / NVIDIA / AMD 三大阵营在 Windows 上的 OpenGL 兼容性风险。  
> 性质：**调研快照**——只调研、不改代码；结论供 P0/P1/P2 决策用。  
> 关联文档：[大屏与超高DPI渲染性能调查报告2026-09-25.md](大屏与超高DPI渲染性能调查报告2026-09-25.md)、  
> [表格滚动延迟调查报告2026-09-25.md](表格滚动延迟调查报告2026-09-25.md)、[DESIGN.md](DESIGN.md)。

---

## 0. 30 秒结论

1. **项目当前没有任何硬件加速设置**（全仓无 `QT_OPENGL*` / `AA_Use*OpenGL` / `QSG_*` / `QOpenGLWidget` 代码），  
   渲染全部走 Qt Widgets 的 **CPU raster 引擎**，这是 Qt Widgets 的默认形态，符合架构预期。
2. **Qt 6 已移除 ANGLE**：`AA_UseOpenGLES` / `QT_OPENGL=angle` 在 Qt 6 全部失效，  
   Windows 上 QWidget 系的硬件加速**只剩 OpenGL proper 一条路**（Qt 官方文档明确）。
3. 三大 GPU 阵营里，NVIDIA 桌面 GL 最稳，Intel 核显分代差异最大（老 HD 系驱动冻结），AMD 中间；  
   **RDP / 无 GPU 虚拟机是最大兼容性黑洞**——本项目恰好存在 RDP 远程使用场景。
4. 建议：**P0 不迁移渲染后端**（现有 CPU 侧优化收益已验证）；如试点 GL 视口（P1），  
   必须同时落软件回退链（打包产物已自带 `opengl32sw.dll`，具备兜底条件）。

## 一、现状盘点（证据）

### 1.1 渲染架构现状

| 项          | 现状                                                                                                                       | 出处                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |

| 硬件加速相关设置   | **不存在**。全仓检索 `AA_UseDesktopOpenGL` / `AA_UseOpenGLES` / `AA_UseSoftwareOpenGL` / `QOpenGL` / `QT_OPENGL*` / `QSG_*` 均零命中 | 全仓 grep（2026-09-28）                                                                      |

### 1.2 打包产物里的 GL 运行时（实测 dist/）

```
dist/AutoWork/_internal/PySide6/
├── Qt6OpenGL.dll        # Qt OpenGL 模块（QOpenGLWidget 所需，随 wheel 打入）
├── opengl32sw.dll       # Mesa llvmpipe 软件 OpenGL（兜底关键件，已自带 ✅）
```

## 二、Qt 6 硬件加速技术面（候选方案）

### 2.1 前置事实：Qt 6 相比 Qt 5 的关键变化（官方文档核实）

- **ANGLE 移除**：Qt 6 不再捆绑 ANGLE（GL ES→D3D 转译层），`AA_UseOpenGLES` 与  
  `QT_OPENGL=angle` **彻底失效**；动态 GL 构建初始化失败时也不再自动回退 ANGLE。
- **QWidget 系**：`QOpenGLWidget` / `QOpenGLWindow` 在 Qt 6 仍走 **OpenGL proper**，  
  没有任何 D3D/Vulkan 直通选项（RHI 只服务 Qt Quick / Quick 3D）。
- **Qt Quick 系**：Qt 6 起走 RHI，Windows 默认 **D3D11**，可用  
  `QSG_RHI_BACKEND=d3d11|vulkan|opengl|d3d12` 切换；`QSG_RHI_PREFER_SOFTWARE_RENDERER=1`  
  可强制 D3D WARP 软光栅。
- 动态 GL 加载（`-opengl dynamic`，PySide6 wheel 默认形态）：启动时探测系统  
  `opengl32.dll` 是否有 GL 2.0，有则用之，否则自动回退 `opengl32sw.dll`（Mesa llvmpipe）。

### 2.2 候选方案对比

| 方案                      | 内容                                                                                | 预期收益                                                           | 代价/风险                                                              | 判定                |
| ----------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------ | ----------------- |
| **A. 保持 raster（现状）**    | 不动渲染后端，继续 lean delegate / 文本层缓存路线                                                 | `已验证：S2 文本缓存 -84%、S5 整格缓存 -44~-59%（100k 记录 query_page 0.14ms）` | 0                                                                  | ✅ **P0 维持**       |
| **B. QOpenGLWidget 视口** | 给大表格容器挂 GL viewport，`AA_UseDesktopOpenGL` + 动态加载                                  | 合成/滚动走 GPU；但 delegate 仍 raster 到纹理，收益主要在**合成阶段**，绘制热点不解决       | 三厂商驱动矩阵 + RDP 兼容性测试成本高；与 Mica backdrop 组合未验证                       | ⚠️ P1 试点可选，预期收益有限 |
| **C. 迁移 Qt Quick/QML**  | RHI（D3D11 默认）全 GPU 渲染                                                             | 合成 + 绘制全 GPU，D3D11 比 GL 跨厂商更稳                                  | qfluentwidgets 是 QWidget 库，**整条 UI 栈重写**；WebEngine-Mica 坑证明宿主合成层敏感 | ❌ 否决（工作量不可接受）     |
| **D. 重引入 QWebEngine**   | Chromium GPU 合成                                                                   | 内嵌 Web 技术栈                                                     | 已实测与 Mica 冲突黑屏（`windows/stat_charts.py` 方案 A）                      | ❌ 已否决（历史结论）       |
| **E. 软件渲染兜底**           | `AA_UseSoftwareOpenGL`（强制 opengl32sw）或 WARP（`QSG_RHI_PREFER_SOFTWARE_RENDERER=1`） | RDP / VM / 老驱动机器的**稳定性保障**，非性能方案                               | 软渲染 CPU 占用高，只作兜底                                                   | ✅ 并入 P1/P2 兜底链    |

> **关键判断**：本项目渲染热点是 **delegate 逐格绘制 + CJK 字体光栅化**（见  
> 表格滚动延迟报告），这两件事在 GL viewport 方案 B 下**依然在 CPU 上做**——  
> GPU 只接管最后的纹理合成。这就是"收益预期有限"的技术依据。

## 三、GPU 厂商兼容性矩阵（Windows + OpenGL proper）

### 3.1 三阵营概览

| 维度           | Intel 核显                                                     | NVIDIA（GeForce/Quadro）                                         | AMD（Radeon）                                           |
| ------------ | ------------------------------------------------------------ | -------------------------------------------------------------- | ----------------------------------------------------- |
| 桌面 OpenGL 支持 | 分代分裂（见 3.2）                                                  | **最佳**，GeForce 全线 GL 4.6，驱动持续更新                                | 良好，GCN 起 GL 4.6，Adrenalin 驱动后期明显改善                    |
| 驱动更新策略       | 跟 Windows Update（OEM 机器常冻结在出厂版本）                             | GeForce Experience/官方站，更新频繁                                    | Adrenalin 月更                                          |
| 已知典型坑        | 老驱动 FBO/纹理 bug；混合双显（Intel+NVIDIA/AMD）下窗口跨屏渲染异常；OEM 白名单驱动缺失扩展 | **Optimus 双显**：默认常走 Intel 核显而非独显，需控制面板/驱动 profile 指定；驱动大版本偶发回归 | 早年 Catalyst→Adrenalin 交接期 ICD 兼容问题多；老 FirePro/企业卡驱动冻结 |
| 虚拟机/RDP      | 无 GPU 直通 → 无硬件 GL                                            | 同左                                                             | 同左                                                    |
| 对本项目权重       | **最高**（售后/球桌现场机器多为核显办公机）                                     | 低（本项目用户群少见）                                                    | 中                                                     |

### 3.2 Intel 核显分代（风险最高的阵营）

| 代际                                  | 代表型号               | GL 上限         | 状态                              | 对 QOpenGLWidget 方案的影响            |
| ----------------------------------- | ------------------ | ------------- | ------------------------------- | -------------------------------- |
| 旧 HD 系列（Ivy Bridge 及更早）             | HD 4000            | GL 4.0~4.3 封顶 | **驱动已冻结**（OEM 机常见）              | 可用但 bug 多（FBO 格式、MSAA）；必须进兼容性黑名单 |
| HD 5xx/6xx（Skylake~Kaby Lake）       | HD 520 / 620       | GL 4.5~4.6    | 驱动仍在 Windows Update 分发，但增速放缓    | 基本可用；跨屏/休眠恢复偶发黑块                 |
| UHD 6xx/7xx（Coffee Lake~Alder Lake） | UHD 630 / 770      | GL 4.6        | 活跃支持                            | 可用                               |
| Xe / Arc（DG 系列）                     | Iris Xe / Arc A 系列 | GL 4.6        | 活跃支持（Arc 早期驱动 GL 崩溃较多，2023 后收敛） | 可用                               |

### 3.3 RDP / 远程会话（本项目的真实场景 ⚠️）

本项目存在既定的 RDP 远程使用场景（生产机 `49.235.34.253:19955`）。RDP 会话下：

- 桌面被重定向为 **WARP/软合成**，多数环境**没有可用的硬件 OpenGL ICD**；
- Qt 动态 GL 探测 `opengl32.dll` 无 GL 2.0 → 自动回退 `opengl32sw.dll`（本包已带，能跑但 CPU 占用显著上升）；
- 强制 `AA_UseDesktopOpenGL`（显式指定后 Qt **跳过探测**）会在无 ICD 的会话里  
  **直接拿不到 GL 上下文**——即方案 B 若做，**绝不能硬编码显式模式，必须保留动态探测**。
- 结论：RDP 场景 = 方案 B 的天然回归测试场，也是"为什么不建议动渲染后端"的最直接论据。

### 3.4 兼容性风险汇总矩阵

| 环境                  | 方案 A（raster）         | 方案 B（QOpenGLWidget）        | 方案 C（Quick/D3D11）  |
| ------------------- | -------------------- | -------------------------- | ------------------ |
| NVIDIA 独显           | ✅ 无风险                | ✅ 低风险（Optimus 需指定高性能 GPU）  | ✅ 低风险              |
| Intel 新核显（UHD 6xx+） | ✅ 无风险                | ⚠️ 中风险（跨屏/休眠恢复）            | ✅ 低风险              |
| Intel 老核显（HD 4xxx-） | ✅ 无风险                | ⚠️ **高风险**（驱动冻结 + FBO bug） | ⚠️ 中风险             |
| AMD Radeon          | ✅ 无风险                | ⚠️ 中风险（驱动版本散）              | ✅ 低风险              |
| RDP / VM / 无 GPU    | ✅ 无风险（raster 不依赖 GL） | ❌ 需软件回退，CPU 占用高            | ✅ 自动回退 WARP（Qt 内建） |
| 与 Mica/Acrylic 共存   | ✅ 已验证                | ❓ **未验证**（WebEngine 已在此翻车） | ❓ 未验证              |

## 四、结论与建议

### 4.1 结论

1. 硬件加速对本项目**当前瓶颈无解**：热点在 delegate 绘制与字体光栅化（CPU），  
   GL viewport 只加速合成阶段；现有 CPU 优化链（S2/S5 缓存）已拿到主要收益。
2. Qt 6 的技术面使 QWidget 系硬件加速**只剩 OpenGL proper 一条路**，而 OpenGL 恰是  
   三大 GPU 阵营中兼容性最参差的 API（对比：Qt Quick 的 D3D11 默认后端反而更稳，  
   但迁移成本不可接受）。
3. RDP 远程场景与 Mica backdrop 共存是两个**未验证/已翻车**的宿主组合因素，  
   任何 GL 化尝试都必须先过这两关。

### 4.2 建议（P0/P1/P2）

| 优先级        | 动作                                                             | 说明                                                                                                                                                                |
| ---------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **P0**     | 渲染后端**保持 raster 不动**                                           | 继续沿 lean delegate / 缓存路线；本报告作为"为什么不加硬件加速"的决策依据归档                                                                                                                  |
| **P1（可选）** | 若未来确需试点：QOpenGLWidget + 动态 GL，且**禁止硬编码** `AA_UseDesktopOpenGL` | 前置条件：① 三厂商真机矩阵回归（Intel 老核显 + UHD 630 + 任一 N/A 卡）；② RDP 会话 smoke（验证自动回退 `opengl32sw.dll`）；③ 与 Mica backdrop 共存的冒烟脚本（`tools/smoke/smoke_gl_viewport_mica.py` 命名，待建） |
| **P2**     | 兜底与观测设施（成本极低，随时可做）                                             | ① 启动日志记录 GL 探测结果（`QSG_INFO=1` 等价信息：回退是否发生、llvmpipe 是否加载）；② 兼容性黑名单机制（Qt 支持 `QT_OPENGL_BUGLIST` JSON，按显卡/驱动版本自动降级，Chromium 格式）                                      |

### 4.3 验证计划（若启动 P1）

1. `tools/smoke/` 新增 GL 视口冒烟：GL 上下文建立 → 帧率基线 → 关闭后像素等价对比（对齐 S5 的 35 例回归口径）；
2. 真机矩阵：至少覆盖 Intel HD 4000 级 / UHD 630 / NVIDIA 一张 / AMD 一张，各跑 `pytest tests/ -q` + 冒烟脚本；
3. RDP 会话回归：`49.235.34.253:19955` 远程桌面内跑全量冒烟，确认自动软回退生效且 CPU 占用可接受；
4. 数据安全：探针执行前对 `config/` `database/` 做 mtime+size 快照（AGENTS.md §5.2 惯例）。

## 六、补充：硬件加速对表格控件的优化项分析（2026-09-28 追问）

> 问题：改用硬件加速，对 QTableWidget 的性能到底有哪些优化项？

### 6.1 先看一帧的流水线

```
【现状 raster】                          【GL viewport（方案 B）】
delegate 逐格 QPainter 绘制  ← 热点①      delegate 逐格 QPainter 绘制（QOpenGLPaintEngine）← 热点①仍在 CPU
  ↓ 进 backing store（CPU 内存）            ↓ 进 GPU FBO
backing store → 窗口提交                  FBO 合成（GPU）
  ↓                                        ↓
DWM 合成到屏幕（这步本来就在 GPU！）        DWM 合成（不变）
```

两个关键事实：

1. **终点合成早就是 GPU 的**——Windows Vista 起 DWM 负责窗口到屏幕的合成，  
   raster 模式提交的是一张 CPU 位图，"贴到屏幕"这一步没有任何 CPU 浪费可省。
2. 换 GL viewport 后，**delegate 绘制仍走 QPainter**（只是引擎换成 QOpenGLPaintEngine），  
   本项目已验证的热点（委托逐格绘制 × CJK 字体光栅化 × DPI 光栅放大，  
   见表格滚动延迟报告）**一个都没离开 CPU**。

### 6.2 GL viewport 真实存在的优化项（按预期收益排序）

| # | 优化项                         | 机制                                      | 对本项目的预期收益                                                                                                 |
| - | --------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 1 | **滚动时的视口位块搬移**              | 平滑滚动/加速滚动时可见区重绘范围更大，GL 下搬移是 GPU blit    | **低**：S5 整格缓存落地后，重绘本身就是"缓存 QPixmap 的 blit"，CPU blit 对内存带宽而言已接近地板                                          |
| 2 | **大面积纯色/交替行填充**             | 填充率是 GPU 强项                             | **可忽略**：交替行填充在 raster 下就是 memset 级操作，从来不是热点                                                               |
| 3 | **glyph 纹理图集**              | QOpenGLPaintEngine 用纹理图集缓存字形，重复字符免重光栅   | **负收益风险**：raster 的 QImage 字形缓存同样会缓存；而小文本碎片 draw call 在 GL 引擎里状态切换开销反而更高，Qt 社区长期结论是 2D UI 场景 raster 引擎通常更快 |
| 4 | **不透明度/模糊特效合成**             | opacity 渐变、QGraphicsEffect 走 GPU shader | **与表格无关**：这是弹窗淡入（P0-1 已做阈值降级）的潜在受益项，不是表格的                                                                 |
| 5 | **超大 DPI backing store 搬移** | 55 寸 4K 物理像素大位图搬运                       | **低**：受益主体仍是"合成阶段"，且 DWM 已分走一次                                                                            |

### 6.3 换 GL viewport 的副作用（表格场景特有）

- QOpenGLWidget 在 QScrollArea/复杂子控件宿主下有一批历史行为差异  
  （原生子窗口叠加、`WA_PaintOnScreen` 语义、grab()/截图变 glReadPixels 回读变慢）；
- FBO 随窗口/DPI 变化重建，4K 双缓冲 ≈ 2 × 33MB 显存；
- 换来的是 §3.4 整张 GPU 驱动兼容矩阵 + RDP 会话回退风险。

### 6.4 追问结论

**硬件加速对表格控件的"真实优化项"只有合成/搬移阶段，而本项目表格的性能地板  
已被 S2/S5 缓存方案压到 CPU blit 级别，GPU 能接管的剩余空间 < 换后端引入的  
兼容性成本。** 若仍要定量验证，唯一推荐做法是不改主程序，在  
`tools/perf/perf_scroll_latency.py` 基础上加一个 `--gl-viewport` 开关做 A/B 实测  
（单面板、可回退），拿到真实帧耗时差再决策——预期结果是差异在误差范围内。
