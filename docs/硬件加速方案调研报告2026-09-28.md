# 硬件加速方案调研报告（2026-09-28）

> 主题：桌面端（PySide6 + qfluentwidgets）是否/如何引入 GPU 硬件加速，  
> 以及 Intel 核显 / NVIDIA / AMD 三大阵营在 Windows 上的 OpenGL 兼容性风险。  
> 性质：**调研快照**——只调研、不改代码；结论供 P0/P1/P2 决策用。  
> 勘误：2026-09-29 复核修订五处（dist 实测清单、GL 绘制机制、0.14ms 引用、  
> buglist 表述、明文 IP），全部修订点见文末 §七。  
> 关联文档：[大屏与超高DPI渲染性能调查报告2026-09-25.md](大屏与超高DPI渲染性能调查报告2026-09-25.md)、  
> [表格滚动延迟调查报告2026-09-25.md](表格滚动延迟调查报告2026-09-25.md)、[DESIGN.md](DESIGN.md)。

## 0. 30 秒结论

1. **项目当前没有任何硬件加速设置**（全仓无 `QT_OPENGL*` / `AA_Use*OpenGL` / `QSG_*` / `QOpenGLWidget` 代码），  
   渲染全部走 Qt Widgets 的 **CPU raster 引擎**，这是 Qt Widgets 的默认形态，符合架构预期。
2. **Qt 6 已移除 ANGLE**：`AA_UseOpenGLES` / `QT_OPENGL=angle` 在 Qt 6 全部失效，  
   Windows 上 QWidget 系的硬件加速**只剩 OpenGL proper 一条路**（Qt 官方文档明确）。
3. 三大 GPU 阵营里，NVIDIA 桌面 GL 最稳，Intel 核显分代差异最大（老 HD 系驱动冻结），AMD 中间；  
   **RDP / 无 GPU 虚拟机是最大兼容性黑洞**——本项目恰好存在 RDP 远程使用场景。
4. 建议：**P0 不迁移渲染后端**（现有 CPU 侧优化收益已验证）；如试点 GL（P1），  
   必须先补齐 QtOpenGL 打包分发（现包内只有兜底件 `opengl32sw.dll`，**没有** `Qt6OpenGL/Qt6OpenGLWidgets`，
   见 §1.2 勘误），且"给现有表格挂 GL 视口"这条路径并不存在，见 §二方案 B 与 §六勘误。

### 1.2 打包产物里的 GL 运行时（实测 dist/）

```
dist/AutoWork/_internal/PySide6/    # 2026-09-24 构建（spec 此后未改动，结果可代表现行打包逻辑）
├── Qt6Core/Gui/Widgets/Svg/SvgWidgets/Network/Xml.dll + 对应 .pyd（共 7 组）
├── opengl32sw.dll       # Mesa llvmpipe 软件 OpenGL（20.6 MB，兜底关键件，确在包内 ✅）
├── （无 Qt6OpenGL.dll / Qt6OpenGLWidgets.dll / QtOpenGL.pyd / QtOpenGLWidgets.pyd
──   ——勘误：项目零 GL 引用，pip 布局下 PyInstaller hook 按 import 收集，
    AutoWork.spec 的 conda 收集分支不生效，GL 模块**未进包**，见 §七勘误①）
└── （无 libEGL.dll / libGLESv2.dll —— ANGLE 在 Qt 6 已移除，与官方一致）
```

**结论（勘误后）：软件回退件在包里，但 GL 主件不在**。`opengl32sw.dll` 确随包分发
（Qt 动态加载失败时的默认软回退查找名即此），但 `QOpenGLWidget` 所在的
`Qt6OpenGL/Qt6OpenGLWidgets` DLL 与 `QtOpenGL/QtOpenGLWidgets.pyd` 目前**均未进包**——
打包版连 `import QOpenGLWidget` 都会失败。方案 B 的任何试点都要先补 spec 分发
（注意本仓已登记过打包过滤的 reclassification 陷阱），"具备兜底条件"只在补分发之后才成立。  
附带推论：现状纯 raster 应用不会创建任何 GL 上下文，这 20.6 MB 的 `opengl32sw.dll`
是**永不加载的分发死重**，剔除与否是独立的体积决策项（更新包每次少 20MB）。

## 二、Qt 6 硬件加速技术面（候选方案）

### 2.1 前置事实：Qt 6 相比 Qt 5 的关键变化（官方文档核实）

- **ANGLE 移除**：Qt 6 不再捆绑 ANGLE（GL ES→D3D 转译层），`AA_UseOpenGLES` 与  
  `QT_OPENGL=angle` **彻底失效**；动态 GL 构建初始化失败时也不再自动回退 ANGLE。
- **QWidget 系**：`QOpenGLWidget` / `QOpenGLWindow` 在 Qt 6 仍走 **OpenGL proper**，  
  没有任何 D3D/Vulkan 直通选项（RHI 只服务 Qt Quick / Quick 3D）。
- **Qt Quick 系**：Qt 6 起走 RHI，Windows 默认 **D3D11**，可用  
  `QSG_RHI_BACKEND=d3d11|vulkan|opengl|d3d12` 切换；`QSG_RHI_PREFER_SOFTWARE_RENDERER=1`  
  可强制 D3D WARP 软光栅。
- 动态 GL 加载（`-opengl dynamic`，PySide6 wheel 默认形态）：启动时探测系统  
  `opengl32.dll` 是否有 GL 2.0，有则用之，否则自动回退 `opengl32sw.dll`（Mesa llvmpipe）。

> 这就是"收益预期有限"的技术依据。

### 3.3 RDP / 远程会话（本项目的真实场景 ⚠️）

本项目存在既定的 RDP 远程使用场景（生产机与端口见 `docs/DEPLOYMENT.md`，此处不重复明文）。RDP 会话下：

- 桌面被重定向为 **WARP/软合成**，多数环境**没有可用的硬件 OpenGL ICD**；
- Qt 动态 GL 探测 `opengl32.dll` 无 GL 2.0 → 自动回退 `opengl32sw.dll`（本包已带，能跑但 CPU 占用显著上升）；
- 强制 `AA_UseDesktopOpenGL`（显式指定后 Qt **跳过探测**）会在无 ICD 的会话里  
  **直接拿不到 GL 上下文**——即方案 B 若做，**绝不能硬编码显式模式，必须保留动态探测**。
- 结论：RDP 场景 = 方案 B 的天然回归测试场，也是"为什么不建议动渲染后端"的最直接论据。

### 3.4 兼容性风险汇总矩阵

## 四、结论与建议

### 4.1 结论

1. 硬件加速对本项目**当前瓶颈无解**：热点在 delegate 绘制与字体光栅化（CPU），  
   GL viewport 只加速合成阶段；现有 CPU 优化链（S2/S5 缓存）已拿到主要收益。
2. Qt 6 的技术面使 QWidget 系硬件加速**只剩 OpenGL proper 一条路**，而 OpenGL 恰是  
   三大 GPU 阵营中兼容性最参差的 API（对比：Qt Quick 的 D3D11 默认后端反而更稳，  
   但迁移成本不可接受）。
3. RDP 远程场景与 Mica backdrop 共存是两个**未验证/已翻车**的宿主组合因素，  
   任何 GL 化尝试都必须先过这两关。

### 4.2 建议（P0/P1/P2）

| 优先级        | 动作                                                             | 说明                                                                                                                                                                |
| ---------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **P0**     | 渲染后端**保持 raster 不动**                                           | 继续沿 lean delegate / 缓存路线；本报告作为"为什么不加硬件加速"的决策依据归档                                                                                                                  |
| **P1（可选）** | 若未来确需试点：QOpenGLWidget + 动态 GL，且**禁止硬编码** `AA_UseDesktopOpenGL` | 前置条件：⓪ spec 补发 `Qt6OpenGL/Qt6OpenGLWidgets.dll` + `QtOpenGL/QtOpenGLWidgets.pyd`（现包内无，见 §1.2）；① 表格自绘重写原型（不存在"给现有表格挂视口"路径，见 §二方案 B）；② 三厂商真机矩阵回归（Intel 老核显 + UHD 630 + 任一 N/A 卡）；③ RDP 会话 smoke（验证自动回退 `opengl32sw.dll`）；④ 与 Mica backdrop 共存的冒烟脚本（`tools/smoke/smoke_gl_viewport_mica.py` 命名，待建）；⑤ S5 像素等价回归在 GL 回读下的容差口径 |
| **P2**     | 兜底与观测设施（成本极低，随时可做）                                             | ① 启动日志记录 GL 探测结果（`QSG_INFO=1` 等价信息：回退是否发生、llvmpipe 是否加载）；② 兼容性黑名单机制（Qt 支持 `QT_OPENGL_BUGLIST` JSON，按显卡/驱动版本自动降级，Chromium 格式）                                      |

### 4.3 验证计划（若启动 P1）

1. `tools/smoke/` 新增 GL 视口冒烟：GL 上下文建立 → 帧率基线 → 关闭后像素等价对比（对齐 S5 的 35 例回归口径）；
2. 真机矩阵：至少覆盖 Intel HD 4000 级 / UHD 630 / NVIDIA 一张 / AMD 一张，各跑 `pytest tests/ -q` + 冒烟脚本；
3. RDP 会话回归：生产远程桌面内跑全量冒烟（地址见 `docs/DEPLOYMENT.md`），确认自动软回退生效且 CPU 占用可接受；
4. 数据安全：探针执行前对 `config/` `database/` 做 mtime+size 快照（AGENTS.md §5.2 惯例）。

## 六、补充：硬件加速对表格控件的优化项分析（2026-09-28 追问）

> 问题：改用硬件加速，对 QTableWidget 的性能到底有哪些优化项？

### 6.1 先看一帧的流水线

```
【现状 raster】                          【方案 B：表格自绘重写为 GL widget】
delegate 逐格 QPainter 绘制  ← 热点①      自绘 GL 代码逐格绘制（QOpenGLPaintEngine，仅此时才生效）← 热点①仍在 CPU
  ↓ 进 backing store（CPU 内存）            ↓ 进 GPU FBO（前提：整个表格已重写，非"挂视口"）
backing store → 窗口提交                  FBO 合成（GPU）
  ↓                                        ↓
DWM 合成到屏幕（这步本来就在 GPU！）        DWM 合成（不变）
```

两个关键事实：

1. **终点合成早就是 GPU 的**——Windows Vista 起 DWM 负责窗口到屏幕的合成，  
   raster 模式提交的是一张 CPU 位图，"贴到屏幕"这一步没有任何 CPU 浪费可省。
2. （勘误）**`QOpenGLPaintEngine` 只服务于 QOpenGLWidget 自身 `paintGL()` 里的 QPainter**；  
   QTableWidget 的 delegate 恒走 raster 引擎进 backing store，**在旁边挂一个 QOpenGLWidget  
   不会让 delegate"换引擎"**。所以"给现有大表格挂个 GL 视口"这条路径根本不存在——  
   真要用 GL 只能把表格整体重写为自绘 widget，届时热点（委托逐格绘制逻辑 × CJK 字体光栅化 ×  
   DPI 光栅放大）**主体仍在 CPU**，且要额外付一次 GL 子窗口与原生子控件混排的合成/回读。

### 6.2 GL viewport 真实存在的优化项（按预期收益排序）

| # | 优化项                         | 机制                                      | 对本项目的预期收益                                                                                                 |
| - | --------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 1 | **滚动时的视口位块搬移**              | 平滑滚动/加速滚动时可见区重绘范围更大，GL 下搬移是 GPU blit    | **低**：S5 整格缓存落地后，重绘本身就是"缓存 QPixmap 的 blit"，CPU blit 对内存带宽而言已接近地板                                          |
| 2 | **大面积纯色/交替行填充**             | 填充率是 GPU 强项                             | **可忽略**：交替行填充在 raster 下就是 memset 级操作，从来不是热点                                                               |
| 3 | **glyph 纹理图集**              | QOpenGLPaintEngine 用纹理图集缓存字形，重复字符免重光栅   | **负收益风险**：raster 的 QImage 字形缓存同样会缓存；而小文本碎片 draw call 在 GL 引擎里状态切换开销反而更高，Qt 社区长期结论是 2D UI 场景 raster 引擎通常更快 |
| 4 | **不透明度/模糊特效合成**             | opacity 渐变、QGraphicsEffect 走 GPU shader | **与表格无关**：这是弹窗淡入（P0-1 已做阈值降级）的潜在受益项，不是表格的                                                                 |
| 5 | **超大 DPI backing store 搬移** | 55 寸 4K 物理像素大位图搬运                       | **低**：受益主体仍是"合成阶段"，且 DWM 已分走一次                                                                            |

### 6.3 换 GL viewport 的副作用（表格场景特有）

- QOpenGLWidget 在 QScrollArea/复杂子控件宿主下有一批历史行为差异  
  （原生子窗口叠加、`WA_PaintOnScreen` 语义、grab()/截图变 glReadPixels 回读变慢）；
- FBO 随窗口/DPI 变化重建，4K 双缓冲 ≈ 2 × 33MB 显存；
- 换来的是 §3.4 整张 GPU 驱动兼容矩阵 + RDP 会话回退风险。

### 6.4 追问结论

**硬件加速对表格控件的"真实优化项"只有合成/搬移阶段，而本项目表格的性能地板  
已被 S2/S5 缓存方案压到 CPU blit 级别，GPU 能接管的剩余空间 < 换后端引入的  
兼容性成本。** 若仍要定量验证，唯一推荐做法是不改主程序，在  
`tools/perf/perf_scroll_latency.py` 基础上加一个"自绘 GL 面板"开关做 A/B 实测  
（**须跑在开发环境**——当前 dist 无 QtOpenGL 模块，打包版跑不了 GL 路径，见 §1.2；  
单面板、可回退），拿到真实帧耗时差再决策——预期结果是差异在误差范围内。
