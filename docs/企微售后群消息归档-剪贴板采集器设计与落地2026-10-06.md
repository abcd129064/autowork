## 一、背景与约束

| 项 | 事实 |
| --- | --- |
| 触发原因 | 用户是售后群群主，但**不是企微超管**；官方会话存档的 4 个后台动作（开通专区 / 传确认函 / 配 RSA 公钥 / 加可信 IP）一个也做不了 |

## 二、采集机制（真机逆向出来的操作序列）

原理：**模拟一个手快的人** —— 在企微窗口里拖选消息、按 PageUp 翻页、Ctrl+C，
然后读系统剪贴板。企微客户端「复制」出来的文本**自带发送人和时间戳**，
所以结构化程度远高于截图 OCR。全程只用 `SendInput` + `OpenClipboard`（纯 Win32），
不注入进程、不 hook、不读进程内存、不解密企微本地数据库、不调非公开协议。

### 2.1 先记三条失败路径（都是实测踩出来的）

| 尝试 | 结果 | 原因 |
| --- | --- | --- |
| 拖选 → 连按 PageUp → Ctrl+C | 剪贴板**一直不变**（3 轮全 318 字符） | PageUp 只把列表滚上去了，**选区没扩展** |
| 拖选时不松左键（`--hold`）→ 连按 PageUp | 同样不变（3 轮全 428 字符） | 只按键、鼠标不动，企微不重算选区 |
| `--mode scroll`：滚轮上翻 → **重新拖选** → Ctrl+C | 有效但粗：4 格滚轮一轮就从"最新"滚到"列表顶"（本群消息太少），只能靠批次重叠去重 | 可用，但滚动幅度不可控 |

### 2.2 成立的序列（`--mode pageup --hold`）★ 推荐

**关键是用户点破的一句话："按 pageup 后需要按住左键移动一下才会复制到"。**
即完整动作为：**按住左键 → PageUp → 鼠标移动一点 → Ctrl+C**。落在代码里（`win_api/wecom_clip_driver.py:565-598`）：

```
第 0 轮：从锚点向上拖选 drag_px（默认 = 最大化后窗口高的 55%，下限 320px）→ Ctrl+C → 读剪贴板
之后每轮：key_tap(VK_PRIOR) → sleep(page_wait)
          → mouse_move(sx, band_top ± jiggle)   # 奇偶交替上下，保证坐标真的变了
          → Ctrl+C → 读剪贴板
终止：连续 stable（默认 3）轮剪贴板内容完全不变 / 达到 pages 上限 / 用户按 Esc 急停
```

配套的工程细节（每一条都是踩坑换来的）：

- **必须先声明 DPI 感知**（`SetProcessDpiAwarenessContext(-4)`）。本机三显示器、主屏 150% 缩放、企微窗口在负坐标区 (1903,-1080)-(3823,0)，不声明的话归一化坐标会整体偏移。
- **激活窗口要用 `AttachThreadInput` 挂到前台线程**，否则 `SetForegroundWindow` 被系统静默忽略。
- **拖拽要分步**（24 步），一次跳到底会被当成单击、不建选区。
- **剪贴板要重试读取**（`read_clipboard(retries=12)`），它经常被别的进程占着。
- **收尾要恢复现场**：松开左键、鼠标归位、还原窗口位置、把前台窗口还给原来的程序（异常路径也恢复）。

### 2.3 备选序列（`--mode scroll`）

滚轮上翻 N 格 → **重新拖选同一段** → Ctrl+C。不依赖"选区自动扩展"，
但滚动幅度不可控，必须靠**批次重叠自检**（相邻两批的 msg_id 集合若有零交集 → 判定漏采并告警）来兜。

### 2.4 真机操作步骤（唯一 GUI/采集基线解释器）

```powershell

# ① 只读自检（不发输入）：结构体尺寸 / 坐标换算 / 剪贴板 / 解析器
```

## 四、解析器（`core/wecom_clip.py`）

### 4.1 剪贴板文本的真实格式（对用户手工复制样本逐字节实测）

行尾 CRLF、无 BOM。**消息头 = `<发送人显示名> <M/D> <H:MM:SS>`**，正文跟在下一行，消息之间空行分隔：

```
江苏~朱华国@微信@微信联系人 8/12 12:55:45
[视频]

孙跃源 9/22 18:14:31
更换电池后，要按f2进入bios界面，
1点开Power Management，AC Recovery选项，选择Power On
```

实测特性（**都是实测，不是猜的**）：

- **时间戳只有月/日，没有年份** → 年份必须由采集时刻推断。
- 外部联系人显示名带后缀 `@微信@微信联系人`（`sender_kind=external_wechat`），内部成员没有（`internal`）。
- @提及用 **U+2005（FOUR-PER-EM SPACE）** 分隔，且**同一条消息里可能一个用显示名、一个用原始 openim id**（`@25984982603779408@openim`）。
- 非文本消息表现**不统一**：视频 → 正文 `[视频]`；**图片 / 文件 → 正文为空**。
- 正文可以多行。

### 4.2 关键规则（改动前先读这段）

- `HEADER_RE` 用**非贪婪** `(.+?)` 匹配发送人 + 强制 `M/D H:MM:SS` 收尾 → 正文里像消息头的行不会误切（只会产生 `time_regression` 告警）。
- `normalize_clip_text` **只 rstrip 行尾**，保留行首空白（@提及场景行首空格有意义）。
- `msg_id` = `sha1(room_id, sender_raw, M, D, H, M, S, content)[:20]`，**刻意不含年份** —— 年份是推断的，一旦推断变化，含年份的指纹会让去重整体失效。
- `msg_ts` 是**定长字符串** `"YYYY-MM-DD HH:MM:SS"`（不是 datetime），因为 DDL 是 `VARCHAR(32)`，且字符串比较正好等价于时间比较、能吃索引。
- 去重两遍：① 按 `msg_id`；② 同一 `(sender_raw, msg_ts)` **且归一化正文互为子串** → 保留最长的（必须两个条件同时满足，避免误并同秒的两条不同消息）。第二遍是为了修"拖选边界把正文开头的 @提及截掉"造成的重复（实测 36 → 35 条）。
- `ParseWarning.code`：`no_header` / `leading_text` / `empty_body` / `bad_datetime` / `time_regression`。**只有 `bad_datetime` 会丢消息**，其余只告警 —— 尤其 `time_regression` 只告警不过滤，避免把正文里像消息头的行当真丢掉。

## 五、归档库

### 5.1 三张表（`database/schema.py`，SQLite/MySQL 同一份定义）

| 表 | 主键 | 用途 |
| --- | --- | --- |
| `chat_archive_messages` | `msg_id`（指纹，双端都是主键） | 16 列：`source, room_id, room_name, sender_id, sender_name, sender_raw, sender_kind, msg_type, content, media_count, msg_ts, msg_ts_inferred_year, mentions, pull_batch, created_at` |
| `chat_archive_tags` | `id`（自增） | `msg_id, category, matched_rule, confidence, tagged_by, created_at` —— 打标层落点，本次未接 |
| `chat_archive_cursor` | `scope` | `next_cursor, last_msg_ts, last_success_ts, updated_at` —— **断点自愈的依据**，定时增量采集靠它 |

索引：`idx_chat_archive_room_ts(room_id, msg_ts)`、`idx_chat_archive_source_ts(source, msg_ts)`、`idx_chat_tags_msg(msg_id)`、`idx_chat_tags_category(category)`。

两条容易被忽略的约定：

- **分组维度是 `room_id`，`room_name` 只做展示**（沿用 `database/aftersale_db.py:887` 那个 `TRIM(room_name)` 的教训：群一改名就撕裂、群里重名就合并）。
- **`chat_archive_cursor` 天然豁免保留期清理**：`database/data_retention.py` 的表白名单 `_SIZE_TABLES` / `_STATUS_TABLES` 里没有它，而 `_cleanup_by_size` 取不到映射就 `continue`。已有结构性 + 功能性两条回归测试锁死（往 `cfg["tables"]` 里硬塞归档表名，断言 `deleted == 0` 且数据与 cursor 原样）。

### 5.2 导入管线

```python
from core import wecom_clip
# 从冒烟产物目录一条龙：读 batch → 解析 → 去重 → 入库 → 推进断点
wecom_clip.import_batches_dir(out_dir, room_id="after_sales", room_name="售后群")
```

- `insert_messages` 是**先查后插**（分块 60 行），刻意不用 `INSERT OR IGNORE`：`database/backend.py:178 convert_insert_or_replace` 只转 `INSERT OR REPLACE`，`OR IGNORE` 在 MySQL 侧会原样下发报错。
- 返回 `{"inserted", "skipped", "invalid"}`；批内重复计 `invalid`。
- 写库成功后 `set_cursor(scope=room_id, next_cursor=latest_msg_ts)` —— **增量采集的下一步永远从上一次成功的位置开始**。
- DAO 的数据库调用是**函数内延迟导入**（`from database import chat_archive_db`），所以 `core/wecom_clip` 的纯解析函数可以在不碰数据库的情况下被单测。

### 5.3 三维透视（`query_pivot`）

群 × 时间段 × 问题类型，口径对齐既有 `windows/aftersale/rank.py`。注意：
`LEFT JOIN chat_archive_tags` + `GROUP BY m.room_id, COALESCE(NULLIF(t.category,''), '未分类')`
→ **「未分类」在结果里是按群分行出现的**，跨群汇总要自己求和（写测试时踩过这个坑）。

## 八、局限与已知问题

1. **图片 / 文件 / 视频只有占位符，拿不到媒体本身。** 剪贴板给的是 `[视频]` 或空正文。
   售后群里客户发的故障截图**采不到图**，只能知道"这里有一条非文本消息"（`media_count=1`）。
   要图就得走截图 OCR 那条路（本方案刻意不做，见 §十）。
2. **年份是推断的。** 剪贴板不给年份，靠"首条 (M,D) 晚于采集日则取采集年-1，其后 (M,D) 回绕则 +1"补。跨年边界的批量历史数据要人工核一眼。
3. **@提及的形态不稳定**：可能是显示名，也可能是 `25984982603779408@openim` 这种原始 id。目前原样保留在 `mentions` 里。
4. **采集期间独占桌面**：约 1 分钟不能动鼠标键盘，Esc 可急停。
5. **依赖窗口布局**：拖拽锚点得落在消息列表里；窗口被最大化、列表滚到最新一条是前提。
6. **只能采"看得见的"**：企微客户端上没加载出来的历史采不到；群消息量大时要调大 `--pages`，靠批次重叠自检确认没漏。
7. **`media_count` 依赖正文特征**：只有 `image/video/file/voice` 记 1，其它一律 0。

## 九、发现的既有缺陷（**不在本次改动范围内，未修**）

### 缺陷 A：MySQL 模式下，SQLite 兜底库永远不会补建新表

`database/table_db.py:287`（`_ensure_initialized` 内）：

```python
if backend.is_mysql_test_mode():
    # MySQL：DDL 已在建库时就绪（IF NOT EXISTS），无需执行建表脚本
    _initialized = True
    return
```

而 `_ensure_initialized` 只有两个调用点：`database/table_db.py:501`（`_get_sqlite_conn` 内，**传的正是 SQLite 连接**）
和 `database/fallback_backup.py:95`（`backup_mysql_to_sqlite` 内，`table_db._ensure_initialized(sl)  # 确保本地表结构就绪`，传的也是裸 sqlite 连接）。
→ 只要 `config/database.json` 里 MySQL 是 enabled，**本地 `database/tables.db` 就再也建不出新表**，
新增的表只会在 MySQL 侧由 `_ensure_mysql_tables` 创建。`fallback_backup.py:95` 的注释说明作者本意就是"确保本地表结构就绪"，
所以这是**实现与意图不一致**，不是刻意设计。实测本机 `database/tables.db`（63.6 MB / 23 张表）里
`chat_archive_*` 三张表确实都不存在。

最小修法：早退条件收紧成"仅当连接不是 SQLite 时"（`isinstance(conn, sqlite3.Connection)`）。
代价：MySQL 模式下首次打开兜底库会多跑一次建表 + `_setup_fts`（1114 行表的索引重建，一次性）。
**改它会动到全仓启动路径，需要单独拍板 + 全量回归。**

### 缺陷 B：MySQL 降级期间写进 SQLite 的归档数据不会回写

`database/merge_back.py:40` 的 `_OPS_TABLES` 只覆盖 `billiard_tables/xqzg_status/kd_status/submission_log`，
`merge_back()` 不含 `chat_archive_*`。→ 降级期入的归档消息，MySQL 恢复后不会合并回去。
`merge_ops_tables` 是通用范式，`chat_archive_messages.msg_id` 与 `chat_archive_cursor.scope` 都是稳定字符串主键，
**适配得上**；但 `chat_archive_tags.id` 是后端本地自增，不宜按 id 合并。待决。

### 当前环境（决定"能不能入库"）

本机 `backend.is_mysql_test_mode() == True`（config → `49.235.34.253`）但 **`pymysql` 未安装**
→ `_get_conn` 每次 `mark_degraded()` 后落到本地 SQLite。
叠加缺陷 A ⇒ **本机现在无法入库**：三张归档表既不在 MySQL（连不上）也不在 `database/tables.db`。
三条出路（按推荐排序）：① 修缺陷 A；② 手工建 3 张表；③ 装上 `pymysql` 让 MySQL 通了由应用自动建表。
