## 三、问题清单（新发现 N / 仍存在 R）

### N1【P0】周期下拉加载 74% 时间耗在反复读 settings.json

- **现象**：打开面板首次加载 185ms，其中周期下拉（get_cycle_options）独占 ~80ms。
- **触发路径**：`database/aftersale_db.py:83 load_cycle_mode()`（每次调用 open+json.load settings.json）← `cycle_start_of():205`（每次调用 load_cycle_mode）← `get_cycle_options():708`（对 DISTINCT 日期**逐个** cycle_start_of）。
- **根因**：load_cycle_mode 无任何缓存；backend.py 同类问题已修（进程缓存），本函数漏网。
- **量化证据**：get_cycle_options 单次调用 = **241 次 settings.json 读盘**（241 个 DISTINCT 日期 × 1 次/日期），累计 **58.1ms，占其总耗时 78.6ms 的 74%**；query_with_stats 每次调用另有 4 次读盘（~1.5ms）。
- **影响面**：每次面板打开、每次手动刷新（_load_cycles_then_data）、导入完成后，worker 线程多付 60ms+；真实磁盘 + 杀软扫描环境下读盘单价更高。
- **兼容性**：tests/ 下 6 个文件均 monkeypatch `adb.load_cycle_mode`（注入函数绕过缓存），缓存方案与既有测试天然兼容；verify_aftersale_paging.py 走 save_cycle_mode（挂失效钩子即可）。

### N2【P0→P1】周期筛选走表达式过滤，索引全部失效，每次加载 3 条全表扫

- **现象**：带周期筛选的加载比"全部周期"更慢（反直觉反转）。
- **触发路径**：`aftersale_db.py:478 _RECORD_DATE_EXPR`（`substr(CASE WHEN occurred_at LIKE ... END,1,10)`）→ `_append_cycle_where():522` → query_page 的 COUNT(:583)/页 SELECT(:585) + query_with_stats 的统计聚合(:615)。
- **根因**：周期过滤作用于**表达式**，现有仅有的两个索引 `idx_aftersale_cycle(cycle_start,id)`、`idx_aftersale_table_no(table_no)` 均不可用；EXPLAIN QUERY PLAN 实测 `SCAN aftersale_records`。
- **量化证据**：query_with_stats(当前周期) **24.2ms**（COUNT 8.2 + 页 SELECT 7.6 + 统计 8.4，3 次全表扫）vs query_with_stats(全部周期) **11.6ms**；关键词 LIKE(8 列) 51.6ms（2 次全表扫，LIKE 前导通配符本就无法走索引）。
- **影响面**：SQLite 内存库 8ms/扫尚可，但**真实磁盘库与 MySQL 主库模式线性放大**（MySQL 100k 全表扫经验值为内存库的 3~10 倍，翻页/筛选/防抖搜索每次触发 3 扫）；这是 MySQL 模式下翻页延迟的主要来源之一。
- **注**：PERF_REVIEW #7（每次搜索都 COUNT）在售后侧"仍存在"，但已被 SQL 分页改造收窄为可接受项。

### N3【P1】表头点击排序 = 本地排序 + 全量重填充（每次 59.7ms）

- **触发路径**：`records.py:921 _on_click_header` → `_apply_sort`（60 行排序，本身 <1ms）→ `_populate`（重建 60 容器 + 139 按钮 + 720 item）。
- **量化证据**：D3 实测 **59.7ms/次**（含重绘）；填充构成见 N5。
- **影响面**：用户反复切换排序时每次点击约 60ms UI 线程卡顿 + 一代 deleteLater 僵尸（见 N6）。

### N4【P1】候选查询 94ms 全表扫 ×4，且触发频率远超必要

- **触发路径**：`aftersale_db.py:792 get_field_candidates`（4 条 GROUP BY 全表扫）← 三处高频触发：`entry.py:131-134 showEvent`（**每次**切到录入页）、`records.py:1010/1056`（**每次**打开新增/编辑弹窗都另起 cand_worker）。
- **量化证据**：单次 **94.2ms**（100k 内存库）；不卡 UI（worker 线程）但占 DB/连接，MySQL 模式下放大。
- **影响面**：切换页面/打开弹窗即触发 4 条全表聚合；数据未变时纯属重复劳动。

### N5【P1】填充成本 75% 在 ops 列 cellWidget（按钮列），720 个 item 仅占 4ms

- **触发路径**：`records.py:744 setCellWidget` + `records.py:763 _make_ops_cell`（60 行 × [已解决]+编辑+删除 ≈ 139 按钮 + 60 容器 + 60 QHBoxLayout）。
- **量化证据**（cProfile，60 行纯填充 ~28ms）：`setCellWidget` **13.0ms** + `_make_ops_cell` 构建 **7.8ms** ≈ **20.8ms（75%）**；`setItem`×720 仅 **1.2ms** + tooltip/flags ≈ 3ms；填充后重绘 ~16.6ms。填充后按钮实际存活 139 个/代。
- **影响面**：每次填充/排序/翻页都重建一代按钮。受功能约束（行内操作按钮必须保留，文档已定"不做删除"），进一步压缩只能走 delegate 自绘（见 S6，高成本）。
- **残余微项**：`cell.flags() & ~ItemIsEditable` 每格跨边界+枚举转换（720 次/页，PySide6 6.11 非 IntEnum 放大）；重要行 ops 容器 setStyleSheet 每行拼串。

### N6【P2】连续填充时 deleteLater 僵尸控件堆积（139 → 1112）

- **触发路径**：`setCellWidget` 替换旧 widget 走 deleteLater；processEvents 不消化 DeferredDelete，须真正的事件循环空转。
- **量化证据**：连续填充 7 次后按钮数 **1112（≈8 代并存）**；显式 `sendPostedEvents(None, QEvent.DeferredDelete)` 后回落 **139**；先清僵尸再填充 32.4ms（略快于 36.4ms）。
- **影响面**：快速连续操作（连点排序/快速翻页+筛选）期间瞬时多持有 ~1000 个控件对象（内存 + 遍历开销）；生产环境事件循环空转后自愈，非泄漏。

### N7【P2】pygwalker 首次 import 在主线程

- **触发路径**：`windows/stat_charts.py:67`（首次点击「统计图表」时 `import pygwalker`）。代码注释明确：后台线程 import 会与 Qt GUI 冲突卡死，故为主线程——已知权衡。
- **影响面**：首次点击主线程卡顿数秒（import 本身）+ to_html 数秒（已在后台线程）。**属"接受现状"项**，任何改法（预热/换线程）都有与 Qt 冲突的前科风险。

### N8【P2】`_on_loaded` 每次在 UI 线程读 settings.json ×2

- **触发路径**：`records.py:406 _update_source_label` → `_web_entry_url()`（:47，open+json.load）×2（setText 与 _web_link_html 各一次）。
- **量化证据**：**0.29ms/次**——微小，但每次加载都发生且在 UI 线程。

### R1【仍存在·低优先】PERF_REVIEW "后续可测项"：EditRecordDialog 实例复用未做

- 本轮实测 init 30.1ms（30+ 控件），频次低，复用有状态残留风险 → 维持 P2。

## 四、解决方案（按收益/成本比降序）

> 均不改业务语义：周期与统计口径、筛选条件、列含义、批量/一键解决行为、只读 Web 端对齐口径全部保持。

### S1【P0】load_cycle_mode 进程内缓存（收益/成本比最高）
- **改法**：aftersale_db.py 加模块级 `_cycle_mode_cache`；`load_cycle_mode` 命中即返回；`save_cycle_mode` 成功写盘后置空缓存（失效钩子）。get_cycle_options 的 241 次循环自然受益，无需改循环。
- **预期收益**：get_cycle_options **78.6 → ~20ms（-74%）**；query_with_stats 每次 -1.5ms；**首次加载 185 → ~115ms**。
- **成本**：~20 行；**风险**：低（测试均 monkeypatch 注入，绕过缓存，天然兼容；settings.json 被外部手改的极端场景与 backend 缓存同策略）。
- **回滚**：删缓存三行。

### S2【P0】表头排序免重填充
- **改法**：`_on_click_header` 改用 `self._table.sortItems(col, order)`（Qt 原生排序，cellWidget 随行移动），排序后按可视行序回读 item 数据重排 `self._rows`，保证行内按钮 lambda 捕获的 row 与 `_rows` 对应。
- **预期收益**：**59.7 → <10ms（-85%）**/次排序；同时消除一代僵尸按钮。
- **成本**：~30 行；**风险：中**——必须验证「按钮回调行号一致性」「勾选状态随行移动」「_rows 重排与 _checked_ids 对齐」；若回归不通过，退回方案 = 保留现实现（S5 落地后单次排序 ~50ms）。
- **回滚**：恢复 `_apply_sort + _populate` 两行调用。

### S3【P1】周期筛选索引化：物化 cycle_start 列（零 DDL）
- **改法**：
  1. 查询侧：`_append_cycle_where` 由表达式过滤改为 `WHERE cycle_start = ?`（周期起点字符串口径不变，两端索引 `idx_aftersale_cycle` 直接可用；SQLite 为 (cycle_start,id) 覆盖索引，MySQL 单列）。
  2. 一致性闭环（关键）：`save_cycle_mode` 保存成功后，后台 worker 全表重算 cycle_start（分批 SELECT id+两日期列 → cycle_start_of → executemany UPDATE；100k 估 1~3s，保存为极低频操作且不卡 UI）；insert_record 本就在维护该列（:342）。
  3. 一次性回填：对存量历史数据跑同一重算函数（Excel 导入的旧数据 cycle_start 用的是导入时配置）。
- **预期收益**：query_with_stats(周期) **24.2 → 3~6ms**（3 条 SQL 全部从全表扫变索引访问）；**MySQL 主库模式收益更大**（全表扫→索引，估计再省一半以上延迟）；翻页端到端 ~73 → ~55ms。
- **成本**：中（查询切换 ~10 行 + 重算函数 ~40 行 + 回填脚本 + 对照测试）；**风险：中**——cycle_start 与实际归属的偏差窗口 = 「改周期配置到重算完成之间」（后台重算窗口内新查询短暂按旧周期物化值过滤；重算完成后自动一致，需在 InfoBar 提示"周期重算中"）。语义上仍是"按当前周期配置归属"，只是物化 + 保存钩子保证一致，正面回应 aftersale_db 模块注释里"不依赖冗余落库字段"的顾虑。
- **回滚**：`_append_cycle_where` 切回表达式过滤（保留旧实现为开关）。
- **验证支撑**：tools/verify_aftersale_paging.py 已有「新实现 vs 旧实现」对照框架，扩展一档「cycle_start 列 vs 表达式」即可。

### S4【P1】get_field_candidates 缓存（写后失效）
- **改法**：aftersale_db 模块级缓存 + `insert_record/update_record/delete_record/mark_resolved_batch/delete_records/import_excel_rows` 尾部统一置脏；录入页 showEvent 与编辑弹窗打开直接吃缓存。
- **预期收益**：切页/开弹窗的 DB 侧 **-94.2ms/次**（worker 线程不卡 UI，但省 DB 与连接占用；MySQL 模式收益更大）。
- **成本**：~15 行；**风险**：低（多人协作场景他人新增候选最多延迟到本地下一次写操作后刷新——可再叠加 60s TTL 兜底）。
- **回滚**：删缓存。

### S5【P1】填充微优化组合（零视觉/功能变化）
- **改法**（records.py `_populate`）：
  a) 只读 flags 循环外预计算一次（`_FLAGS_RO = QTableWidgetItem().flags() & ~ItemIsEditable`），`cell.setFlags(_FLAGS_RO)` 替代每格 `flags()&~...`（720 次跨边界+枚举 → 1 次）；
  b) 填充开头 `QApplication.sendPostedEvents(None, QEvent.DeferredDelete)` 清上一代僵尸（实测 1112→139）；
  c) 重要行 ops 容器的 setStyleSheet 两种主题字符串预构建。
- **预期收益**：填充 **36 → ~30ms（-15~20%）**；连续操作期对象堆积消除。
- **成本**：~10 行；**风险**：低。
- **回滚**：逐条独立可回退。

### S6【P2·可选】ops 列按钮 delegate 自绘（仅当后续仍觉填充/滚动卡才立项）
- **改法**：QStyledItemDelegate 绘制按钮 + viewport mousePressEvent 命中分发，替换 cellWidget。
- **预期收益**：填充再 **-20ms（至 ~10ms）**，滚动重绘更轻。
- **成本/风险**：**高**——需复刻 hover/pressed 视觉、与右键菜单/双击/勾选列共存；hidden_performance_optimizations 已将"删操作列 cellWidget"列为不做（复用池 dangling 风险），自绘虽不删功能但重写整个交互层，回归面大。**当前 36ms/页不构成卡顿主诉，建议挂起。**

### S7【P2】`_web_entry_url`/`_update_source_label` 结果缓存
- 实例变量缓存链接文本，主题色变化（themeColorChanged）与设置变更时刷新；**收益 0.3ms/次**，顺手项。
