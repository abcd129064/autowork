# 企微 RPA 采集工具（rpa_wxcom_chat）可用性调研 2026-10-06

> 调研对象：[github.com/a605204746/rpa_wxcom_chat_public](https://github.com/a605204746/rpa_wxcom_chat_public)
> 起因：用户是售后群群主但**没有企微超级管理员权限**，需要在不接触管理后台的前提下自动归档群消息
> （承 [售后群消息归档可行性评估2026-10-05.md](售后群消息归档可行性评估2026-10-05.md)）。
> 结论全部基于**本机实测**（下载 + 解包 + 静态分析），未运行该程序、未联网激活、未登录任何企微账号。

- 本机 `curl.exe` 走 **schannel**，在沙箱下拿不到凭据：

## 2. 技术栈（解包后实测，非推测）

| 层 | 组件 |
| --- | --- |
| 打包 | **PyInstaller onedir**（`contents_directory=_res`）+ **Python 3.12** |
| 界面 | **pywebview**（WebView2）+ **React + antd**（`_res/frontend/dist/assets/index-*.js` 142 KB），前后端桥为 pywebview JS API：`Bt("<模块>").invoke("<方法>", {...})` |
| UI 自动化 | **pywinauto** + comtypes + pythonnet/clr_loader（.NET UIA）+ **pyautogui / pygetwindow / pyscreeze**（键鼠 / 窗口 / 截图）+ pywin32（`win32clipboard`、`win32gui`、`win32process`、`win32api` …） |
| OCR | **rapidocr_onnxruntime** + PaddleOCR PP-OCRv4 模型：`ch_PP-OCRv4_det_infer.onnx`(4,745,517 B)、`ch_PP-OCRv4_rec_infer.onnx`(10,857,958 B)、`ch_ppocr_mobile_v2.0_cls_infer.onnx`(585,532 B)；推理走 **onnxruntime**；图像走 **opencv**（`cv2.pyd` **86,293,504 B**）+ numpy + **shapely / pyclipper**（几何运算 → 文本框聚类成消息） |
| 存储 | **sqlcipher3**（加密 SQLite，`_sqlite3.cp312-win_amd64.pyd` 5,920,256 B）、openpyxl / xlsxwriter（Excel 导出） |
| 其他 | cryptography（Rust 绑定 `_rust.pyd` 9.9 MB）、httpx、loguru、Pillow、certifi |

体量对比印证 release note"增加了 OCR 相关的库导致包变大了"：**历史版 73 MB → v2.5 263 MB**（cv2 + onnxruntime + 三个 OCR 模型 ≈ 122 MB，是主要增量）。

### 2.1 后端主体不可静态还原

- 应用模块（按中文串筛出）只暴露了模块名：`backend.features.license.bridger`、`backend.core.secret.license`、`backend.core.secret.content_cipher`、`backend.core.secret.fingerprint`、`backend.features.wecom.bridger`。
- 真正的后端 `_res/backend.cp312-win_amd64.pyd`（581,120 B，Cython 编译）**2647 条 ASCII 字符串全是机器码碎片：0 条 URL、0 条 license 关键字、0 条中文**。字符串不可提取。
- 因此**授权服务器域名与"是否上传消息内容"无法从静态分析闭合**（见 §7）。

## 3. 采集机制（由前端文案 + 依赖还原）

前端内置的官方功能清单（四模块）：

| 模块 | 状态 | 官方描述 |
| --- | --- | --- |
| 历史采集 `history` | 可用 | "指定对象，翻页扫描历史记录 / 支持单个与批量模式 / 结果导出至 Excel" |
| 定时监控 `realtime` | 可用 | "设置采集对象与定时间隔 / 按计划自动触发监控 / 每次拉取最新消息入库" |
| Webhook 推送 `webhook` | 可用 | "采集消息直接推送，不入库 / 支持多个推送渠道 / 查看每次请求日志" |
| 在线文档下载 `docdl` | **开发中** | "企业微信在线文档批量下载…" |

实际工作流（文案原文）：

1. **框选企微左侧会话列表区域** → "通过 OCR 识别其中的联系人/群名称"（"正在截屏，请框选会话列表区域（左侧聊天列表）…"）；识别结果"可能存在误差，获取后请人工核查"。
2. **框选聊天消息区域坐标**："拖动框住企业微信的聊天消息区域"、"框选时只需覆盖消息列表部分，不要包含输入框区域"；坐标自动保存。
3. 逐对象切换 + **模拟滚轮向上翻页**，参数："单次滚动量（建议 100）"、"翻页间隔（建议 0.5 秒）"、"每批翻页次"。
4. **停止阈值**："连续多少批内容未变化时认为已到顶"；会话列表扫描"连续 2 轮内容相同自动停止"。
5. 落加密库 / 导出 Excel / webhook 推送（图片以 Base64 内联，"体积较大，须放开限制"）。

**目标匹配按"群名"而非 ID**：文案明确"导航失败跳过：群名不完全匹配，请检查名称是否与企业微信侧边栏一致"——与 [售后群消息归档可行性评估2026-10-05.md](售后群消息归档可行性评估2026-10-05.md) 里 `query_rank` 按 `room_name` 分组的坑是**同一类型**：改名即漏采、重名即错采。

## 4. 可用性判定

### 4.1 满足用户约束的部分（正面）

- **不需要企微超管/管理员权限** —— 纯客户端 UI 自动化，走"人已经登录并在看的那个窗口"（README 自述："模拟人工操作企业微信客户端…就像你自己在企微窗口里选中消息、按 Ctrl+C 复制、再粘贴到文档里"；"我们不破解企业微信，不逆向协议"）。
- **不需要开启会话存档**，因此**完全绕开**上一份文档里的全部后台前置：确认函审核、RSA 公钥、授权范围、可信 IP 白名单、企业认证、分级管理员。
- **没有 5 天窗口限制** —— 只要消息还在客户端本地历史里就能往上翻（上一份文档的"每等一天永久少一天数据"在这条路线上不成立）。
- 采集次数不限（受限的是**查看与明文导出**，见下）。

### 4.2 硬性缺点

#### 4.2.1 授权绑定 + 数据主权（最严重，与"归档"本质冲突）

| 实测文案 | 含义 |
| --- | --- |
| "授权绑定当前机器硬件，更换电脑需重新申请" | 授权 = **本机硬件指纹**级绑定 |
| "激活授权需要联网校验，请连接网络后再试。" / "网络不可用，无法校验授权，请联网后重试" | **激活与校验都要联网**，作者侧有校验服务 |
| "前 200 条消息可在应用内查看 · 导出数据需激活 Pro 授权后方可明文导出" | 试用期 **200 条**；**明文导出要 Pro** |
| "已采集的数据已安全加密存储，激活 Pro 后…" / "授权期内采集的数据（EC1 加密）重新激活后…" | 落库是 **EC1 加密**，解密能力随授权走 |
| "配置文件缺失或损坏，请重新激活以恢复服务" / "您的 Pro 授权已过期，已自动切换为试用模式" / "授权已重置，请重新激活" | 作者侧可**重置/失效**你的授权 |

**结论**：归档的可读性 = 作者的授权服务器 + 这一台机器 + 授权码三者同时存活。作者停服、跑路、你换机、你重装——**历史归档变砖**。这与"归档"要的长期可读、可移交，是直接冲突的。

（另：试用 200 条可通过"清空全部数据"重置，但清空会删掉已采数据，绕不过"明文导出需 Pro"。）

#### 4.2.2 合规与封号风险（风险落在真实业务账号上）

- **企微官方 2024-06-12《关于持续严厉打击"外挂"行为的公告》**原文：未经授权实施外挂行为，包括"账号多开、规避企业微信对消息群发次数的限制，以及**通过机器人流程自动化模拟用户手动操作**等功能"；并称对开发/提供外挂者"采取包括**诉讼**在内的一切手段"。→ 本工具的核心机制被**点名**。
- 企微《用户外挂自查指南》分类第 4 类："**使用非官方功能获取、监控、保存账号或企业数据**…监控聊天记录、文件等数据内容" → 与本工具用途**完全重合**。
- 封号实证：`wechaty/wechaty` issue #2762"被判定为外挂软件，导致企业微信**永久被封（7 个账号）**"。
- 风险主体是**售后群那个真实业务账号**（含客户联系方式与全部会话），不是测试账号。

#### 4.2.3 独占桌面（运维成本被低估）

采集期间工具接管鼠标/键盘并持续截屏；文案反复强调："**企业微信保持最大化**"、"**不要将企业微信最小化到任务栏或托盘**"、"使用前请务必将…再切换到本工具操作"、"避免操作错乱"、release note v2.2 同义。

→ 需要**一台专机**或非工作时段，不能与日常办公复用；截图区域坐标在窗口尺寸变化后要重新框选（"首次使用或调整了企业微信窗口大小后，需要重新框选聊天区域"）。

#### 4.2.4 精度与稳定性

- 官方自述 OCR"识别可能存在误差，获取后请人工核查"；v2.5 release note 仍在修"OCR 有时候获取不对"。
- release notes 里大量 闪退 / 假死 / 黑屏 / 图片采集丢失 修复（v1.6、v1.7、v2.3）。
- 依赖企微客户端 UI：**企微一更新，UI 自动化就可能整体失效**，而作者是**个人开发者**、最后推送 2026-08-29（截至调研约 5 周未更新）。

#### 4.2.5 供应链

无 LICENSE（不可再分发/集成）；单人维护；血统是**微信个人号**工具改名（早期包名 `wx_rpa_chat-win-amd64.rar`）；README 留个人微信做"企业定制或技术支持"（客服与授权都走微信人工通道）。

## 5. 与现有归档设计的关系

上一份文档的结论是"把采集层改为**来源可插拔**：统一入站契约 `ChatMessage{source,msg_id,room_id,sender_id,msg_ts,msg_type,content}`，A（存档 SDK）/ C2（人工导入）/ C3（OCR）是三个可替换适配器"。

本工具**正好就是 C3 那个适配器的现成实现**，可直接以 `source="rpa"` 接入，下游 存储 → 打标 → 报告 **零分支改动**。

但必须钉住两条：

1. **它是适配器，不是主干**。它是"绕过"权限，不是"获得"权限；同时它引入了两个上一份文档里没有的新失败点：**作者授权服务器** 与 **企微客户端 UI 版本**。
2. **不要给它写入主库的权限**。上一份文档已列出的放行条件（鉴权 fail-closed、Web 账号无原表 SELECT、保留期落地且 `chat_archive_cursor` 豁免清理、报告页展示"已同意客户覆盖率"）对它同样适用，且更严——因为它的数据来源本身不可审计。

## 6. 建议

**若确认要自动化补历史（推荐做法）**：

- 定位为**一次性补历史**，**不做常驻定时任务**（定时监控模块不要开）。
- 用**一台不承载重要账号的一次性环境**（备用机 / 虚拟机），该环境只登录这一个企微账号，把封号爆炸半径限制住。
- 采完**立即导出 Excel** 落到仓库侧（`tools/_scratch/` 或正式归档路径），随后**立即卸载**该工具。
- 授权按最短周期买，**不要**让长期归档依赖它的解密能力。
- 全程不要在生产机上跑，不要与 `web/aftersale_api` 同机。

**若不能接受上述风险**：

- 回退到上一份文档的 **C2 人工导出**；或
- 推动 **"办法一"**（让超管点 4 个后台开关），那仍是唯一合规主干。
