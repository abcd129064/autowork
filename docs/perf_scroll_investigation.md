# 滚动性能系统性调研（2026-09-07）

调研范围：全项目表格与上下滚动列表，重点为售后面板（`windows/aftersale/records.py`）。
结论全部基于实测，测量脚本 `tools/perf/scroll_profile.py`（可复跑）。

## 一、测量方法

- 环境：PySide6 6.11.2 + qfluentwidgets，`QT_QPA_PLATFORM=offscreen`，托管 venv。
- 样本：`database/tables.db` 中 197 条真实 `aftersale_records`，复制到 60 行/页（线上页大小）。
- 指标：**每帧滚动耗时** = 逐步 `verticalScrollBar().setValue()` + 同步 `viewport().repaint()`，取多轮中位数。
- 对照方式：**配对对照**——每个变体前后各测一次基线，抵消控件堆积导致的系统性漂移。
- 两个已踩并修正的坑（避免后续复现）：
  1. 页面不 `show()` 时 `repaint()` 被 Qt 直接跳过，耗时恒为 ~0.01ms，viewport 高度为 0。
  2. `show()` 会触发 `showEvent → recalc + 周期 + 数据` 三条 worker 链直连远程 MySQL，
     实测 1.2s 内 172 次 pymysql 收包、0.22s 网络等待，会把 DB 耗时算进滚动耗时。
     已通过预置 `_cycles_loaded/_recalc_done` 隔离。

## 三、售后面板卡顿根因结论

**不是懒加载，也不是虚拟滚动不足。** 决定性证据：行数 60→15，耗时变化 +0.1%（噪声内）。
Qt/QTableWidget 本来就只绘制可见行，数据也已在内存中，滚动过程中没有任何"按需加载内容"的动作。

逐条排除：

| 假设 | 结论 | 证据 |
|---|---|---|
| 滚动时懒加载/动态渲染内容 | **不成立** | 无懒加载代码；行数对耗时零影响 |
| 虚拟滚动不足 | **不成立** | rows 60→15 = +0.1% |
| 行内 cellWidget 过多 | 次要，仅 7.7% | no_ops_widget -7.7%（历史上被当成主因优化过，实测不是） |
| 每格 tooltip | 无影响 | -0.2% |
| 交替行色 | 无影响 | -0.3% |
| 文本高亮/样式重计算 | 部分成立 | 见下 |
| **每帧单元格委托绘制** | **主因** | 文本绘制占 67.6%，qfw delegate 占 51.1% |

主因拆解（每帧 12.6ms 的构成）：

- **文本排版 ≈ 8.6ms（68%）**：每格走 `QStyledItemDelegate::paint → QTextLayout + 省略号计算`。
  这是**每格固定开销**，即使文本只有 5 个字符也要付（244 格 × ~34µs）。
- **qfw delegate Python 壳 ≈ 6.5ms（51%）**：`TableItemDelegate.paint` 每格执行
  `save/restore + setClipRect + 抗锯齿 renderHint + 圆角矩形背景 + initStyleOption`
  （含 `getFont()`、`isDarkTheme()`、多次 `index.data()`）。
- 文本**更长**会线性放大：400 字时 +44.5%。
  但 `ElideNone` 反而更慢（+57.8%）→ 说明瓶颈是 QTextLayout 排版本身，不是省略号截断。

关于"大量文本"：当前生产数据 **197 条，problem 中位 5 字符 / 最大 17，整行 8 字段中位 43 字符**，
文本量并不大。所以长文本是**弹性风险**（数据变长后会明显恶化），不是当前卡顿的直接主因。

## 四、延迟（非滚动）部分

MySQL 为**远程**（49.235.34.253:3306），`SELECT 1` RTT 6.0ms。

| 环节 | 中位 | 冷启 max |
|---|---:|---:|
| recalc_cycle_starts_on_load | 5.7ms | 200.5ms |
| get_cycle_options | 6.0ms | 9.2ms |
| query_with_stats(1,60) | 17.7ms | 22.8ms |
| **_populate(60 行 × 13 列)** | **51.6ms** | 53.1ms |

- 首次打开面板 ≈ 250~300ms（三段串行 worker + 冷建连 + 填充）。
- 每次筛选/翻页 ≈ 17.7ms 查询 + 51.6ms 填充 ≈ **70ms**，叠加 300ms 搜索防抖，构成"明显延迟"体感。
- `_populate` 51.6ms 中，操作列 60 个容器 + ~150 个 QPushButton 的构造是大头。

## 五、预加载 / 预渲染可行性与取舍

| 方案 | 可行性 | 实测 | 取舍 |
|---|---|---|---|
| **预加载更多行/提前建 item** | ❌ 无效 | 行数 60→15 耗时 +0.1% | 没有懒加载可优化；数据已在内存，多建行只增加填充耗时 |
| **预渲染（绘制缓存 blit）** | ✅ 有效 | **-66.4%**（12.3→4.1ms） | 收益接近"完全不画文本"的地板(3.95ms)。代价：每格一张 QPixmap（244 格约数 MB）、需处理列宽/主题/选中/悬停的缓存失效，维护成本中等 |
| **换轻量 delegate** | ✅ 推荐 | **-51.1%**（12.3→6.0ms） | 几乎零运行时代价、无缓存失效问题，维护成本最低，**应作为首选** |
| **减少列数** | ✅ 有效 | **-45%** | 需产品确认列显隐方案；可与 delegate 优化叠加 |
| 数据层预截断长文本 | ✅ 低成本 | 消除 +44.5% 风险 | 截断后 tooltip 保留全文，视觉无损 |

结论：**"预加载"方向是错的（不存在懒加载），"预渲染"方向对但非首选**——
先把 delegate 与列数这两项低成本优化做完，若仍不达标再叠加绘制缓存。

## 六、按优先级的可落地步骤

| 优先级 | 动作 | 预期收益 | 改动范围与风险 |
|---|---|---|---|
| **P0-1** | 自研 `LeanTableDelegate` 替换 qfw `TableItemDelegate`：沿用 qfw 的背景/圆角/勾选框绘制（视觉不变），仅把文本绘制从 `super().paint`（QTextLayout）换成 `painter.drawText` + 逐行 elide 缓存 + 缓存 QFont | **实测 -49.4%**（11.87 → 6.01 ms/帧） | 单点替换，全局表格受益；视觉差异 5.2%（纯文本微排版），见第八节 |
| **P0-2** | 降低每帧单元格数：售后 13 列合并（时间合并 + 问题/原因合并 → 9 列，方案 C） | 实测 **-18%**（激进 8 列方案 -22%） | 需业务拍板列方案；设计稿见 `design/aftersale_columns_v2.html`。注意收益**非线性**（见下） |
| **P1-1** | 数据层预截断 problem/cause/solution（如 24 字符），tooltip 保留全文 | 消除长文本 +44.5% 恶化风险 | `_populate` 内加一行，风险极低 |
| **P1-2** | 操作列 cellWidget 瘦身：改为 1 个「⋯」按钮 + 右键菜单，或仅对悬停行惰性创建 | `_populate` 51.6ms 显著下降 | 交互形态变化需确认；改后滚动再降 ~7.7% |
| **P2-1** | 绘制缓存（QPixmapCache，行级而非格级以省内存） | 再降至 ~4.1ms/帧 | 仅在 P0/P1 后仍卡顿时引入；需处理失效 |
| **P2-2** | 加载链：recalc（冷启 200ms）挪到首屏渲染后的空闲片执行，先出数据再补周期列 | 首开 250~300ms → ~80ms | 需保证周期筛选口径，改动小 |
| **P3** | 全局推广：run_video(11 列) / management 三页(7 列) / remote 系列共用同一 delegate | 全项目一致受益 | 换 delegate 后自动生效，只需回归验证 |

**明确不做**（有数据支撑的反优化）：

- `ScrollPerPixel`（-0.7%，历史上已判定为反优化）
- 关闭抗锯齿 / 去掉圆角背景（实测反而 +12%/+7.7%，本环境呈反向，需真机复核但不建议做）
- 减少每页行数 60→更少（0% 收益，只增加翻页次数）
- 预加载更多行 / 提前建 item（0% 收益）

## 六之二、P0-2 列合并实测（tools/perf/column_merge_probe.py）

列数减少 → 每帧绘制的单元格数减少，但合并后每格文本变长，而文本绘制成本与字符数
正相关（长文本实测 +44.5%），两者部分抵消。用真实数据实测各方案净收益（配对对照）：

| 方案 | 列数 | 相对现状 |
|---|---:|---:|
| 现状 | 13 | 基准（10.4 ms/帧） |
| A 三否列合并为「判定」 | 11 | **-3%** |
| B A + 填写/发生时间合并 | 10 | -9% |
| **C B + 问题/原因合并（推荐）** | 9 | **-18%** |
| D C + 类型并入位置 | 8 | -22% |
| 对照：只删三否列不合并 | 10 | -12.5% |
| 对照：只删类型 + 发生时间 | 9 | -20% |

结论：

- **收益远低于按列数线性外推**（13→8 只拿 -22%，而非 -38%），因为合并拉长了每格文本。
- **窄的三否列（70px × 3）不值得合并**：每格仅 1 字符，合并后反而变 3~7 字符，
  只有 -3%；整组删除反而拿 -12.5%。
- 同列数下**纯删略优于合并**（-20% vs -18%，差 2~3pp），故应优先按信息价值决定删/留，
  性能只用来在等价方案间取舍。
- 设计稿（列结构、示例行、取舍、实现影响面）：`design/aftersale_columns_v2.html`。

## 七、P0-1 视觉影响专项验证（tools/perf/delegate_visual_check.py）

三种 delegate 对同一份真实数据、同一状态（第 4 行选中 / 第 5 行勾选 / 第 2 行 hover / 滚动 3 行）
抓取表格视口位图，白底合成后做像素级差异统计：

| 对照 | 显著差异像素占比 | 结论 |
|---|---:|---|
| baseline vs **lean（P0-1 原型）** | **5.2%** | 全部结构性视觉一致：交替行背景、hover、选中背景、左侧选中指示条、自绘勾选框（含勾选态）、语义色徽章、行高、操作列按钮位置全部不变；差异仅剩文本微排版（断行点/字符亚像素位置） |
| baseline vs **plain（直接换原生 delegate）** | **22.0%** | 外观明显变化：丢 hover/圆角/自绘勾选框/选中样式，**不可直接采用** |

原型开发中实测的三个回归点（正式实现必须处理，均已在此验证修复）：

1. `ForegroundRole` 返回的是 **QBrush 不是 QColor**，`QColor(brush)` 直接抛
   `QVariant must be holding a QColor`，需 `brush.color()` 转换。
2. item 文本含 `\n`（如「时间\n填写人」两行），drawText 的 flags 必须带
   `Qt.TextFlag.TextWordWrap`，且 elide 要**逐行**做，否则两行布局被压成单行。
3. 文本左内边距必须对齐 native 的 `SE_ItemViewItemText`（实测格左 15px），
   用 4px 会让整行文本左移 13px。

验证方法学坑：视口抓图未绘制区域是**透明**的，浅色主题黑字压在透明底上，
仅比 RGB 通道会得出「0 差异」的假结论——必须先合成到白底再比对。
另外 offscreen 环境缺 CJK 字体，文本渲染为方框，上述占比为保守近似，
最终需真机肉眼验收。

性能结论（修复后复测，rounds=3）：lean 6.01ms vs 配对基线 11.87ms = **-49.4%**，
与 plain（-52.6%）几乎持平但外观保留；叠加 cache_paint（-67.2%）仍可作为二期。
