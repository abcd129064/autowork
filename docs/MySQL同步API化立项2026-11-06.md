## 1. 关键架构事实（决定步骤划分）

当前**没有独立的 push/pull 同步引擎**：

- `database/backend.py:95-299` 是 SQL 方言适配层（`convert_placeholders` /
  `convert_on_conflict` / `convert_insert_or_replace` /
  `MysqlConnectionAdapter`）——客户端业务层写 SQLite 方言 SQL，
  透明地在 MySQL 上重放；
- 同步水位与冲突语义散落各处：`database/table_db.py:593`（`_upsert_sync_meta`）、
  `database/table_db.py:1453`（`upsert_kd`）、`database/mysql_sync_card_logic.py`、
  `database/aftersale_cycle.py` 等。

推论：**「把连接包一层 HTTP-SQL 透传」的捷径不安全**（客户端拼好的 SQL 发给
服务端执行 = 注入面搬家）。必须先把同步语义显式化为服务端契约，再逐表
替换传输层——这就是六步的由来。

## 4. 前置风险（立项评审必答）

1. **性能数量级变化**：`query_page` 本地 0.14ms → RTT 级（50~150ms）。
   列表/排名页必须改批量拉取 + 本地缓存——单列性能验证轮。
2. **断网现场录入**：无网现场写本地 SQLite 的能力必须保留，补推走水位化
   API；多端冲突在服务端正确裁决（契约 #2）。
3. **过渡期衔接**：步骤 3 完成前客户端仍直连 MySQL，家里访问问题由
   frp 隧道先行解决（混合路线），API 化不承担止血职责。
4. **服务端单点**：`aftersale-web.service`（`app.py`）承载新 `/api/sync/`，
   评估独立 systemd unit 与重启策略，避免与老系统同进程互相拖累。

## 11. 步骤 5：8 表统一策略框架 + 统一上生产（2026-11-19）

### 11.1 本轮定夺与生产侦察结论

用户指令「全部跑通后上生产」→ 先把剩余 6 张表在**本地**全部跑通，再统一部署；
frp 全程跳过，无因 frp 依赖暂停的步骤。本地 8 表能力实现完毕后，部署前做了
一轮只读侦察，结论直接改变了部署形态：

| 侦察项 | 结果 |
| --- | --- |
| 生产库 | `autowork`（`SHOW DATABASES` 只有它 + 系统库） |
| Web 后端 DB 用户 | `aftersale_ro@127.0.0.1`，仅授权 `aftersale_audit_log` / `aftersale_records` / `aftersale_user_prefs` / `billiard_tables` |
| 目标 8 表 | **只有 `aftersale_records`(~1117 行) / `billiard_tables`(~1269 行) 存在**，两表列齐全 |
| 其余 6 表 + `sync_meta` | `information_schema` 全库查无；`SELECT` 报 1142（权限检查先于存在性） |
| 生产库业务表全集 | 仅 4 张：`aftersale_audit_log` / `aftersale_records` / `aftersale_user_prefs` / `billiard_tables` |

**结论：这 6 张表在生产 MySQL 里从未建立，其权威数据源归属尚未定论**（桌面端
双后端是 MySQL 主 + SQLite 兜底，但这些表可能只在本地 SQLite）。因此：

1. 不擅自做生产 DDL / GRANT —— 建空表也没有数据，且属高风险生产变更；
2. 不把「代码支持 8 表」当成「生产已开通 8 表」对外宣称 —— 否则 6 个 query
   端点会 500，等于契约撒谎；
3. 采用**环境变量显式收窄**：代码保留 8 表能力，生产 `.env` 写
   `SYNC_AVAILABLE_TABLES=aftersale_records,billiard_tables`，契约 / health /
   端点同步裁剪；未开通表返回 **409 而非 500**；补表后改配置重启即放开，代码不动。

### 11.2 8 表统一策略框架（`sync_core.TABLE_SPECS` 单一事实源）

| 表 | strategy | 业务键 | 排序列 / 并列键 | 说明 |
| --- | --- | --- | --- | --- |
| `aftersale_records` | lww | created_at + creator + table_no + problem | updated_at / id | 软删除墓碑需下发 |
| `ledger_records` | lww | created_at + signer + category + kind + video_name | updated_at / id | 无 deleted 列 |
| `device_mapping` | lww | device_code | updated_at / device_code | 字符串并列键 |
| `health_alerts` | overwrite | name | updated_at / name | 无时间戳裁决，按名覆盖 |
| `billiard_tables` | overwrite | id | id / id | 快照表 |
| `xqzg_status` | overwrite | id | id / id | 快照表 |
| `submission_log` | append | id | id / id | `INSERT IGNORE` 只补新增 |
| `kd_status` | upsert_kd | file_path + device_code | id / id | 行级 upsert，**不 DELETE 整日** |

关键护栏：

- `effective_cols(table)`：`id` 不是业务键时（仅 `kd_status`）由服务端自增，
  禁止客户端写入或 UPDATE 改写，避免撞主键 / 串改无关行；其余 3 张运维表的
  `id` 本身是业务主键，必须随行同步。
- `build_upsert_sql()` 绝不生成 `DELETE` / 整表替换；3 个清库入口与
  `sync_health_alerts` 整表替换语义**刻意不暴露端点**，契约标
  `destructive_full_replace: not_exposed`。
- `upsert_kd_clear_same_day` 标 `pending`（SaveKd 清同日语义未实现），另立
  `kd_row_upsert: supported_no_delete`，不把两者混为一项宣称。
- `decode_cursor_for()` 对数值并列键转 `int`，避免字典序 `'10' < '9'` 漏行；
  字符串并列键（device_code / name）保持原值。

### 11.3 三层改动

- 服务端 `web/aftersale_api/sync_core.py`：`TABLE_SPECS` 8 表，新增
  `effective_cols` / `build_query_sql(table, ...)` / `decode_cursor_for` /
  `encode_cursor_for` / `available_tables`；`normalize_upsert_rows` 与
  `build_upsert_sql` 全部按表走。
- 服务端 `web/aftersale_api/sync_api.py`：query 改用 core 生成 SQL；upsert 按
  `strategy` 四分支（lww / overwrite / append / upsert_kd），列下标只认
  `sql["cols"]` / `sql["update_cols"]`，不再与 core 各算一份；health / contract
  按 `available_tables()` 裁剪并附 `provisioning`；未开通表 409。
- 客户端 `database/sync_service.py`：`TABLE_SPECS` 扩到 8 表并带 `strategy`；
  非 lww 表不再拼 `SELECT updated_at`（运维表无该列会直接报错）；append 已存在
  即 skip、overwrite / upsert_kd 命中即覆盖但**绝不删其他行**；
  `check_contract()` 返回的 `tables` 不含目标表时直接拒绝拉取。
