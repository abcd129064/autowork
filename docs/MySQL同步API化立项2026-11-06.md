## 1. 关键架构事实（决定步骤划分）

当前**没有独立的 push/pull 同步引擎**：

- `database/backend.py:95-299` 是 SQL 方言适配层（`convert_placeholders` /
  `convert_on_conflict` / `convert_insert_or_replace` /
  `MysqlConnectionAdapter`）——客户端业务层写 SQLite 方言 SQL，
  透明地在 MySQL 上重放；
- 同步水位与冲突语义散落各处：`database/table_db.py:593`（`_upsert_sync_meta`）、
  `database/table_db.py:1453`（`upsert_kd`）、`database/mysql_sync_card_logic.py`、
  `database/aftersale_cycle.py` 等。

推论：**「把连接包一层 HTTP-SQL 透传」的捷径不安全**（客户端拼好的 SQL 发给
服务端执行 = 注入面搬家）。必须先把同步语义显式化为服务端契约，再逐表
替换传输层——这就是六步的由来。

## 3. 语义契约清单（迁移时必须逐条保留，验收对照表）

| # | 语义 | 现状出处 | 契约要求 |
| --- | --- | --- | --- |
| 1 | **UpsertKd 清同日其他设备记录** | `database/table_db.py:1453`（姊妹仓 WinUI 侧 `UpsertKdAsync` 同口径） | 带 keyword 部分拉取必须走 upsert_kd 语义，清同日其他设备记录的行为在服务端**逐条复刻**——历史验收铁律，不得静默变更 |
| 2 | LWW 最后写入胜 | `database/mysql_sync_card_logic.py`、`fallback_backup.py`、`merge_back.py` | 多端冲突裁决搬到服务端；冲突用例在步骤 2 全部写全，不留实现期模糊 |
| 3 | sync_meta 水位 | `database/table_db.py:593` `_upsert_sync_meta` | MySQL 侧 INSERT OR REPLACE 会变普通 INSERT 必 1062 —— 单行 upsert 的服务端实现必须用等效 `_upsert_sync_meta` 口径 |
| 4 | 同步 0 条必须界面提示 | 清库入口三处 | 整表替换类操作返回 0 行时客户端必须给用户可见提示，不得静默 |
| 5 | query_page 夹 1~500 | `database/table_db.py:751`、`aftersale_db.py:542`、`ledger_db.py:221` | API 分页参数夹逼口径一致 |
| 6 | 导出走不分页独立方法 | 导出链路 | 防止 API 化后列表端点被 500 行夹逼截断导出 |
| 7 | DB worker 竞态守卫 | 查询/写槽分离 + `_query_seq` 代数守卫 | API 化后 worker 侧守卫保留，传输层无并发语义变化 |
| 8 | 降级链路 | `database/backend.py:472-532`（mark_degraded/mark_online） | API 不可用 → 本地 SQLite 透明回退 + 恢复合并，语义与 MySQL 降级同构 |
| 9 | 软删除 deleted=1 / 运维表无 NOT NULL | `database/schema.py` | 服务端 schema 权威化时保持 MySQL DDL 既有约定（显式 utf8mb4、TEXT 无 DEFAULT 等） |

## 4. 前置风险（立项评审必答）

1. **性能数量级变化**：`query_page` 本地 0.14ms → RTT 级（50~150ms）。
   列表/排名页必须改批量拉取 + 本地缓存——单列性能验证轮。
2. **断网现场录入**：无网现场写本地 SQLite 的能力必须保留，补推走水位化
   API；多端冲突在服务端正确裁决（契约 #2）。
3. **过渡期衔接**：步骤 3 完成前客户端仍直连 MySQL，家里访问问题由
   frp 隧道先行解决（混合路线），API 化不承担止血职责。
4. **服务端单点**：`aftersale-web.service`（`app.py`）承载新 `/api/sync/`，
   评估独立 systemd unit 与重启策略，避免与老系统同进程互相拖累。
