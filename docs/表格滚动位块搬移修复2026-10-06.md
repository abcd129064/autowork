# 表格滚动「位块搬移」修复（2026-10-06）

> 状态：**第三轮（取色源修正）已落地**（2026-10-06，默认开）。
> 演进：① 第一版只设 `WA_OpaquePaintEvent` 不画底 → 真机整片叠影；
> ② 第二轮补「画满 viewport」，但底色取自**渲染父级**→ 真机色不对
> （暗色主题填成纯黑、浅色填成灰白，因为父级背景本身透明，渲染父级只能拿到
> palette 色）；③ **本版改为抓屏幕真实像素**，多点一致才采信。
> 验收口径：**像素等价**（`tests/test_table_blit_patch.py` 10 例，含反证与取色可信度用例）。
> 测量工具：tools/perf/perf_scroll_latency.py --truth [--blit on|off]。

## 〇、TL;DR

1. 之前所有表格滚动数字（ms/步）都被怀疑过「是不是 harness 强制整视口重绘造出来的」——
   **本轮证实：对 qfluentwidgets 的表格，整视口重绘就是真机行为**，数字有效，但**机制归因错了**。
2. 真因是**两条各自独立的「位块搬移阻断」**，任何一条单独存在，Qt 就会放弃
   QWidget::scroll() 的位块搬移、改为整视口重绘：
   - **阻断 A（样式化背景）**：TableBase.__init__ 给表格挂 QSS（FluentStyleSheet.TABLE_VIEW），
     QStyleSheetStyle 因此把表格与 viewport 的 WA_OpaquePaintEvent 置 False；
   - **阻断 B（悬浮滚动条压住 viewport）**：库自绘的 SmoothScrollBar 是**表格子控件**，
     竖条压在 viewport 右缘、横条压在下缘。
3. 修复 = 两个条件同时满足：viewport 重设 WA_OpaquePaintEvent=True + 给 viewport 预留
   悬浮滚动条条带（并在每次重布局后重新预留）。
4. 实测（管理面板球桌页 60 行 × 13 列，1600x900 @ scale 1.0，offscreen）：
   **绘制面积 1,173,120 → 1,547 px²/步（1/758）**，
   **每步 10.01 → 1.28 ms**（响应 0.38 + 光栅 9.56 → 响应 0.30 + 光栅 0.98）。
5. **第二轮（本版）补齐了第一版缺的那一半**：先画满再开不透明。取色方式是
   **实测**——渲染表格父级 1×1 像素拿「背后的实底颜色」（不写死主题色，避免主题/
   宿主差异），取不到全不透明色就**不开启**。验收 = 开关前后逐像素比对：主体区
   必须逐字节一致（第一版那种叠影会在这里全线飘红）。键名 `perf_table_scroll_blit_v2`，
   默认开，UI 有开关可即时回退。
   之后再决定是否改默认（改动点只有 `is_table_blit_enabled()` 里的一行）。

## 一、先修测量口径：--truth 自然路径

tools/perf/perf_scroll_latency.py 历史口径是「每步 setValue() + **同步 viewport().repaint()**」，
等于把整视口全量光栅当成每步成本。本轮新增 --truth：**只 setValue()**，用「事件 → 画面静默」
等待（_drain_until_idle），并统计每步绘制面积。两个关键实现坑（都已修）：

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| paint 开始时刻 ≠ 结束时刻 | 事件过滤器只能拿到「事件送达」时刻，paint 在 processEvents 内部同步执行；只用「送达 + 空闲」当步耗时会把整段光栅漏掉，实测出现「整视口重绘却 0.36 ms/步」的假象 | 记录承载 paint 的那次 processEvents 切片耗时（raster_ms），步耗时 = 响应 + 光栅 |
| 强制 repaint 混入 | --truth 期间任何 repaint() 都会把整视口光栅塞回测量 | 自然路径只 setValue()；repaint() 只出现在 _prep_scroll 复位里 |

新增 --blit on|off：A/B 对比位块搬移修复（只改内存开关，不写 config/）。

## 二、根因证据链（全部为 offscreen 实测，探针在 tools/_scratch/）

| # | 实验 | 结果 |
| --- | --- | --- |
| 1 | 裸 QTableWidget 滚动一步 | **条带重绘**：1556×30 px，0.034 视口当量/步 |
| 2 | 同表 + 任意命中表格的 QSS（哪怕只有 QTableView{background:transparent}） | **整视口重绘**（1.000 视口当量/步）；不命中任何控件的 QSS 无影响 |
| 3 | 同表 + viewport().setAttribute(WA_OpaquePaintEvent, True) | **恢复条带重绘** |
| 4 | qfw TableWidget（真机形态） | 整视口重绘 1560×752 px（1.000 视口当量/步） |
| 5 | 仅设 opaque 属性（悬浮滚动条仍压住 viewport 右缘 12px） | **仍然整视口重绘** |
| 6 | 把悬浮滚动条移开 400px（仍可见）/ 隐藏 | **恢复条带重绘** |
| 7 | 悬浮滚动条 reparent 到页面（视觉上仍压住） | 仍整视口重绘 → 阻断判据是**几何重叠**，不是父子关系 |
| 8 | opaque 属性 + 右侧预留 13px 条带 | **恢复条带重绘（1547×1 px）**，换页/改列宽/resize 后保持 |

结论：**A、B 两条都得解**。只解 A（属性）在同表上无效，只解 B（移开滚动条）在真机形态下也无效。

另有一条重要副作用事实：QStyleSheetStyle::polish 会把 WA_OpaquePaintEvent 置 False，
所以**任何一次 QSS 变更都会再次清掉该属性**——修复必须挂在「每次重布局之后」，
不能只在构造时设一次。

## 三、修复实现

core/perf.py：

| 函数 | 作用 |
| --- | --- |
| patch_table_scroll_blit() | 幂等挂载：包一层 TableBase.__init__（首帧应用）+ 包一层 QTableView.updateGeometries（每次重布局后重新预留条带，因为 QTableView::updateGeometries 会重算 viewport margins 把手工值清掉） |
| apply_table_blit(table) | 单个表格应用两个条件：viewport().setAttribute(WA_OpaquePaintEvent) + setViewportMargins(左/上不变, 右/下 = 滚动条宽度+1)，并同步收窄 horizontalHeader / 收短 verticalHeader（表头由 updateGeometries 先按旧 viewport 摆位，不收会钻到悬浮条下面） |
| _blit_strip_width(table, orient) | 该方向「可滚动（maximum() > minimum()）且存在 qfw 悬浮条」才留条带；不可滚动 → 0（不留白）。构造期未布局时条尺寸会退化成异常值，夹到 12px |
| is_table_blit_enabled() / set_table_blit_enabled() | 开关，perf 域 perf_table_scroll_blit，默认开；切换即时生效（apply_table_blit_globally() 遍历所有表格） |

挂载与入口：

- main.py：patch_table_scroll_blit()（紧随 patch_lean_table_delegate()）。
- 主面板「性能选项」对话框新增「表格滚动加速」开关（main_window/ui_mixin.py）。
- 设置中心 → 性能组新增同名行（main_window/hub_pages.py）。

## 四、实测数据

环境：offscreen（CPU 软件光栅，**不含 DWM 合成**），管理面板球桌页 60 行 × 13 列，
--win 1600x900 --scale 1.0，--truth --steps 10 --rounds 2。

| 委托变体 | 修复前 自然路径 | 修复后 自然路径 | 绘制面积/步 |
| --- | ---: | ---: | --- |
| prod（_ReadOnlySelectDelegate，生产现状） | 10.01 ms（0.38 + 9.56） | **1.28 ms**（0.30 + 0.98） | 1,173,120 → **1,547** px²（1/758） |
| default（qfw 默认委托） | 13.51 ms（0.42 + 13.10） | **1.53 ms** | 同上 |
| lean（LeanTableDelegate） | 5.44 ms（0.44 + 4.98） | **1.80 ms** | 同上 |
| cache（整格缓存原型） | 3.77 ms（0.42 + 3.34） | **0.71 ms** | 同上 |

要点：

- 修复前「响应」只占 4%，**96% 是整视口光栅**；修复后每步只剩「一行高 × 可见列数」的条带。
- 历史优化（S1 轻量委托、S2/S5 缓存）降的是**每格成本**，对整视口重绘是线性收益；
  本次修复降的是**每步光栅的格数**（约 260 格 → 13 格量级），两者可叠加。
- offscreen 无 CJK 字体，真机整形成本更高，**修复的相对收益只会更大**。
## 五、第一版事故复盘 + 第二轮的形态

### 5.1 第一版为什么不可用（真机截图 + offscreen 复现）

第一版只做了一件事：把 viewport 的 `WA_OpaquePaintEvent` 置 True。收益与代价是同
一件事——Qt 因此允许位块搬移，同时**不再代擦 viewport 背景**。而本项目表格的像素
本来就不是自己画满的：qfw QSS 把 `QTableView` / `::item` 背景设为 transparent、
单元格还有 `margin=2` 的透明缝隙、行底色只有 hover/选中/隔行才画。结果：标记为
「不透明」的 viewport 里，没人负责的像素保留上一帧 → 真机滚动整片叠影
（offscreen `page.grab()` 同根因表现为表格区纯黑）。

### 5.2 第二轮的形态（本版）

1. **先标定再开启**：`_sample_table_bg()` 在表格四边各取一个**紧贴表格外侧**的
   全局点，用 `QScreen.grabWindow(0, x, y, 1, 1)` 抓**屏幕真实像素** —— 这是唯一
   能拿到「用户真正看到的颜色」的途径（含主题色 / Mica 背景 / 业务 QSS）。
   可信度门槛：至少 2 个有效采样且颜色**完全一致**才采信；抓不到或互相矛盾 →
   不标定（功能静默不生效）。标定在事件循环里做（`QTimer.singleShot(0)`）。
   offscreen 平台没有真实屏幕，退化为「渲染父级 1×1」**仅供离线回归**。
2. **每次绘制先填满**：给 viewport 装一个 Paint **事件过滤器**（`_make_blit_filter`），
   在 paintEvent 之前用标定颜色 `fillRect(ev.rect())` 再放行。用过滤器而不是包
   `TableBase.paintEvent`：过滤器一定先于 paintEvent 执行（无论哪个子类实现了
   paintEvent），否则自带 paintEvent 的子类会绕过填底而 viewport 仍被标为不透明
   = 又变成第一版那种叠影。整屏首绘、滚动新露出条带、hover 局部都走同一条路径，
   搬移不变式（未暴露区域来自上一次正确像素）因此成立。
3. **失败安全**：取不到颜色 → 不设不透明 → 功能静默不生效（绝不出现「没人画底
   的不透明 viewport」）。
4. **主题切换失效重建**：颜色是实测像素，不能跨主题复用；挂
   `qconfig.themeChangedFinished` 清缓存并重新标定。
5. **仍然需要条带**：给 viewport 右侧/底部预留悬浮滚动条条带（`_blit_strip_width`
   + 包装 `TableBase.updateGeometries`），解决「阻断 B」。代价是内容右侧/底部各
   让出 13px、最后一列会重排（这是设计内的视觉变化）。

### 5.3 第三处修正：取色源（真机第二次反馈）

**现象（2026-10-06 真机）**：开启后表格组件底色不对 —— **暗色主题下是纯黑，
浅色主题下是灰白**。

**机理**：第二轮的标定用 `parentWidget().grab(1×1)`。本项目页面本身背景透明
（"透明叠透明"一路透到窗口/云台背景），渲染父级时 Qt 只能拿该控件的
**palette 色**回填 —— 于是拿到的是 palette，而不是用户看到的那层颜色。

**修正**：改为抓**屏幕真实像素**（`QScreen.grabWindow(0, x, y, 1, 1)`），
并要求四个采样点（上/下/左/右，各距表格 6px）中至少两个有效且颜色完全一致；
不一致（例如有窗口遮挡、或表格四周不是纯色）就**不标定**。

**保留的局限**（写下来避免再踩）：

- Mica 场景下取到的是「标定当刻的背景虚化」，表格区会固定成那个颜色而不再随
  壁纸实时变化——表格区基本被行底色覆盖，观感影响很小，但属于有损近似。
- 采样点必须落在表格外侧：若表格四周紧贴其它控件（无 6px 间隙），采样会命中
  别的控件 → 多点不一致 → 功能自动不生效（宁可不加速，也不填错色）。

## 七、对既有文档的口径修正

判据：**绘制面积/步**应从「≈1.000 视口当量」掉到「≤0.01 视口当量」。
面积口径与机器快慢无关，是比 ms 更稳的**机制**判据；ms 用来对比修复前后的同一台机器。
⚠️ 但面积判据**不能**作为可用性验收（本轮教训）——必须同时做**像素等价**：
同一状态下「搬移渲染」与「强制整视口重绘」的结果逐字节比对，再上真机目视。
  而不是「Qt 本来就这样」。
- docs/大屏与超高DPI渲染性能调查报告2026-09-25.md §4.1 的三处口径过期（上一轮调研已列出）
  仍未回改：默认动画路径已变为「卡片级淡入」「菜单 FADE_IN 映射」，
- 本文之后，「表格滚动慢」的排查顺序：① 用 `--truth` 看**绘制面积**判断是否在位块
  搬移路径上；② 若要走搬移，先确认**像素由谁画满**（本轮就是栽在这里）——
  「面积对了」不等于「画面对了」。
  （用 --truth 看绘制面积），而不是继续优化每格成本。
