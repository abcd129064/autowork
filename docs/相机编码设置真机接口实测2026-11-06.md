# 相机编码设置真机接口实测 2026-11-06

> 设备：DH-IPC-HAC9488XY-HY，固件回包口径以本机为准；接入方式沿用「相机工具」页
> 的 frp 隧道会话（49.235.34.253:4238，admin）。
> 本文是「编码设置」页字段口径的唯一依据：页面控件是否可写、tooltip 怎么写、
> 哪些字段仍属未知，都以这里的实测结论为准，不再凭设计稿推测。

## 一、背景

「编码设置」页（`windows/camera/encode_page.py`）UI 已按
`design/encode_settings_v6_three.html` 完成，本次只修设备调用层与读写校验，
不动布局与交互结构。修复前的问题集中在五处：

1. `core/dahua_sdk.py` 把 ENCODE_VIDEO 的通道写死成 0，页面「通道」下拉是摆设；
2. 一次 UI 任务里连着发多个配置请求（读主+辅两路、RMW 的读-写-回读），
   节流只做在 UI 执行层的任务之间，任务内部漏掉了；
3. `SetNewDevConfig` 按**字符数**报载荷长度，中文配置名会被截成半截 JSON；
4. `VideoColor` 按 `table[0]` 取色，撞上"第 0 行是停用时段"就读到没人用的参数；
5. 写后读回比对用 `str()` 比，帧率写 20 回来 20.0 被误判成"没生效"。

## 二、实测能力矩阵

探针逐字段「改值 → 读回 → 恢复原值 → 再读回」，全部写入都已复原
（收尾全量比对：无漂移）。

### 可写且落库

| 配置 | 字段 | 通道 |
| --- | --- | --- |
| ENCODE_VIDEO 1100 | 编码模式 / 码流控制 / 码率上限 / 帧率 / I 帧间隔 / 图像质量 / 视频使能 | 主码流、辅码流1 |
| ENCODE_VIDEO 1100 | 分辨率（width+height） | **仅主码流** |
| 1306 曝光 | 曝光模式 / 抗闪 / 曝光补偿 / 增益 | ✔ |
| 1309 背光 | 背光模式 / 宽动态等级 / 强光抑制 | ✔ |

### 读得到、写不进（固件"接受但不落库"）

`SetConfig` / `SetNewDevConfig` 一律回成功，读回仍是原值：

- `VideoColor`（亮度 / 对比度 / 饱和度 / Gamma / 色度）——试过整表回写、
  只发生效行、只发首行三种载荷，结果一致；
- `VideoInOptions`（白平衡模式、红/蓝增益 GainRed/GainBlue、日夜切换模式、
  灵敏度、延时）——整表写入均不落库；
- `Lighting`（补光模式、强度）；
- 1202 / 1203 音频输入输出音量；
- 9601 的镜像 / 翻转（能力位 `bMirror`/`bFlip` 反倒回 true，说明能力位不可信）。

### 固件直接拒收（SDK err 21 "verify returned data"）

- 9601 的 `nRotate90`（旋转）；
- **辅码流1 改分辨率**（1280×720 与 704×576 都拒，主码流同样两档却可写）；
- `Encode` JSON 整张表（含 `AudioEnable`、`Audio.Compression`、
  `Audio.Frequency`、`Video.Quality` 等任意字段）。

### 本机不存在

- 1312 透雾：GetConfig 回"设备不支持当前操作"；
- `VideoEncode` / `VideoIn` / `AudioEncode` / `DayNight` / `WhiteBalance` /
  `EncodeCaps` 等 NewDevConfig 名：SDK 回"当前 SDK 不支持该功能"；
- 防抖：9601 的 `nStable` 能力掩码回 0（页面据此保持禁用）。

### 能力集接口本身不可信

`GetDevConfig(DEVICECFG=0x0001)` 能读到 `DH_DSP_ENCODECAP`，但本机
`dwImageSizeMask=131072`（只点亮 720P）与实测"主码流 1080P 可读写、
辅码流 640×360"直接矛盾，`dwEncodeModeMask=128`（只点亮 H.264）也和
"辅码流可切 H.265"矛盾。结论：**分辨率/编码模式选项表不能由该掩码驱动**，
仍以设备现值 + 预设候选 + 写后读回为准。`dwStreamCap=3`（主码流+辅码流1）
与实测一致，可用于判断有哪几路。

## 三、已修复接口

### `core/dahua_sdk.py`

| 接口 | 修复 |
| --- | --- |
| `_cfg` / `_pace`（新增） | 所有 GetConfig/SetConfig/Get·SetNewDevConfig 走同一出口，相邻请求强制补出 0.25s 间距；节流从 UI 层下沉，任务内部的背靠背不再漏 |
| `classify_error` / `_fail`（新增）、`DahuaSdkError.kind` | SDK 原文错误翻成处置建议并归类为 rejected / unsupported / transport / illegal |
| `_with_retry` | 只对 transport 类重试；设备拒收重试只会白等并放大误写风险 |
| `set_json_config` | 载荷长度改按**字节**报；附带 `err` 码入消息 |
| `json_config` | 缓冲区 32 KB → 128 KB，且检测花括号不配对并按"截断"报错，不再吐半截 JSON |
| `encode_video` / `set_encode_video` / `_encode_video_struct` | 增加 `channel` 形参（此前恒 0） |
| `image_ctrl` | 返回 `stable` / `stable_sensitivity` 能力位 |
| `_rows` / `_active_row`（新增）、`video_color` | 按 TimeSection 启用位取生效行，不再靠 `table[0]` 的行序凑巧 |
| `set_video_color` / `set_video_options` / `set_lighting` | 统一"写后读回"契约（返回设备真值，原来返回 None 逼调用方多发一次 GET） |
| `set_video_color` | 只改生效行，停用时段不再被顺带改写 |
| `video_options` / `set_video_options` | 补 `gain_red` / `gain_blue`（真机回包里就有） |
| `_set_channel_name` | 同样改按字节报长度（中文通道名截断） |

### `windows/camera/encode_page.py`

| 位置 | 修复 |
| --- | --- |
| `_channel` / 各读写入口 | 顶栏「通道」真正下发到设备；换通道作废已读态；预览起流也跟随通道 |
| `_read_ok` + `_refresh_gate` | 未读到设备现值不放行「应用」，杜绝把滑块构造默认值（色彩 50、增益 0）写进设备 |
| `_build_stream_card` 自定义分辨率 | 选中「自定义…」时宽/高回填设备现值，不再停在 SpinBox 下限 176×144 |
| `_on_apply` | 逐字段写后比对（`_diff_stream` / `_same_value`），按设计稿字段名报"哪几项没生效"；被拒时回读纠偏，卡片不停在被拒档位 |
| `_on_read`（读取全部） | 从"只读两路码流"扩到码流 + 图像属性 + 色彩 + 6 个 P2 分组，逐批计数并汇总失败项 |
| `_read_image` / `_on_apply_image` | 9601 与 VideoColor 合并成一批（少一次排队），任一失败不拖累另一段 |
| `_mark_no_land` / `_clear_no_land` | 改过的字段一个都没落库 ⇒ 整栏置灰 + tooltip 写明"该固件接受写入但不落库"；重新读取则放行还回 |
| `_group_labels`（specs 自带卡名） | "未生效"提示从 `white_balance` 这类内部键名改成设计稿字段名 |
| 占位 tooltip | 换成实测口径：除雾=设备不支持 1312；音频编码/采样率=Encode 可读但拒写；红蓝增益=GainRed/GainBlue 存在但不落库；快门=dbExposureValue1/2 与 1/N 档无可靠换算；防抖=按 nStable 能力位决定 |

## 五、仍存在的问题与待跟进字段

1. **辅码流分辨率选项是虚构能力**：4238 拒收 1280×720 / 704×576，但 UI 仍把它们
   列为候选（其它固件可能需要）。当前靠"被拒后回读纠偏 + 报出拒绝原因"兜底，
   理想做法是按机型能力集裁剪候选项——而本机能力集接口自身不可信（见第二节），
   需要先找到可靠的分辨率能力来源。
2. **色彩 / 音量 / 白平衡 / 日夜 / 补光 / 镜像翻转在本机是只读**：靠写后读回
   判空转再置灰。要事前判准（第一次进页面就置灰而不是等用户点一次），需要
   一份机型 → 落库能力的登记表。
3. **快门**：1306 里是 `dbExposureValue1/2`（毫秒，0.1~80），设计稿写的是
   1/25、1/100、1/10000 这样的秒档；真机回包 `ExposureValue1=0 /
   ExposureValue2=40`。换算关系未经确认，仍为禁用占位。
4. **音频使能 / 编码 / 采样率**：`Encode` JSON 读得到（G.711A / 8000 /
   AudioEnable=true），写入被整表拒收。目前仍按占位处理；若要做成"只读展示
   设备真值"，需要给分组卡补一条"只接线不写回"的通道。
5. **防抖 / 锐度 / 2D·3D 降噪 / BLC 区域 / 补光灵敏度 / 日夜电子机械类型**：
   或本机能力位为 0，或字段未在 core 导出，维持禁用。
6. **MainFormat 有 4 项、ExtraFormat 有 3 项**：本次只按索引 0 理解（ENCODE_VIDEO
   1100 走 emFormatType=1/4 已够），索引与"普通/动检/报警"场景的对应关系没机会
   验证（Encode 表整体拒写）。多码流机型（辅码流2/3）需要扩 `STREAM_*`。
7. **AGENTS.md §5.2 测试基线过期**、`docs/README.md` 里"大华相机工具集成调研"
   仍标"调研快照（待实施）"，实际已落地两页，可一并订正。
