## 〇、环境注记（修正 §5.1 解释器认知）

`docs/Qt内联引导说明.md` 的标准引导模板（`os.add_dll_directory` 三目录 + `QT_PLUGIN_PATH`，置于一切 import 之前）在 **miniconda 解释器（PySide6 6.11.0 + qfluentwidgets 1.11.2）** 下于普通 PowerShell（非 conda base 激活态）实测完全可用。AGENTS §5.1 「miniconda 的 PySide6 已损坏」仅适用于 conda base **激活态**（PATH 注入 conda 自带 Qt DLL）且无引导的场景。本轮两个 harness 均以 miniconda + 内联引导 + `QT_QPA_PLATFORM=offscreen` 运行，这是目前唯一能同时提供 PySide6 与 qfluentwidgets 的可用组合。

数据规模：临时库 kd_status 10 000 行（昨日/前日两分区）+ billiard_tables 1 000 行 + 售后 3 000 行；页面 50/100/300 行档；每项 3 次取中位。offscreen 无 GPU，真机数值通常更高（叠加渲染与销毁）。

## 二、问题清单（新发现 M / 行为项 B）

### M1【P1】设备页首次切入：日历缓存预建 77ms 主导了 110ms 首切卡顿

- **触发路径**：`device_page.py:607` `QTimer.singleShot(0, self._apply_calendar_cache)` → `_apply_calendar_cache()`（:754）同步构建 CalendarView（缩到今年 ±10 年的日视图，逐日生成 ~7 300 个日期项）。
- **量化证据**：中位 76.7ms / 首次 102.6ms（`A4b`）；DevicePage 懒构建 e2e 110ms 中它占 ~70%（`A4`）。注释里的「约 40ms」是当年估值，实测已翻倍（qfluentwidgets 1.11.2 的 DayScrollView 变重？待深究，但事实成立）。
- **设计已做的对冲**：缩跨度（100 年→±10 年）、延后 singleShot(0)、构建完成前点击日历走默认重建路径。问题在于 singleShot(0) 只是排到队尾，用户感知的「首次切页到可操作」窗口内它仍在主线程串行执行。
- **影响面**：仅 kd 数据源、仅首次进入设备状态页；每次打开管理面板后第一次切页必然发生。

### M2【P1】GamePage 打开面板即全建 4 个游戏（38ms，窗口构造的 40%）

- **触发路径**：`window.py:68` `self.game_page = GamePage(self)`（无 `_lazy_built` 模式）→ `moyu_page.py:84-87` 一次性构造 MoyuReaderWidget / Game2048Widget / SnakeWidget / MinesweeperWidget 并全部入栈。
- **量化证据**：GamePage 构造 36~45ms（`A1`/`A8`）；ManagementPanelWindow 构造 96ms 中它独占 ~40%。
- **影响面**：管理面板是常驻窗口，该成本只在打开面板时付一次；但它是构造期最大可削减项，且四个游戏里三个（2048/贪吃蛇/扫雷）多数用户不会用。

### M3【P2·行为项】HealthPage 页面不可见仍每 30 分钟全量拉接口+落库+重建

- **触发路径**：`health_page.py:648-656` 两个常驻 QTimer（30min `_fetch_timer` 拉微信接口全量 health → `sync_health_alerts` 落库；1h `_display_timer` 从库重载重建表格）；页面隐藏/面板最小化期间照常触发。
- **量化证据**：主线程无感（全异步，`_rebuild_table` 24ms@1000 行）；成本在**网络与服务器侧**：每 30 分钟一次全量接口拉取 + 全表落库写放大，即便用户根本没在看健康度页。
- **对照**：球桌页 frps 列刷新已做 `isVisible()` 门控（`table_page.py:451`）；售后面板自动刷新轮询已做 show/hideEvent 联动停启（`records.py:589/696`）。HealthPage 是全程序里唯一没有可见性门控的周期任务。

### M4【P2·微项】`_refresh_frps_column` 循环内重复枚举列索引 + 对已有 item 重复 setItem

- **触发路径**：`table_page.py:434-447`：`next((i for i ... enumerate(TABLE_COLUMNS) ...))` 写在行循环体内，每行重复枚举（O(rows×cols)）；且 `tbl.setItem(r, col, cell)` 在 cell 就是该格现有 item 时重复插入，Qt 每次 emit `QTableWidget: cannot insert an item that is already owned by another QTableWidget`（本轮 harness 实测每格一条警告）。
- **量化证据**：50 行 0.5ms——性能无感，但警告刷屏（本轮 stderr 数百条）掩盖真实日志；列索引与 item 复用均为一行改动。

### M5【确认项】HealthPage `_rebuild_table` 1000 行 24ms（09-23 修复维持）

- 09-23 修复（CheckBox cellWidget → 可勾选 item + delegate）声称纯 item 重建 ~10ms；本轮实测 24ms@1000 行（含每行 5 item 着色、stale 黄底分支、blockSignals）。告警实际量级通常远小于 1000 行，**无需行动**，仅确认无回归。

## 四、解决方案（按收益/成本比降序）

> 均不改业务语义：游戏逻辑、日历选择范围、健康度数据时效口径全部保持。

### N1【P1】DevicePage 日历缓存构建再延后 + 让路首查

- **改法**：`_apply_calendar_cache` 的触发从 `QTimer.singleShot(0, ...)` 改为**首查填充完成后 + 空闲延迟**（如 `singleShot(800ms)` 或首查回调里补发）；日历构建前的窗口期用户点击日历走默认重建路径（现有兜底分支已覆盖，功能不缺失）。
- **预期收益**：首次切页「到可操作」**110 → ~35ms（-70%）**；日历预建 77ms 移出用户感知窗口（点开日历前大概率已完成）。
- **成本**：~5 行；**风险**：低（兜底路径是既有代码，非新增逻辑）。
- **回滚**：恢复 singleShot(0) 一行。

### N2【P1】GamePage 懒构建（复用 DevicePage 现成范式）

- **改法**：`GamePage.__init__` 只建壳（`_lazy_built=False`）；`showEvent` 首次进入执行原构造体。与 DevicePage/AdminSettingsPage 的懒构建范式完全一致。
- **预期收益**：ManagementPanelWindow 构造 **96 → ~60ms（-37%）**；首次切到摸鱼中心 +40ms（可感知性低——用户是主动切过去的）。同时省 4 个游戏控件的常驻内存。
- **成本**：~10 行；**风险**：低（游戏无跨页状态依赖；`auto_resume/auto_pause` 逻辑挂在 stack.currentChanged 上，随懒构建整体后移不受影响）。
- **回滚**：还原 `__init__` 即全量构建。

### N3【P2】HealthPage 定时任务加可见性门控

- **改法**：`_fetch_health_data` 入口与 `_refresh_display` 增加 `self.isVisible()` 判断；定时器照跑但页面隐藏时跳过，`showEvent` 时若距上次拉取/展示超过冷却间隔则立即补一次（对齐 TrendPage 的 `_REFRESH_COOLDOWN` 模式，`health_page.py:397-410` 已有现成写法）。
- **预期收益**：页面不可见期间不再有 30 分钟一次的全量接口拉取与全表落库（**网络/服务器/写放大侧收益**，非 UI 线程）；数据时效口径不变（回看页面即补拉）。
- **成本**：~15 行；**风险**：低（「已处理」勾选状态在重建时丢失的场景与现状一致——现状 1h 定时重建同样会重置勾选）。
- **回滚**：去掉门控两处判断。

### N4【P2·微项】`_refresh_frps_column` 列索引外提 + item 复用改 setText

- **改法**：frps 列与 snk 列的索引在循环外 `next()` 一次；已有 item 时只 `setText`/`setForeground`，无 item 才新建（消除 Qt 重复插入警告刷屏）。
- **预期收益**：0.5ms → 忽略不计；主要是**日志清洁**（数百条警告/次刷新）。
- **成本**：~6 行；**风险**：无。

## 五、伪优化「不做」清单（本轮确认）

| 项 | 不做原因 |
|---|---|
| 日历缓存缩到 ±3 年以内进一步提速 | DayScrollView 跨度即用户可滚动选日期的边界，设备页按日期分区查历史数据，任意收窄都会限制业务可选日期；77ms 已移出感知窗口（N1） |
| CalendarView 全局单例跨页共享 | 与 picker 的信号绑定/生命周期解耦后需要重新处理 resetted/dateChanged 接线与窗口归属，回归面大于收益 |
| HealthPage 拉取改增量/WebSocket | 接口只有全量 health 能力；数据源能力限制 |
| 游戏控件迁独立窗口/进程 | 功能架构变更，与「摸鱼中心」页签形态冲突 |
| `_populate`/查询进一步微优化 | 1.4ms/0.7ms 已贴近 Qt 下限，无优化空间 |
| FTS rebuild 提示/迁移 | 一次性成本且已有 `fts_built` 幂等标记，真实库常驻不重复 |
| 售后 EditRecordDialog 实例复用 | 09-06 报告 R1 维持 P2 的结论复测后依然成立（32ms 且低频） |
