# MySQL 访问 frp STCP 隧道实施方案（2026-11-06）

> 状态：**设计·待实施**（生产侧未动，客户端代码未动；本文档为实施蓝图 + 回滚预案）
> 背景：桌面端直连生产 MySQL（49.235.34.253:3306），服务器端以「来源 IP 白名单」作为
> 访问控制，用户换网络（回家）即失效。方案把身份凭证从「IP」换成「sk + token」：
> 所有外部访问走 frp STCP 隧道，MySQL 彻底退出公网。
> 姊妹文档：[MySQL同步API化立项2026-11-06.md](MySQL同步API化立项2026-11-06.md)（终态方案，
> 本隧道为 API 化完成前的过渡通道，API 化落地后自然退役）。

---

## 1. 架构

- **客户端（每台 autowork 机器）**：frpc 进程内加一条常驻 `stcp` visitor，
  本地绑定 `127.0.0.1:33007`；桌面端 MySQL 连接串改指 `127.0.0.1:33007`。
- **frps（49.235.34.253:7900）**：仅做中转，**不监听任何公网业务端口**；
  认证 = 强 token（加固后替换现行弱值）。
- **生产机**：常驻一个 frpc（role=server，stcp proxy `mysql_sync`，
  `sk=<强随机>`，转发 `127.0.0.1:3306`）；MySQL 收紧为仅本机监听。
- **身份模型**：持有同一 sk 的 visitor 才能建隧道；MySQL 账号收紧为
  `sync@'127.0.0.1'`（最小权限，仅业务库）。

与相机隧道（xtcp 打洞）的差异：本隧道走 frps 中转（stcp），不受 NAT 打洞
成功率影响，适合「稳定可达优先于带宽」的 DB 流量；中转多一跳约 10~40ms，
对现有 `query_page` 0.14ms 级无感。

## 2. 凭证

- 需要两个强随机值：`FRPS_TOKEN`（frps 认证）与 `MYSQL_STCP_SK`（隧道密钥）。
  真实值由运维生成后妥善保管（不入库、不进文档、不进提交历史），
  本文档一律以 `<FRPS_TOKEN>` / `<MYSQL_STCP_SK>` 占位。
- **生产实况（2026-11-06 只读侦察确认，`/opt/frp_0.65.0_linux_amd64/frps.toml`）**：
  - `auth.token` 长度 3、前缀 "123" → 弱 token 实锤，批 B 必换；
  - `webServer.user="admin"` / `password="abc123"`，且 `webServer.addr="0.0.0.0"` 监听 7400
    → **frps 管理面板弱口令公网裸奔**，与客户端 frps_admin 概览卡共用，批 B 必须一并换强口令
    （保持 0.0.0.0 可达以供桌面端 frps_admin 使用，或经用户决策收敛来源）；
  - `enablePrometheus = true`：指标端口随 webServer 暴露，随口令一并处理；
  - frps 为手工拉起（无 systemd、无 crontab），**重启不自愈**——批 B 顺手 systemd 化；
  - frps 版本 0.65.0：stcp 能力远早于该版本，**无需升级**，避免版本墙回归面扩大；
  - `log.level = "debug"` 生产环境，建议顺带降为 info；
  - 客户端侧弱值：`frpc_xtcp_panel.toml:4` `auth.token = "123"`；各 visitor
    `secretKey = "abc123"`（含 `core/frp_remote.py:660-661` 的 `_default_secret_key`
    回退值）——加固时所有存量 visitor 的 sk 与 frps token 需同步更换。
- MySQL 现状：监听 `*:3306`（无显式 bind 行）、iptables/firewalld/ufw 均无规则
  → **「指定 IP 访问」实现在云安全组层**（控制台配置，SSH 侧不可见）；root 无免密登录，
  用户 host 授权留批 A 时用 DB 凭据核查；
- frpc server 端：生产机无常驻 frpc（批 A 全新部署）；二进制直接复用
  `/opt/frp_0.65.0_linux_amd64/frpc`（发行包自带，与 frps 同版本零兼容风险）。

## 3. 生产机侧改动（阶段 A，需运维确认后执行）

### A1. frps 加固

- frps 配置（`/opt/frp_0.65.0_linux_amd64/frps.toml`）中 `auth.token` 替换为
  `<FRPS_TOKEN>`；
- `webServer.password` 替换为强口令（保持 0.0.0.0:7400 可达，桌面端
  `core/frps_admin.py` 概览卡依赖该管理口）；
- frps systemd 化（`Restart=on-failure`，替代当前手工拉起、重启不自愈的状态）；
- `log.level` 由 debug 降为 info；
- 建议同时启用 `transport.tls.enable`（frpc 侧对应开启）。
- 影响面：所有客户端 frpc 的 token 同步更新——**相机隧道/远程面板会短暂断开**，
  需分批更新客户端配置后再观察。**不升级 frps 版本**（0.65.0 已支持 stcp）。

### A2. server 端 frpc（常驻）

```toml
serverAddr = "127.0.0.1"        # frps 与 MySQL 同机，走本机回环
serverPort = 7900
auth.method = "token"
auth.token = "<FRPS_TOKEN>"

[[proxies]]
name = "mysql_sync"
type = "stcp"
secretKey = "<MYSQL_STCP_SK>"
localIP = "127.0.0.1"
localPort = 3306
```

- 以 systemd 常驻部署（`Restart=on-failure`，参照现有 todeskd.service 模式）；
  该 frpc 与 MySQL 同机，`serverAddr` 走 127.0.0.1，不占公网流量。

### A3. MySQL 收紧（最后执行，撤白名单）

1. 确认客户端全部切换到隧道且同步正常（见 §5 阶段 C 验收）；
2. MySQL 账号：业务同步账号改为仅允许 `127.0.0.1` 来源；
3. `bind-address = 127.0.0.1`；
4. 防火墙/安全组：**撤掉 3306 公网放行规则**（保留 22 / 7900 / 80 / 443 等
   业务端口）。

## 4. 客户端侧改动（阶段 B，代码 scope）

现状事实（已核查）：

- frpc 为**单进程单 TOML**：`RemoteSessionManager`（`core/frp_remote.py:166`）
  持有唯一 visitor 注册表，写出 `frpc_xtcp_panel.toml`；
- visitor 块的 `type` 写死为 `xtcp`：`core/frp_remote.py:1240`；
- TOML 回读恢复：`core/frp_remote.py:124-163`（`_parse_visitors_toml`，无 type 字段）；
- 开机自愈链路：`autostart()`（`core/frp_remote.py:696`）恢复「启用中的全部隧道」，
  含 prewarm + 退避自愈（5s/30s/2min）。

改动点（5 处，全部小改，业务代码零改动）：

| # | 位置 | 改动 |
| --- | --- | --- |
| B1 | `core/frp_remote.py` 注册表记录 | visitor 记录新增可选字段 `type`（缺省 `"xtcp"`，向后兼容）；新增常量 `SOURCE_DB_TUNNEL = "数据链路"`（常驻标识，不进 `_PANEL_SOURCES`） |
| B2 | `core/frp_remote.py:1230-1248` `_write_visitor_blocks` | 按 `v.get("type", "xtcp")` 写出 type 行 |
| B3 | `core/frp_remote.py:124-163` `_parse_visitors_toml` | 回读时解析 `type`，防止重启后 mysql visitor 被恢复成 xtcp |
| B4 | 新增注册入口（如 `ensure_db_tunnel()`） | 固定 `serverName="mysql_sync"`、`type="stcp"`、`bindPort=33007`（固定端口，走 `register_visitor` 的冲突检测）、专用 sk 从 settings 读 `mysql_stcp_sk`；`disabled` 恒 False，禁止 UI 删除/断开 |
| B5 | 隧道面板 UI（消费 `records()` 的窗口） | 按 `source == SOURCE_DB_TUNNEL` 过滤或单独分组展示——常驻数据链路不是用户会话 |

busy 契约分析（为何不冲突）：

- SFTP 会话队列上限 3 的统计口径是 `open_session` 的 snk 会话，mysql visitor
  永不经 `open_session` → **不占并发位**；
- `is_busy_on_port` 按端口查询，33007 固定且不会被会话分配（会话端口走
  `generate_random_port(exclude_ports=used_ports())`，33007 在注册表内必被排除）；
- `remove_visitors_by_source`（`core/frp_remote.py:498`）按 source 删，
  `SOURCE_DB_TUNNEL` 不在面板来源集合 → 「清空手工隧道」不会误删数据链路。

连接切换（不改代码，走现有配置）：

- `database/mysql_sync.py:18-24`（`_load_mysql_config`）与
  `database/backend.py:58-93`（`_read_mysql_settings`）读 settings 的
  database 域：`host=127.0.0.1`、`port=33007`（DPAPI 域，用设置界面改，不动 config 文件）。
- 降级链路复用现状：隧道断 → MySQL 连接失败 → `mark_degraded()` 透明回退
  本地 SQLite（LWW），恢复后自动合并——与「MySQL 网络不可达」是同一分支，无新增逻辑。

启动就绪：`autostart()` 拉起 frpc 后 visitor 注册即含 mysql_sync；
首个 DB 连接的 0.5~5s 冷启动窗口由现有 `_PORT_READY_*` 轮询（200ms 间隔、
8s 上限）与连接重试覆盖。

## 5. 执行顺序（三批，每批可独立回滚）

| 批 | 内容 | 验收 | 回滚 |
| --- | --- | --- | --- |
| A | 生产机：A2 常驻 frpc（先不动 frps token、不动防火墙） | 客户端手工加 stcp visitor 连 `127.0.0.1:33007` 可同步 | 停用并移除该 frpc 服务 |
| B | frps token 加固 + 全部客户端 frpc 配置同步换 token；客户端代码 B1-B5 上线（走正常发布链） | 相机隧道/远程面板回归无新增失败；mysql 隧道家里+现场各一台真机同步正常 | frps 换回旧 token；客户端连接串切回直连 |
| C | MySQL 收紧（A3：bind 127.0.0.1 + 撤公网规则 + 账号收紧） | 撤规则后 24h 内隧道同步零异常；`verify` 对比直连数据一致 | 恢复防火墙放行规则即可（frp 侧不动） |

> 批 A 先行的理由：A 不影响任何存量链路，纯增量；出问题删服务即回滚。
> 批 B 的客户端代码与发布走既有自动更新链（整包 zip + updater）。

## 7. 风险与关联挂账

- **frps 弱口令是前置条件**：不换 token/sk，隧道建在弱地基上（§2）；
- frpc 成为 DB 前置依赖：自愈三档兜底 + SQLite 降级链路现成，风险可控；
- 生产操作全部走 `tools/deploy/prod_ssh.py`（密码仅从环境变量
  `AFT_SSH_PASS` 读取），实施前向用户确认 scope 与回滚（AGENTS.md §3.4）；
- 延迟：中转 +10~40ms，对 0.14ms 级查询与同步链路无感；
- 本隧道是 API 化（见姊妹立项文档）完成前的过渡通道，API 化收口后退役。
